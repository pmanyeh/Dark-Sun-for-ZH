## 1. 專案現況的整體結構：兩條並行路線

本專案實際上同時在跑兩條互相獨立、彼此互補的路線，兩者共用同一份翻譯語料，
但程式碼與 repo 完全隔離：

| | 路線 A（本 repo，主專案） | 路線 B（`dsun-hires-text-poc`，獨立 repo） |
| --- | --- | --- |
| 做法 | 維持遊戲原生 320×200，逐畫面 patch EXE／overlay／GFF，必要時重新設計版面塞入中文 | 讓 DSUN.EXE 自己持續輸出 1024×768（或其他）VBE，先求全遊戲穩定顯示，再做真正高解析中文字型 |
| 現況 | 持續在出可驗收的候選版（v55→v57→v58b→...），已有實機驗收證據 | 仍在 Phase 1（全遊戲持續高解析顯示基礎），Hires 中文本身尚未開始 |
| 優點 | 風險低、逐步可玩、失敗範圍侷限在單一畫面 | 一旦打底完成，理論上可系統化涵蓋所有畫面與字型品質 |
| 缺點 | 每個畫面都是手工外科手術，overlay relocation 等衝突要逐一處理，不會因為做過的畫面變多而變輕鬆 | 需要逆向整個 graphics driver，時程不確定；目前已知還有未掃描的程式碼區域，可能藏著新問題 |

`dsun-hires-text-poc` 的 `baseline/` 快照標註為主專案的「v59」，時間點與本 repo
`re_71`（v58b，2026-09-11）銜接一致，證實路線 B 是從路線 A 當時的成果分支出去的，
兩者血緣相同、之後各自獨立發展。

## 2. 路線 B 現況摘要（背景參考，供對照）

以下整理自 `dsun-hires-text-poc/v9` 最新交接文件（`delegation/HANDOFF_NEW_SESSION_2026-09-16.md`
及對應 result log）：

- 目前候選：`runtime-ram-buffer-mirror-v65`。已用 RAM chunky surface 鏡像取代
  `draw_dot`／`draw_line`／`draw_rect`／`draw_bitmap`／buffer copy／`show_page` 等
  原生繪圖 ABI，搭配 resolver／registry／EMS mirror，遵循「原生優先執行、鏡像失敗
  就靜默 fallback」的安全設計。
- 已在真實遊戲流程證實：VIEW 人物頁、裝備 hover、VIEW→USE、一段真實門口對話，
  全程維持 1024×768 VBE、零次 fallback。
- 已知未解問題：VIEW→世界地圖切換仍會釋放並重新取得一次 VBE；對話回應畫面下半部
  文字框內容與 Mode-X 參考畫面不一致（同步/複製來源 bug，未解）；presenter 預設仍
  是關閉狀態（`ram_present_tick_dispatch == 0000:0000`）；尚未做任何長時間穩定性測試。
- **尚未測試的範圍**：片頭、主選單、載入、戰鬥、存讀檔、色盤效果——驗收清單中
  超過一半仍是空白。
- `audit_native_graphics.py` 稽核（`artifacts/native-graphics-vga-audit-v2.json`）
  顯示 graphics segment 還有 **10,437 bytes 完全未掃描**、32 處 VGA port 存取
  沒辦法靜態確認、一個連用途都還沒指認出來的函式 `post_cursor_helper807C`。
  代表已知的繪圖函式清單可能不完整，尤其是尚未測過的戰鬥／存讀檔等區域。
- Hires 中文字型渲染本身在這個新架構裡**完全還沒開始**，`HANDOFF_NEW_SESSION_2026-09-15.md`
  明確列為 "Explicitly not complete"。

### 這次對話釐清／修正的關鍵架構認知

- **「無法整塊搬移 Mode-X 記憶體」的真正原因，不是平面遮罩本身**（那只是效能問題，
  已經用逐 plane 連續讀取解決），而是 **DSUN 沒有統一的「幀完成」訊號**：`show_page`
  只負責兩個硬體頁面的翻頁，但像裝備 hover 這類更新會**直接改寫目前可見頁**，完全
  不經過 `show_page`（實測證據：`re_75`，hover 事件序列 `show_page` 計數為 0）。
  這代表任何只 hook 翻頁時刻的「拍照式」放大方案，天生就會漏掉這類直接寫入。
- 這種「大範圍變更走雙緩衝＋翻頁、小範圍 UI 回饋直接寫可見頁」的混合模式，是
  1990 年代 VGA 遊戲常見的效能取捨手法，不是 DSUN 特有的怪異設計。
- 曾討論「用分頁保護＋page fault（INT 0Eh）攔截記憶體寫入」的構想：概念上等同
  hypervisor 的 MMIO 攔截技術（合理、業界常見的手法），但在此專案不可行，因為
  DSUN.EXE 是 16-bit real mode（沒有分頁單元可用），且要接到等效機制只能修改
  DOSBox-X 本身——這正是專案從頭到尾的硬限制（"Never modify DOSBox-X"）。DOSBox-X
  內部大概率已經用等效的 C++ memory handler 機制在做同樣的事。

## 3. 路線 A 現況摘要（下一個 session 的接續重點）

已驗收版本鏈：**v55**（使用者已驗收的啟動基準）→ **v57**（物品頁六列中文能力
標籤＋數字、背包及右側武器排版）→ **v58b**（VIEW CHARACTER 屬性頁重排）。

### v58b 已解決的（`re_71`）

六項能力值原本一欄六列（`STR/DEX/CON/INT/WIS/CHR`），改為**兩欄三列**：

```text
力量: 19    智力: 16       裝備格 1
敏捷: 21    智慧: 19       裝備格 2
體質: 19    魅力: 15       裝備格 3
```

利用橫向空間換取每列可容納 10px 字高的中文，裝備格三格同步重新定位。
114 個測試通過，DOSBox 實機驗收過載入、切換角色、裝備圖示更新。
只修補兩段準備參數機器碼（`0x8A0E8..0x8A114`、`0x8A149..0x8A16B`），保留原有
overlay relocation 資料不動，並新增 `verify_overlay_relocations` 檢查機制以防
重蹈第一版 v58（因覆寫 loader segment operand 被拒絕）的覆轍。

**這推翻了本輪對話一度做出的錯誤判斷**：曾誤判 VIEW CHARACTER 這種密集屬性頁
「必然需要路線 B（拉高解析度）」，但 v58b 證明**版面重新設計**（不只是單純放大
字格）也是路線 A 的有效手段之一，路線 A 的解法空間比預期更廣。

### v58b 明確尚未完成（`re_71` 原文）

種族／性別、陣營、職業和下半部資料（EXP、HP、PSI、AC、武器傷害等）
**維持原文與原座標，中文化尚未完成**。

### `re_68` 已定位但尚未實裝的固定字串

| 原文 | 檔案 offset | 草稿 | 備註 |
| --- | --- | --- | --- |
| `BACKPACK` | `0x4A1B3` | 背包 | **技術阻礙**：不經過 NAME-ID 解碼入口，是透過 far call thunk（`0x6E111`→`0580:005C`）傳遞任意字串指標；現有 FONT-local core 只接受 NAME ID 輸入，必須先確認新的解碼入口／寬度計算／字形快取／重繪機制才能處理 |
| `STR:`／`DEX:`／`CON:`／`INT:`／`WIS:`／`CHR:` | `0x4999B` 起 | 力量:／敏捷:／體質:／智力:／智慧:／魅力: | 六個標籤在 EXE 內**緊鄰排列**，直接塞入中文會覆蓋下一個標籤，必須另設字串儲存區並確認所有消費者與指標都正確修補 |
| `%C%C%CPSI:` | `0x4A3AC` | `%C%C%C靈能:` | 必須保留格式控制碼；還有其他相同原文字串，不能全域取代 |
| `AC: %2d` | `0x497C0` | `防禦: %2d` | 必須保留數值格式參數 |
| `Bone` | `0x4A109` | 骨製 | 材質上下文，經指標 `17A9:4356` |

另外 `敏`（U+654F）、`慧`（U+6167）尚未映射到既有字形庫（C0–C5 banks），需要
透過既有字庫建置流程分配 ID、產生字形、驗證。

## 4. 建議下一個 session 的切入點

1. 先讀 `re_68`～`re_73`，確認目前實際已驗收到哪一版（可能已超過本文件記錄的
   v58b／v60，需要用 `git log`／目錄時間戳核對最新狀態）。
2. 從 `re_71` 明確列出的「尚待完成」清單開始：VIEW CHARACTER 頁的種族/性別、
   陣營、職業、下半部數值。
3. 或從 `re_68` 列出但尚未實裝的固定字串開始，**優先處理沒有已知技術阻礙的項目**
   （`AC:`／`PSI:`／`Bone` 等單列字串），`BACKPACK` 因為需要先解出新解碼入口，
   複雜度較高，可留到後面。
4. 六個能力標籤（`STR:` 等）因為有「相鄰字串覆蓋」的已知風險，動工前務必先設計
   好獨立字串儲存區方案，不要重演 v58 第一版覆寫 loader segment operand 被拒絕的
   錯誤。
5. v55 仍是可隨時回退的驗收基準；所有新候選版都應該獨立 staging，不要直接覆蓋
   既有已驗收版本。

## 5. 使用者的長期目標（背景資訊）

使用者的最終目標不只是 Dark Sun 一款遊戲，而是想中文化多款 DOS 時代遊戲，並找出
「盡量」一致的工作流程，減少每次從零開始。核心技術痛點：許多 DOS 遊戲原生字型
只有 8×8，塞不下中文。本輪對話整理出的可重用資產／方法論：

- 翻譯字串 hash 打包模式（`dsun-hires-text-poc` 用 FNV-1a 對照原文字串與翻譯後
  glyph 序列，不重複存 Unicode 字串本體）。
- TTF → 點陣字型建置流程（高解析度繪製 → 縮放/synthetic embolden → 量化成幾階
  coverage → 封裝成 bitplane），與哪一款遊戲無關，可直接搬用。
- 尋找文字繪製函式的方法論：breakpoint 追蹤所有寫 VRAM 的呼叫 + 覆蓋率稽核工具
  （如 `audit_native_graphics.py`）確認有沒有漏掉。
- 判斷「這款遊戲該走路線 A 還是路線 B」時，**不能只憑直覺判定某個密集資訊頁
  『放不下』就跳去路線 B**——v58b 證明版面重新設計（如雙欄化）的解法空間比預期
  更廣，應該先認真嘗試路面重排，解不掉才升級路線 B。
