# 動態除錯成果第二輪：用記憶體寫入斷點鎖定 FUN_0000_5160、追出常駐段的通用 GFF 載入器

> **日期**：2026-08-11（延續 `re_08`，同樣是人在場操作 DOSBox-X 除錯器完成，這次改良了鎖定目標的方法）
> **前提文件**：`re_07_verified_gpl_loop_and_dosbox_setup.md`（`FUN_0000_5160` 的靜態反編譯與記錄格式）、`re_08_overlay_manager_dynamic_trace.md`（overlay manager 機制與環境設定）

---

## 1. 這次做了什麼

延續 `re_08` 想找 `Loadgamefromdisk`/解壓縮邏輯的目標，這次分兩階段：

1. **靜態階段**：對已匯入 Ghidra 的 `overlay_chunk1.bin`（`re_08` 用過的同一份），重新檢視 `FUN_0000_5160` 反編譯結果裡呼叫的三個函式（`FUN_0000_15ab`、`FUN_0000_1b74`、`FUN_0000_14a4`），用**原始機器碼位元組**（不信任反編譯輸出）核對，發現這三個函式在這份靜態匯入的 64KB 切片裡**只有 2~4 bytes**（例如 `FUN_0000_14a4` = `33 C0 5D CB`，`xor ax,ax; pop bp; retf`），不可能是真正的邏輯——推論是這些呼叫的真正目標活在**另一個 overlay 或常駐段**，只是編譯期的字面 segment 值（`CALLF 0100:04A4`，Ghidra 顯示成拉平的 `0000:14A4`）要等執行期做重定位才知道真正指向哪裡。
2. **動態階段**：改用**記憶體寫入斷點（`BPM`）打在 `FUN_0000_5160` 函式一進入就會寫的全域變數上**（而不是像 `re_08` 那樣去猜 overlay 執行期段位址、或去篩 `INT 21h` 開檔/讀檔事件），成功穩定抓到 `FUN_0000_5160` 即時執行，並一路 `F11`（Trace）追出它呼叫鏈的真正終點。

## 2. 新方法：用函式內部一定會執行的全域寫入當斷點（比猜位址/篩檔案 I/O 有效率）

### 2.1 為什麼開檔/讀檔篩選法今天遇到瓶頸

延續 `re_08` 的 `BPINT 21 3D`（開檔）在這次環境裡，一路篩到鬥技場對話出現，**始終沒有看到開啟 `GPLDATA.GFF`**；改用 `BPINT 21 3F`（讀檔）逐一核對 handle/緩衝區內容，篩出的兩個候選 handle 都被排除：

| handle | 讀取內容 | 結論 |
|---|---|---|
| 5 | 714 bytes，內容是可辨識的 x86 函式開頭（`55 8B EC 83 EC 04 ...`） | 這是 overlay 單元的**程式碼**被換入記憶體，不是資料 |
| 10 | 824 bytes，103 筆固定 8-byte 記錄（偏移量+固定 ID+段位址） | 是 overlay manager 自己的**進入點/重定位中繼資料表**，不是對話資料 |

兩者都不是 GPL 資料，說明「檔案開/讀事件」這條線索雜訊太多，逐一篩選效率太低。

### 2.2 改用 `BPM`：抓「一定會發生的副作用」

回頭看 `re_07`/`re_08` 已經拿到的 `FUN_0000_5160` 反編譯結果，它一進函式、任何分支判斷都還沒做之前，第一件事就是：

```c
*(undefined2 *)0x4c3e = param_5;
```

這是一個**固定位址的全域變數寫入**，不像程式碼本身會因為 overlay 換頁而搬家——只要資料段（`DS`）本身固定，這個位址每次都一樣。多次觀察到 `SS`（甚至 `DS`）在不同斷點都是 `4B7A`，判斷這是整個程式共用、不受 overlay 影響的全域資料段。於是下：

```
BPM 4B7A:4C3E
```

**這個方法立刻奏效**：不管 `FUN_0000_5160` 這次被載入到哪個 overlay 段，只要它被呼叫過一次，這個全域變數就會被寫入，斷點就會觸發，觸發當下的 `CS:IP` 就是這次執行期真正的函式位址——完全不需要事先猜測或篩選檔案 I/O。

**這次的結果**：斷點觸發在 `CS:EIP = 5B7C:00000024`，Code Overview 內容與反編譯出的邏輯逐行對上（`cmp dword [bp+08],0000` 對應 `if (param_3 < 1)`、`cmp di,270F` 對應 `if (0x270e < param_2)` 等），確認找到了真正在跑的 `FUN_0000_5160`，這次的入口點在 `5B7C:0000` 附近。

> ⚠️ **這個方法有個已知副作用**（見 §4）：後來發現 `0x4C3E` 其實是一個**更通用的全域**（「目前查詢的資源標籤」），不是 `FUN_0000_5160` 專屬，所以這個斷點也會被其他呼叫同一套通用載入器的地方觸發，不是 100% 精準。但作為「先抓到函式本體、不用猜位址」這第一步，仍然遠比猜位址或篩 I/O 有效率。

## 3. 追出的呼叫鏈：從 `FUN_0000_5160` 到常駐段的通用 GFF 容器載入器

沿著 `5B7C:0024`（`FUN_0000_5160` 內部）一路 `F11` 跳進去，每一步都用 Register Overview 核對 `CS:IP`：

| 位置 | 指令 | 說明 |
|---|---|---|
| `5B7C:0089` | `CALL 2C84:04A4`（**編譯期字面值是 `0100:04A4`，執行期重定位成 `2C84`**） | 對應 `re_07` 反編譯出的 `FUN_0000_14a4` 呼叫——**這就是 `re_08`/`re_09` 開頭一直找不到本體的那個「空殼函式」，真身在 `2C84` 段** |
| `2C84:04A4` | 標準 Borland 堆疊溢位檢查前導碼，接著 `push` 五個參數 | `2C84` 段裡的函式，非 overlay（見 §3.1） |
| `2C84:04C6` | `push cs; call 000007A6`（近呼叫，同段內） | 真正的邏輯入口 |
| `2C84:07A6` | 初始化兩個局部變數為 `FFFFFFFF`，接著 `call 2D2D:012F`（遠呼叫） | 準備呼叫另一個常駐段 |
| `2D2D:012F` | `cmp dword [9DD2],49464647`（= `"GFFI"`）判斷是否為合法 GFF 檔頭，回傳 `AX=1`/`AX=0` | **驗證 GFF magic number 的函式**，對應 `re_02` §1a 記錄的容器格式 |

呼叫鏈：`FUN_0000_5160`（overlay `5B7C`）→ `2C84:04A4` → `2C84:07A6` → `2D2D:012F`。

### 3.1 `2C84` 與 `2D2D` 是常駐段，不受 overlay 換頁影響

證據：`5B7C:0089` 的 `CALL` 指令**在編譯期就寫死了字面 segment 值**（`0100`，執行期重定位成 `2C84`），不是透過 `re_08` §4 記錄的 `int 3Fh` overlay 呼叫樁機制去跳轉——代表 `2C84` 這個目標**不需要 overlay manager 換頁就能直接呼叫**，是常駐段的一部分。這對下一步的靜態分析很重要（見 §6）。

### 3.2 通用 GFF 容器載入/驗證邏輯，`re_02` 的格式假設在更多標籤上得到驗證

在 `2D2D:012F` 驗證 magic number通過後，回到 `2C84:07CB`，`ds:[9DCA]` held 一個 far pointer（本次觀察到的值：`9442:0004`），指向剛載入的 GFF 容器內容。實際 dump 這塊記憶體：

```
9442:0014  47 46 46 49 00 00 03 00 1C 00 00 00 D0 97 01 00
            G  F  F  I  版本=3      entry table 位移=0x1C   資料大小=0x0197D0
9442:0024  78 00 00 00 ...
            entry 數量 = 0x78 = 120
9442:0054  45 54 41 42 01 00 00 00 2A 00 00 00 64 8D 01 00
            "ETAB"      count=1     size=0x2A     offset=0x018D64
9442:0064  38 03 00 00 47 4D 41 50 01 00 00 00 2A 00 00 00
                        "GMAP"      count=1     size=0x2A
9442:0074  64 5C 01 00 00 31 00 00 52 4D 41 50 01 00 00 00
            offset=0x015C64                      "RMAP" ...
```

**這跟 `re_02` §1a/§1c 記錄的 `GPLDATA.GFF` 檔頭與 `"GPL "` 標籤目錄結構逐欄位對上**，但這次 entry 數量是 120（不是 `GPLDATA.GFF` 的 756），而且目錄裡看到的是 `ETAB`/`GMAP`/`RMAP`（地圖/區域資料標籤）——**這次載入的是某個場景/區域用的 GFF 檔，不是 `GPLDATA.GFF`**。

**結論**：`re_02` 原本只針對 `"GPL "` 標籤驗證過的「標籤+數量+位移」目錄結構，這次證實是**整個 GFF 格式家族共用的通用結構**，`2C84`/`2D2D` 這兩個常駐段裡的函式就是處理任意標籤類型的通用載入/驗證/查詢邏輯，不是 GPL 專屬程式碼。

## 4. 一個被推翻的假設：`0x4C3E` 不是 GPL 專屬，是「目前查詢標籤」的通用全域

繼續用同一個 `BPM 4B7A:4C3E` 斷點追第二次觸發，這次落在 `2C84:05DB`（同一個常駐段裡結構相似的另一個函式），核對呼叫參數：

```
2C84:000005F7  push dword [bp+06]    ss:[FD88]=20504D42
```

`20504D42` 拆成 4 個 bytes 讀作 ASCII 是 `42 4D 50 20` = `"BMP "`（點陣圖標籤）。**代表 `0x4C3E` 其實是「這次查詢的是哪個 4 字元資源標籤」的通用全域變數，`GPL `、`BMP `、應該還有其他標籤查詢都會寫到這裡**——不是 `FUN_0000_5160` 專屬。

**這推翻了「這個斷點只會在 GPL 相關呼叫觸發」的隱含假設**，也解釋了為什麼一路追到對話文字都出現在畫面上了，卻始終沒有等到標籤值等於 `"GPL "`（换算成同樣的 dword 顯示應為 `204C5047`）的那一次觸發。

**目前的工作假設**（未驗證）：個別 GPL script 的抓取，很可能**不是透過「用 `"GPL "` 標籤查詢容器」這條路徑**，而是更早（可能在關卡/區域載入時）就已經解析過一次 `"GPL "` 標籤的目錄、把 217 筆 `id/offset/size` 記在別處，之後個別 GPL script 的讀取走的是**直接用已知位移讀取**的更短路徑，不會再經過這個通用的「標籤查詢」函式。這點還沒有實測證實，是下次動態追蹤的優先驗證項目。

## 5. 本次也做了、但結果是負面的兩個靜態測試（記錄下來避免重工）

### 5.1 `re_07` 驗證過的記錄格式，套用到磁碟原始 bytes 上解析失敗

用 Python 直接對 217 個 GPL 區塊的原始 bytes（略過已知的 8-byte 區塊頭）套用 `re_07` 反組譯驗證過的記錄格式（`opcode(1) + 未解析(7) + 長度(2) + 內容`，`0xFF` 終止）：

```
可乾淨解析到 0xFF 結尾的區塊：1~2 / 217
解析失敗（長度欄位指向超出區塊邊界）：215~216 / 217
```

跳過區塊頭再試一次，結果同樣是絕大多數解析失敗（216/217）。**結論**：這個記錄格式是 `FUN_0000_5160` 在記憶體裡消費的資料結構，不等於磁碟上原始 bytes 的樣子——中間必然還有一層尚未解開的轉換（解壓縮/解碼）。

### 5.2 u5-cht 風格的字典 token 壓縮假設，套用後比隨機亂數還差

參考姊妹專案 `u5-cht`（《創世紀 V》中文重製）的做法（118 字常用詞字典，bit7 當「字面字元 vs token」的極性旗標），對全部 217 個區塊測試兩種極性：

```
極性 A（bit7 有設=字面字元）：可印字元比例平均 0.495
極性 B（bit7 沒設=字面字元）：可印字元比例平均 0.531
對照組（完全不解碼的原始 bytes）：0.326
```

乍看比對照組高，但**如果這兩種極性猜對了，隨機亂數在「字面字元」通道本身就該有約 0.74 的可印字元比例**（0x20–0x7E 佔 128 個可能值裡的 95 個）。0.495 和 0.531 都**低於隨機亂數的期望值**，代表這套簡單的 bit7 字典模型在 Dark Sun 這裡不成立，磁碟上的位元組分佈明顯偏向控制字元範圍，更像是尚未解壓縮的原始資料，而不是字典壓縮後的文字。

**兩個負面結果指向同一個結論**：`re_01` §6 早就標記的 `Loadgamefromdisk` 內的 `Uncompress` 呼叫，是目前唯一能讓後續任何文字模型假設變得可測試的前提。

## 6. 給下次接續的具體建議

### 6.1 優先度最高：把常駐段完整匯入 Ghidra 做靜態分析

**這次最大的戰略性發現**：`2C84` 和 `2D2D` 是**常駐段**（不受 overlay 換頁影響，`§3.1` 已證實），這代表它們**不需要再靠動態除錯去猜執行期位址**——直接把 `DSUN.EXE` 常駐段（檔案偏移 `0` 到 `0x52ea0`，`re_07` §1.1 已定義這個範圍）完整匯入 Ghidra，對 `2C84`、`2D2D` 這兩個段（以及它們可能呼叫到的其他常駐段）做完整靜態反編譯，這次不會再遇到「函式是空殼」的問題（`re_08`/`re_09` 開頭遇到的那種），因為目標真的就在這個範圍裡，不會被誤匯入到不相關的 overlay 切片。

### 6.2 驗證 §4 的工作假設

找出 `"GPL "` 標籤的目錄（217 筆 `id/offset/size`）究竟是在哪個時間點、透過哪個函式被解析出來並快取的——合理猜測是關卡/區域載入的早期階段，值得對著開機到進入鬥技場這段重新用 `BPM 4B7A:4C3E` 追一次，這次**不要在對話出現前就放棄**，而是記錄下**每一次**標籤查詢的值（不只是等 `"GPL "`），畫出一次完整的「這個階段到底查詢過哪些標籤、依序是什麼」的時間軸，應該能看到 `"GPL "` 真正被查詢的那一刻，以及查完之後結果被存到哪裡。

### 6.3 除錯器操作備忘（補充 `re_07`/`re_08`）

- **單步是按鍵，不是打字指令**：`F10` = Step Over（跳過）、`F11` = Trace（跳進去）。之前以為要打字輸入 `P`/`T` 是錯的，會得到 `*** Debugger command not recognized`。
- `ALT + X` 可以直接把 Data view 切到 `DS:DX`（讀檔緩衝區位址），比手動讀暫存器再打 `D seg:off` 快很多；同組還有 `ALT+D/E/S/B` 對應 `DS:SI`/`ES:DI`/`SS:SP`/`ES:BX`。
- `BPM [seg]:[off]` 設記憶體寫入斷點；`BPLIST` 列出目前所有斷點；`BPDEL *` 全部刪除——多個暫時性斷點疊在一起很容易造成「明明在追新東西卻撞到舊斷點」的混亂（這次就踩過一次），**每次換追蹤目標前先 `BPLIST` 檢查、`BPDEL *` 清乾淨**。
- 不確定指令語法時，直接 `HELP` 查（這次靠這個查到 `F10`/`F11` 才解決卡住的問題），不要憑印象猜命令列語法。
