# v65：性別搬移到裝備格那一排

日期：2026-09-17

延續 `re_85`。使用者提供排版示意圖，要求把「性別」搬到裝備格那一排（左上角），
「種族」留在原本那一行、「陣營」放最後一行跟種族合併。本版只完成第一步——
搬性別；陣營合併會需要先找到陣營真正的繪製位置，這次會先擱置（見下）。

## 1. 結論

`scratch_test/cjk_display_staging_v65_view_gender_reposition` 已實機驗證：
GERAKIS/K'RATCHEK/CERMAK/CILLA 四位角色的「性別」都正確顯示在裝備格那一排
（(x=149, y=44)），「種族」單獨留在原本 y=86 那一行、起始 X 不再被性別的寬度往右推。
陣營維持原狀，不動。

## 2. 陣營呼叫點重新查證：確認 re_72 的舊記錄是錯的

本次用跟性別/種族一樣的「設中斷點＋單步執行」方式，*即時*（不是靠靜態位元組
推算）重新驗證了 `0x8A1DC`（`re_72` 與 v64 checkpoint 都假設是「陣營」的呼叫點）
實際跳去哪裡：

```text
4A41:002F -> jmp 5FB0:19A8
```

繼續往下追蹤 `5FB0:19A8` 的完整內容後發現，這段程式碼在檢查
「種族==人類 (`es:[bx+0x18]==1`) 且某職業等級 ≥2 (`es:[bx+0x24]≥2`)」，
條件成立時觸發一個彈出訊息（呼叫 `2D55:0432`、`2143:0B36`、`2E10:0618` 等），
跟畫面上的陣營文字完全無關。再往下追蹤，緊接在它後面的同一個共用函式庫裡，
還發現了本專案自己在 v61 做的「AC:」標籤 patch 原始碼（`mov ax,0xFFE9` 等）——
這證實了這整個 overlay（segment index 16，檔案位移 `0x63250`–`0x6527f`）其實是
給*好幾個不同畫面*共用的「畫欄位」工具庫，不是 VIEW CHARACTER 專屬的，
`re_72` 把 `0x8A1DC` 標記成「陣營」是誤判。

另外也在檔案裡找到一個「看起來很像」陣營繪製包裝函式的候選（`0x0643F5`，
會把陣營字串表基底位址 `0xed2` 當參數傳給共用函式），但即時掃描整個 1MB
guest RAM 都沒找到它被載入——不確定它是不是給別的畫面用的，或者還要別的
觸發條件才會載入。真正的陣營繪製位置目前仍未知。

## 3. 技術細節：如何讓性別跟種族分開移動

繪圖函式（`5FB0:1907`，檔案位移 `0x64B57`）內部性別跟種族**各自有自己的
「push di; push si」**（分別在呼叫兩次共用的 `%C%C%C%s` formatter 之前）——
兩者的座標不是共用同一份，只是初始值相同。因此可以只覆蓋性別那一份的
X/Y 為固定常數，不影響種族那一份：

- v64 的性別 tag redirect（22 bytes，到 `push 0x14` 之前）擴大成 46 bytes，
  一路吸收到（但不含）`call 339E:016D` 那個 far call 本身──它的 segment word
  是 overlay relocation 目標，永遠不能覆寫。
- FONT-local `gender_decoded` 因此要自己重新 push 原本那些參數（顏色跳脫碼、
  版面模板 id），只把原本的 `push di; push si` 換成寫死的 `GENDER_Y=44,
  GENDER_X=149`，其餘完全比照原樣。
- 種族原本的 X 是 `si + 性別文字寬度`；把「性別寬度」那個寫死常數從 24
  改成 0，種族就自動變回 `X=si=149`，不用動種族自己的程式碼。
