# 下半部（職業／等級／經驗／HP／PSI／防禦／DAM）呼叫點即時偵查

日期：2026-09-17

延續 `re_87`。使用者確認 v66b 的陣營／性別／種族都正常後，接著要求繼續處理
VIEW CHARACTER 下半部：職業（含多職業）、等級、經驗、HP、PSI、防禦、DAM。
本次是**偵查記錄**，尚未動手 patch 任何東西——範圍比陣營大很多（職業要處理
最多三職並存＋多職缺字寬度、經驗有門檻換算、HP/PSI 要合併兩份不同的角色
紀錄），先把每個欄位真正的繪製位置、資料來源用即時單步執行釘死，下次才能
照抄陣營/性別的模式動手，不用重蹈 `re_86` 誤判陣營呼叫點的覆轍。

沿用同一套技巧：在 GERAKIS／K'RATCHEK 的 VIEW CHARACTER 畫面上，對
`5FB0:1907`（性別／種族繪圖函式）設中斷點，用返回位址反查 VIEW 自己的呼叫
序列所在段（這次仍是 `5EBF`，兩次啟動都一樣），再往後逐段解讀。

## 1. 職業（含多職業）——目前唯一需要「覆寫字串資料」而非單純換位置的欄位

VIEW 自己的呼叫序列裡，職業那一段（Y=106）不是走 `4A41` 那份常駐 jump table，
而是近呼叫 VIEW 自己另一個函式（`5EBF:0A44`），這個函式只是個轉發包裝：

```text
5EBF:0A44: push bp; mov bp,sp
5EBF:0A47: push 0x1200        ; 版面模板 id
5EBF:0A4A: push 0x00FE        ; 顏色
5EBF:0A4D: push [bp+10]       ; Y
5EBF:0A50: push [bp+0E]       ; X
5EBF:0A53: push dword [bp+0A] ; 遠指標＝角色身分紀錄本體（不是字串！）
5EBF:0A57: push dword [bp+06] ; 呼叫端自己的遠指標，原樣轉發
5EBF:0A5B: call 4A96:0084     ; 有 overlay lazy-load（int 3F 觸發載入）
5EBF:0A64: retf
```

`4A96:0084` 第一次呼叫時是「int 3F」overlay 佔位符，觸發 DOS overlay
manager 從磁碟載入真正的程式碼後，跳到 `5B7C:2DC1`——這才是真正的多職業
組字邏輯：

```text
5B7C:2DC9: mov si,[bp+14]        ; si = 0x1200（跟 VIEW 那個「模板 id」同一個數字，
                                 ;   其實是 DS 段內字串指標表的固定位移，不是模板）
5B7C:2DCC: les bx,[bp+0A]        ; bx:es = 角色身分紀錄
5B7C:2DCF: cmp byte es:[bx+21],0 ; 職業欄位1（record+0x21）
           …無則跳過，有則 al=職業ID，呼叫 2F59（量寬 helper）取得寬度→DI
5B7C:2DFC: cmp byte es:[bx+22],0 ; 職業欄位2（record+0x22），同上→[bp-2]
5B7C:2E2C: cmp byte es:[bx+23],0 ; 職業欄位3（record+0x23），同上→DX
5B7C:2E59-2EBE：三職都有時，用 (職業ID-1)*4 當索引，
   從 DS:[0x1200 + 索引*4] 取一個遠指標（指到英文職業名稱字串），
   三個一起連同顏色/寬度組成參數，呼叫 339E:016D
   （！！跟性別/種族/陣營共用的同一個 %C%C%C%s 格式化函式！！）
   版面模板固定是 0x1D62（3 選字串串接版），不是 0x0E11。
```

**欄位位移**：`record+0x21`／`+0x22`／`+0x23` = 最多三個職業 ID（1-indexed，
0＝無此職），緊接在等級陣列（`record+0x24..0x26`，`re_85` 已記錄）之前。
兩者合起來剛好對應存檔格式 `ds_character_t` 裡 `real_class[3]` + `level[3]`
的相鄰配置。

**字串表**：`DS:0x1200` 起是一份「(職業ID-1)*4」索引的遠指標陣列，指向
`DS:0x128D` 起的共用英文字串池，實機讀出的內容（GERAKIS=職業10=Gladiator、
K'RATCHEK=職業9,7,12=Fighter,Druid,Psionic，皆與畫面吻合）：

| 職業 ID 範圍 | 字串 |
|---|---|
| 1–4 | Cleric |
| 5–8 | Druid |
| 9 | Fighter |
| 10 | Gladiator |
| 11 | Preserver |
| 12 | Psionic |
| 13–16 | Ranger |
| （池子最後，未讀 ID） | Thief |

同一個「基礎類別」共用 4 個 ID 這件事，猜測是遊戲原本預留給「同一職業的
不同陣營／出身限制」用的變體欄位，但顯示文字相同；池子後面還接了三個
看起來像除錯殘留、目前沒有任何 ID 指到的字串（` MAGE`／`CLERIC`／
`PSlONlC`，全大寫且有錯字，不用管）。8 個真正會用到的英文職業名稱只有：
Cleric／Druid／Fighter／Gladiator／Preserver／Psionic／Ranger／Thief。

**中文化的可行路徑（尚未實作）**：最終繪圖呼叫是 `339E:016D`——跟性別/種族/
陣營同一個、已經證實吃得下 `0x5E`-tag 的 CJK escape 序列的格式化函式。這表示
理論上**不需要改 5B7C:2DC1 這段組字/量寬邏輯本身**，只要：
1. 把 `DS:0x1200` 那份「(ID-1)×4」指標表，各職業改指到中文 tag 字串（可以是
   FONT-local 新增的職業字表，或直接複用材質/種族那種「先建字串再取指標」
   的做法）；
2. 確認 `call 2F59`（寬度量測 helper）能不能正確量到 CJK tag 字串的寬度——
   這是**唯一還沒驗證、可能卡住的地方**：如果它只認純 ASCII 寬度表，會員
   把中文寬度算錯，導致多職業「／」串接的位置跑掉。下次要先單步進
   `2F59` 確認它的量寬方式，再決定要不要順便把它也接上 CJK tag 的量寬邏輯
   （FONT 那邊應該已經有現成的「量 CJK tag 寬度」helper，見 `re_85`
   「量寬 helper」段落）。

## 2. 等級（Level）—— 走常駐共用庫，跟性別/種族/陣營同等級的簡單欄位

Y=113，VIEW 呼叫 `4A41:0039`，jump table 目標 `5FB0:1A01`（**常駐**，不用
overlay lazy-load，patch 起來應該跟陣營一樣直接）。呼叫前 VIEW 自己算了
71-byte 角色紀錄指標當參數傳入，研判內部會讀 `record+0x24..0x26`（等級陣列）
搭配 `record+0x21..0x23`（職業陣列）決定要印幾個數字、用什麼分隔——這段
內部邏輯還沒單步進去確認，下次要做。

## 3. 經驗值（EXP）—— 目前最複雜，還沒摸清楚

Y=120，VIEW 先呼叫 `4A52:0025`（傳入 58-byte 戰鬥紀錄指標，基底
`[1665]/[1667]`，stride `0x3A`——這是**另一份**跟 71-byte 角色紀錄不同的
陣列，猜測是 `re_85` table 提過的「combat」紀錄），這通常是在準備/計算
「目前經驗（門檻）」的門檻數字；緊接著呼叫 `4A5D:004D`（傳入 71-byte
角色紀錄）做實際繪製，兩個都不在 `4A41` 常駐 jump table 上，還沒確認是否
也是 overlay lazy-load。`re_72` 當年留的疑問「門檻來源／多職業選取邏輯」
這次依然沒解掉，需要下次專門單步進 `4A52:0025` 確認算法。

## 4. HP／PSI —— 標籤是寫死英文字串，數字才是欄位

- HP 標籤（X=149,Y=127）：直接呼叫 `339E:016D`，字串指標是寫死的
  `DS:0x3363`（沒有查任何角色欄位，等於是一段固定的 `"HP:"` 靜態字串)。
- HP 數字（X=189,Y=127）：呼叫 `4A41:003E` → `5FB0:1A1B`（**常駐**），同時
  傳入 71-byte 角色紀錄跟 58-byte 戰鬥紀錄兩個指標——研判要把「目前/上限」
  兩個數字都印出來（畫面顯示「54/54」這種格式）需要兩份資料源。
- PSI 標籤（X=149,Y=134）：`339E:016D`，寫死字串 `DS:0x336D`（`"PSI:"`）。
- PSI 數字（X=189,Y=134）：`4A41:0043` → `5FB0:1A9D`（**常駐**），同上兩份
  紀錄指標。

固定的 `"HP:"`／`"PSI:"` 標籤字串（`DS:0x3363`／`0x336D`）翻譯起來應該最
簡單——只要在 GFF／EXE 對應位置換成中文 tag 字串就好，機制上比職業簡單
很多，可以優先做。

## 5. 防禦（AC）／傷害（DAM）

Y=141。看到兩個常駐 jump table 呼叫：`4A41:0048`→`5FB0:1B20`（AC，
先呼叫另一個 `49E2:007F` 準備數字，再進 1B20 繪製）、`4A41:004D`→
`5FB0:1B69`（DAM）。`X=199` 那組 push（`008D00C7`）對應到 DAM 位置，跟
`re_72` 舊表「AC/DAM (149,141)/(199,141)」的座標一致。這兩個目前看起來
機制單純（跟 HP/PSI 數字類似），還沒單步進去確認細節。

## 6. 優先順序建議（尚未跟使用者確認）

複雜度／風險由低到高：
1. **HP:／PSI: 固定標籤翻譯**——不涉及任何欄位查表，最安全，先做。
2. **等級／AC／DAM**——常駐共用庫、單一數字，機制應該跟陣營差不多，其次做。
3. **職業（含多職業）**——需要先驗證 CJK 寬度量測相容性，中風險。
4. **經驗值**——牽涉獨立的 58-byte 戰鬥紀錄與門檻換算，還沒摸清楚算法，
   建議放最後，且要先花一次會期單獨追蹤 `4A52:0025`。

## 6.5 追加發現：VIEW 自己的包裝程式碼不像 `5FB0` 那樣穩定常駐

原本想先做「HP:/PSI: 固定標籤」這個看似最簡單的項目，實作到一半（asm 端
新增 `view_hp_label_entry`／`view_psi_label_entry`，機制完全比照 `re_83`
已經驗證過的 `psi_label_entry`）時，在 EXE 端要找對應的 patch 位置卡住：

- 靜態在檔案裡搜尋 `"%C%C%CHP:\0"`／`"%C%C%CPSI:\0"` 這兩段字串本身
  （純資料，位於常駐 `DS` 段）沒問題，各自唯一命中一次
  （`0x8A2A0` 附近讀到字串內容、confirm 跟畫面一致）。
- 但**推這兩個字串位址的那幾行組合語言**（`push ds; push 0x3363` 等）
  所在的程式碼，是 VIEW 自己的一個 overlay 單元（用 `vendor/opends/tools/
  ovr-map/ovr-map.py` 查表確認：這段落在 `file_start=0x89E70,
  file_end=0x8AD73` 的 overlay #0x30，本身有 8 個內部進入點，其中一個
  entry_offset 剛好對應到本次職業繪圖包裝函式 `0x0A44`）。這個 overlay
  單元**不是每次都載入在同一個執行期 segment**：同一次 DOSBox-X
  session 裡，前一刻在 `5EBF` 對到的 `push ds; push 0x3363`，換一次角色
  重繪之後，同樣的（透過 `5FB0:1907` 斷點回推得到的）呼叫端 segment
  再讀，`0x442` 那個位置的內容就完全變了、對不上；在同一數字 segment
  底下設中斷點也不會再命中。研判是 Borland overlay manager 把好幾個
  不同的邏輯單元輪流換進同一段記憶體視窗，光靠「這次跑起來剛好在
  `5EBF:xxxx`」記錄下來的位址，換一次角色、換一次畫面就可能失效。
- 順手核對「常駐、應該最安全」的等級／HP數字／PSI數字／AC／DAM
  （`5FB0:1A01`／`1A1B`／`1A9D`／`1B20`／`1B69`，本文件第2、4、5節記錄的
  jump table 目標）時，反組譯 `5FB0:1A01` 起段，內容看起來也不像「印出
  等級數字」，反而像另一段迴圈邏輯，還呼叫了 `4A96:00DE`——`4A96` 正是
  職業名稱那段會觸發 `int 3F` 換頁的 overlay trampoline 段！這代表
  `5FB0` 這個大範圍不是整段都跟性別/種族/陣營那三個已驗證過的位址
  （`1907`／`19A8`）一樣「永遠常駐、位元組不變」，`1A01` 之後這一截可能
  也牽涉到 overlay 換頁，不能直接比照抄。

**結論**：性別／種族／陣營能穩定 patch，是因為它們剛好落在整個 EXE 裡
少數「反覆驗證過確實常駐不換頁」的窄範圍（`5FB0:1907`~`19E6`）內；再往
下（等級開始）跟 VIEW 自己的包裝函式，都不能只憑一次 session 的即時
反組譯／中斷點記錄的位址就直接拿來寫 patch，必須先比照
`verify_overlay_relocations` 已經在用的 `ovr-map.py` 表格，逐一確認
「這個 file offset 屬於哪個 overlay 單元、這個單元的內容是否真的不會
再變」，才能確保 patch 位置正確、不會因為換頁而失效或錯改到別的邏輯。
這比原先估計的複雜，本次會期先不動手，留給下一輪。

## 6.6 追加調查：等級／HP數字／PSI數字／防禦數字其實不需要翻譯

`re_89`（v67）解決 overlay 定位問題後，回頭查等級／HP／PSI／防禦／DAM：

- **等級**（`5FB0:1A01`）：只是個轉發包裝（跟職業的 `5EBF:0A44` 同一種
  形狀），近呼叫同一個 5FB0 segment 內的 `0x11C7`，還沒細看，但顯示的
  是純數字（GERAKIS 顯示「3」），**沒有需要翻譯的文字**。
- **HP 數字**（`5FB0:1A1B`）／**PSI 數字**（`5FB0:1A9D`）：讀取
  71-byte 角色紀錄（`+0x08`＝上限）與另一份 58-byte 戰鬥紀錄
  （`+0x00`＝目前值），呼叫兩個近程式碼片段（可能是數字轉字串／依血量
  百分比選顏色），最後一樣送進 `339E:016D` 畫出來。**只有阿拉伯數字跟
  `/`，沒有文字**，不需要動。
- **防禦數字**：同理，是純數字。`AC:` 標籤已經因為 `re_83` 的 sprintf
  共用格式字串而自動變成中文（`re_89` 已確認）。

也就是說，優先順序清單裡「等級／防禦／DAM」這一項，扣掉「數字本身不用
翻」之後，真正剩下要處理的只有 **DAM: 這個標籤本身**。

## 6.7 DAM:／EXP: 標籤：已定位字串，消費端還沒抓穩

靜態在檔案裡找到（僅各一次）：`"DAM: \0"`（file `0x497C8`，緊接在
`re_83` 記錄的 `"AC: %2d\0"` 格式字串後面 8 bytes）、`"EXP: \0"`（file
`0x49A4B`）。用同一套「找 `push ds;push <DS位移>`」的方法，找到疑似
DAM: 的消費端在 file `0x64DD8`，前面是一段配置 **378 bytes 堆疊緩衝區**
（`sub sp,0x37E`）、呼叫一個 far call（segment word `0x0348`，可能也是
relocation 佔位符）把角色索引格式化進緩衝區，然後 `push ds;push DAM:`
接另一個 far call（**segment word 是 `0000`**，幾乎可以確定也是
relocation 佔位符）——看起來是在**組合傷害字串**（`"DAM: "` + 倍率 +
骰子 + 加值，例如畫面上的 `"1.5x1D6+12"`），不是單純的「push 字串就送
繪圓」，比 HP:/PSI: 複雜。

**卡住的地方**：想用「`file_offset - 0x64B57 + 0x1907`」這條（`re_85`
記錄、且對性別/種族/陣營三個位址都驗證過的）公式換算成實機 segment:offset
下中斷點，換算出來的位址反組譯結果**兜不起來**（換算給的位址其實落在
另一個看起來完全無關、正在跑迴圈的函式中間）。還沒查出是公式本身对
`0x64DD8` 這一段不適用（可能这段路径也牽涉 overlay，只是還沒用
`ovr-map.py` 查表確認)，還是單純哪裡算錯。**這次沒有再往下猜，留給
下一輪先查表確認再動手**，避免重蹈之前的覆轍。

`EXP: ` 的消費端這次完全沒找到（同一招「找 push ds;push 偏移」搜尋
沒有命中），可能是用暫存器組出位址、或是也在某個 overlay 裡用不同手法
參照，需要換一種找法（例如即時中斷點＋反查呼叫端，而非純靜態位元組
搜尋）。
