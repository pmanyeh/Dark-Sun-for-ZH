# 動態除錯成果：overlay manager 呼叫機制實測、真實載入位址對回檔案位移

> **日期**：2026-08-10（延續 `re_07` 第 3 節建議的高風險支線，這次真的在 DOSBox-X 除錯器裡人在場手動操作完成）
> **前提文件**：`re_07_verified_gpl_loop_and_dosbox_setup.md`（環境設定、指令備忘、已驗證的 GPL 迴圈結構）

---

## 1. 這次做了什麼

用 `re_07` 記錄的 DOSBox-X 環境（`darksun.conf`），在除錯器裡：

1. 用 `BPINT 21 3D` 中斷所有 DOS 開檔呼叫，逐一用 `D DS:DX` 檢查檔名，篩選出遊戲開啟 `C:\GPLDATA.GFF` 的那一次中斷。
2. 從斷點當下的暫存器狀態出發，沿著 `BP` 鏈（每層 `[BP+0]`=上層舊 BP、`[BP+2..]`=遠呼叫返回位址）**手動往上爬呼叫堆疊 5 層**，逐層用 `C <seg>:<off>` 反組譯確認每一次遠呼叫（`call far`）的呼叫端與被呼叫端都對得上。
3. 途中直接撞見並確認了 **Borland/Turbo overlay manager 的呼叫樁（`int 3Fh` stub）與動態填值的遠跳分派表**，這正是 `re_07` 第 3 節第 1、2 點想找的東西。
4. 把其中一個已載入 overlay（執行期段位址 `5B7C`）的記憶體內容，直接拿去跟本機的 `DSUN.EXE` 檔案做位元組比對，**反推出它在檔案裡的絕對位移**。

**重要提醒**：以下所有段位址（`3860`、`2C84`、`5B7C`、`4A35`、`62F1`、`4A2B`、`1D36`……）都是**這一次執行期**的動態分配結果。DOSBox 本身是決定性模擬（沒有 ASLR），所以理論上**只要重複同一套啟動流程與操作順序，應該會拿到一樣的段位址**；但不保證每次重啟都完全相同（取決於是否有輸入時機差異等）。下次要重現時，建議整段流程從頭照做一次並重新驗證，不要直接假設這些段位址還有效。

## 2. 開檔當下的斷點狀態（已驗證）

在 `BPINT 21 3D` 中斷、`D DS:DX` 確認檔名為 `C:\GPLDATA.GFF` 之後，斷點狀態：

```
EAX = 00003D02        ; AH=3D(開檔), AL=02(讀寫模式開啟)
CS:IP = 3860:00D9      ; int 21 指令本身，尚未執行
DS = ES = SS = 4B7A
EDX = 0000FD78         ; DX = 檔名字串的 offset
EBP = 0000FD2C
ESP = 0000FD26
```

`4B7A:0000FD78` 開始的記憶體：`43 3A 5C 47 50 4C 44 41 54 41 2E 47 46 46 00`
= `C:\GPLDATA.GFF`（null 結尾），確認無誤。

`3860:00D9` 附近的程式碼是一個**通用的 DOS 開檔包裝函式**（呼叫 `int 21`，用 `jnc` 判斷成功/失敗，失敗就把 `AX`（錯誤碼）存進全域變數 `DS:[3CD8]`）——不是 GPL 專屬邏輯，任何檔案開啟都會經過這裡。

## 3. 往上追出的呼叫鏈（逐層驗證，每一層都反組譯確認過呼叫指令本身）

用 `[BP+0]`=舊 BP、`[BP+2..+3]`=返回 offset、`[BP+4..+5]`=返回 segment（全部是 **far call**，4 bytes 返回位址）逐層往上爬：

| 層 | 函式所在段:偏移 | 這層 BP | 呼叫下一層的指令 | 返回位址（呼叫者） |
|---|---|---|---|---|
| 1 | `3860:00D9`（int21 開檔包裝） | `FD2C` | 被 `2C84:008D` 的 `call 3860:0090` 呼叫 | → `2C84:0092` |
| 2 | `2C84:0064`（通用 `_open(filename, mode)`） | `FD64` | `2C84:008D  call 3860:0090` | → `5B7C:006F` |
| 3 | `5B7C:0040`附近（組完整路徑字串 + 呼叫開檔） | `FDCA` | `5B7C:006A  call 2C84:0064` | → `62F1:0248` |
| 4 | `62F1`（呼叫 overlay 樁進入 5B7C） | `FECC` | `62F1:0243  call 4A35:0025`（**overlay 呼叫樁**，見第4節） | → `1D36:0181` |
| 5 | `1D36:0001` 起（以 ID 索引的資源載入函式，驗證參數 `cmp word [bp+06],0001`） | `FFE0` | `1D36:017C  call 4A2B:0020`（**另一個 overlay 呼叫樁**） | 尚未繼續往上追 |

第 5 層 `1D36:000D` 有 `cmp word [bp+06],0001` / `jge` 這種參數合法性檢查，型態明顯是「**通用的、用數字 ID 索引的資源載入函式**」（例如 `LoadResourceById(id, ...)`），不是 GPL 專屬程式碼——`GPLDATA.GFF` 這個檔名字串本身，在整條追蹤路徑上**沒有以字面常數的形式出現過**（`62F1` 裡一度懷疑的 `11BE:0904` 遠指標，實際 dump 出來是全 0 的緩衝區，不是字串來源）。合理推測：這個 ID 本身（透過某個固定常數傳入 `1D36`）才是「這是 GPL 資料」的真正代表，檔名字串應該是在 `1D36` 更內部、或更上層，用這個 ID 查表組出來的。

## 4. 確認到的 Overlay Manager 機制（`re_07` 第 3 節要找的東西）

### 4.1 `int 3Fh` 呼叫樁（overlay manager call stub）

`4A35:0000` 反組譯：
```
4A35:0000  CD 3F     int  3Fh          ← Borland/Turbo overlay manager 呼叫樁
4A35:0002  ...       （後面接的不是程式碼，是資料——int 3Fh 處理常式會自己去讀
                        返回位址後面的資料字組，取得「要載入哪個 overlay 單元」
                        等資訊，再自行調整返回位址跳過這段資料）
```
這證實了 `re_07` 提到「常駐段內有 994 個 `CD 3F` 呼叫樁」的猜測，而且是**實際觀察到執行中的一個**。

### 4.2 動態填值的遠跳分派表（overlay dispatch table）

`4A35:0025` 開始，一連串固定 5 bytes 一筆（`EA` = far jmp，opcode + 2 bytes offset + 2 bytes segment）：

```
4A35:0025   jmp  5B7C:002D
4A35:002A   jmp  5B7C:0084
4A35:002F   jmp  5B7C:00AB
4A35:0034   jmp  5B7C:00DD
4A35:0039   jmp  5B7C:010F
4A35:003E   jmp  5B7C:0152
4A35:0043   jmp  5B7C:01C8
4A35:0048   jmp  5B7C:0206
4A35:004D   jmp  5B7C:021C
4A35:0052   jmp  5B7C:0268
4A35:0057   jmp  5B7C:030E
```

`re_07` 說這張表「磁碟上全 0、要執行期才會動態填值」——**這裡就是它被填值後的實際樣子**：11 個入口，全部指向同一個已載入 overlay（`5B7C`）裡的不同函式進入點。`62F1:0243` 呼叫的 `4A35:0025` 正好是第一筆，跳進 `5B7C:002D`；而我們前面看到的 `5B7C:0040`（`5B7C:006A call 2C84:0064` 那個函式）緊接在 `5B7C:002D` 那個進入點附近，是同一個 overlay 裡的另一個匯出函式。

另外還發現 `4A2B` 是另一個結構相同的 overlay 呼叫樁段（`1D36:017C call 4A2B:0020`），指向的應該是 `62F1` 這個 overlay——同一套機制，不同的呼叫端/overlay 單元。

### 4.3 已載入 overlay 對回檔案位移（實際位元組比對，不是猜的）

把 `5B7C:0000` 開始的 128 bytes 記憶體：
```
55 8B EC 81 EC 00 01 56 33 F6 C4 5E 06 03 DE 26
8A 07 88 82 00 FF 81 FE FF 00 7D 0E 8B C6 46 8B ...
```
拿去 `DSUN.EXE`（611408 bytes）裡逐位元組搜尋，**在整個檔案裡只找到唯一一個完全吻合的位置**：

```
檔案位移 0x62030  ↔  執行期 5B7C:0000（linear 0x05B7C0）
```

這正好落在 `re_07` 認定的 overlay 池範圍內（`0x52ea0` 之後），互相印證。由此可算出**這次執行、這個 overlay 的載入位移**：
```
delta = 檔案位移 - 執行期線性位址 = 0x62030 - 0x05B7C0 = 0x6870
```
（這個 `delta` 只對「這次執行、這個 overlay」有效，不是全域常數——不同 overlay 單元、不同次啟動，都可能載入到不同記憶體位置。）

## 5. 給下次接續的具體線索

### 5.1 一個值得優先驗證的假設位址

`re_07` 已驗證 `FUN_0000_5160`（GPL 記錄執行迴圈）的**檔案絕對位移約 `0x68000`**。用上面這次算出的 `delta = 0x6870` 反推：
```
預測執行期線性位址 = 0x68000 - 0x6870 = 0x61790
相對於這次 5B7C 的段基底（0x05B7C0）= 0x61790 - 0x05B7C0 = 0x5FD0
→ 假設位址：5B7C:5FD0
```
**這只是一個未驗證的假設**（成立條件是 `FUN_0000_5160` 跟這次追到的 `5B7C` overlay 屬於同一個 overlay 載入單元，且單元大小涵蓋得到 `0x5FD0` 這個偏移）。下次重啟同一套環境、走到同一個斷點時，**第一件事可以先檢查 `5B7C:5FD0`（或重新算出的等效位址）的內容，看反組譯出來像不像 `FUN_0000_5160` 的開頭**，如果吻合就直接省掉後面一大段摸索。

### 5.2 為什麼往上爬呼叫堆疊追不到 `CS:0x38F` 分派表

這次沿著「開檔」呼叫鏈往上追 5 層（`3860→2C84→5B7C→4A35(樁)→62F1→4A2B(樁)→1D36`），追出來的是一套**通用、以數字 ID 索引的資源載入子系統**，不是 GPL 專屬程式碼。`re_07` 要找的 `CS:0x38F` opcode 分派表，在 `FUN_0000_5160` 這個 GPL 記錄執行迴圈**內部**，那是**檔案被開啟、內容被讀進記憶體之後，遊戲真正開始解讀 GPL 位元組碼時**才會執行到的程式碼——時間點在「開檔」之後，邏輯上也不是「開檔」呼叫鏈的一部分。**繼續往上爬這條呼叫堆疊不會追到它**，下次要嘛：
  * 直接驗證 5.1 的假設位址；或
  * 放行這次的開檔斷點（`F5`），改成觀察後續的 `int 21h AH=3F`（讀檔）或其他 overlay 載入事件，抓 `FUN_0000_5160` 真正開始執行的那一刻。

### 5.3 這次用到的除錯器指令備忘（補充 `re_07`）

* `C [seg]:[off]` — 設定 Code Overview 顯示的位址（**不是 `U`**，`re_07` 舊版指令備忘裡沒寫到，這次現場用 `HELP` 查到的）。
* `D [seg]:[off]` — 設定 Data Overview 顯示的位址（`re_07` 已記錄）。
* 呼叫堆疊人工回溯法：確認函式開場是標準的 `push bp`(`55`) / `mov bp,sp`(`8BEC`) 或 `enter` (`C8 xx xx 00`) 之後，`[BP+0]`=舊 BP，`[BP+2..+5]`=遠呼叫返回位址（`[BP+2..+3]`=offset，`[BP+4..+5]`=segment），再往後才是參數。近呼叫（near call）返回位址只佔 2 bytes，要先看清楚是哪種呼叫方式再解讀，本次全程遇到的都是遠呼叫。
