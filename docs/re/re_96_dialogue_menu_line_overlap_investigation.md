# 對話選項選單行距重疊問題：調查進度 checkpoint

> 日期：2026-09-18
> 狀態：問題尚未解決，本文件記錄已排除的假設、已確認的技術事實，
> 以及建議的下一步切入點，供下一輪調查直接接續，不用從頭重查。

## 1. 背景

`re_42`／`re_46` 記錄的「多選項共用同一個 `gpl menu`（`0x48`）指令位址」
匯入限制，已在 `tools/compile_gpl_dialogue_patch.py` 於
`f831429`（2026-09-10，"complete GPL6" 批次提交）解決：
`relocate_json_strings` 現在支援同一個位址接受多筆編輯，並以文字內容
比對匹配每個選項到正確的 catalog 單元。`tests/test_gpl_dialogue_importer.py`
的 `test_menu_accepts_multiple_option_text_edits_at_the_same_offset` 等
測試已驗證這個機制。

本輪（2026-09-18）依此重新編譯 GPL-2/3/4/5/6/9/162/195（`gpl_arc_menu_options_v1`
系列，最終產物 `step2-plus-name1/gpl-dialogue-patch.json`，355 個
翻譯單元），建出候選版 `scratch_test/cjk_display_staging_v76_arc_menu_options`。
實機驗證：GPL-4@0x03BC 這個六選一選單（"WHAT DO YOU SAY?"）的選項文字
已正確顯示中文，NPC 本文與此前一致正常。**但選項清單五行文字彼此
重疊，看不清楚**——這是翻譯內容補齊後第一次真正點亮這個畫面才暴露
出來的全新問題，跟本次翻譯內容本身無關。

編譯時排除了兩處既有的、GPL menu entry 結構與匯入器假設不符的選項
（詳見 `quarantined_menu_offsets_v4.json`）：

- GPL-5 offset `0x05BF`（1471）：`entry 0` 不是預期的單一 compressed
  string 表達式。
- GPL-6 offset `0x0260`（608）：`entry 9` 同樣的問題——這正是 `re_46`
  記錄過的「GPL-6@0x0260：9 個選項」那個選單。

這是**匯入器層級**的既有限制（結構驗證拒絕不符合假設的 entry），
跟本文件討論的「行距重疊」是兩個不同層級的問題，不要混為一談。

## 2. 已排除的假設

1. **不是 `--ebox-line-gap` 參數沒有生效**。v76 build 用了 `--ebox-line-gap 2`
   （與 v75 一致），本文（NPC 說話）該有的行距在 v76 上仍然正常。
2. **不是 `EBOX_LAYOUT_ADVANCE`／`EBOX_ADVANCE_HELPER`**
   （`tools/patch_dsun_scratch_cache.py`）。反查這兩個常數的實作
   （`ebox_layout_advance_call()`／`ebox_layout_locals_and_helper()`）
   後確認：這組只管「每個字元往右（X 方向）前進多少」，即
   `ebox_cjk_width_body()` 最後回傳的 `CJK advance = 10`，跟行距（Y 方向）
   完全無關。
3. **`EBOX_NEXT_PAGE_DELTA_FILE_OFFSETS`（兩個 `0x7CDBC`／`0x7DBC5`）
   不是「本文 vs 選單」各一份**。靜態比對 patched EXE 這兩處附近的
   bytes，幾乎是同一段程式碼的兩份複製（只有區域變數位移 `fc`/`fa`、
   `f8`/`f6` 不同），比較像是「上一頁／下一頁」兩個方向各一份，
   不是「兩種畫面」各一份。
4. **選單清單 Y 座標不是查 `EBOX_STORE_LINE_HEIGHT` patch 過的那張
   line table**（見下一節的實機證據）。這是本輪最重要的新發現。

## 3. 已確認的技術事實（實機動態除錯）

### 3.1 DOSBox-X-AI bridge 的一個新踩雷點：stdout 導管會讓 `pause_execution` 讓整個行程當機

透過 Bash 工具的 `run_in_background` 啟動 `dosbox-x.exe` 時，其
stdout/stderr 會被導向一個 log 檔案（工具本身的行為）。這正好符合
`DOSBox-X-AI/AGENT_GUIDE.zh-TW.md` 第 4 節明確記載的已知限制：
**如果 `dosbox-x.exe` 自己的 std handle 在啟動時被重新導向／接管，
第一次呼叫需要「除錯器真正停止」的方法（`pause_execution`、
`read_memory`、`set_breakpoint` 等）時，主控台初始化會讓整個行程
連帶 AI 橋接層一起當機**。`capture_frame`／`key_tap`／滑鼠輸入等
「不需要停止狀態」的方法完全不受影響（這也是為什麼前面測試都正常，
直到第一次需要 `pause_execution` 才炸開）。

**解法**：改用 PowerShell 的 `Start-Process` 啟動 `dosbox-x.exe`
（不透過會攔截 stdout 的殼層/背景工具），行程才能正常繼承一個真正
的 Win32 console，`pause_execution` 之後才不會讓行程當掉。以後在這個
專案裡凡是需要用到「除錯器停止」類方法（斷點、讀記憶體、單步）的
session，一律要用這種方式啟動 DOSBox-X，不要用會導管 stdout 的
背景執行方式。

### 3.2 選單的「分頁」操作方式

使用者提醒選項清單本身也有分頁功能。實測確認：**方向鍵上／下
（`up`／`down`）會安全地翻選單的頁**（畫面右下角的三角箭頭方向會
跟著變，選項內容也會換一批），**不會推進對話、不會離開目前的
選單畫面**。這是後續要反覆觸發選單重繪時，唯一已知、安全、可重複
使用的操作——不會像「選一個選項」那樣把當下的測試情境直接摧毀。

`space` 鍵對這個選單畫面沒有效果。

### 3.3 EBOX 繪製 segment 定位：`36AA`

用 `read_memory`／`disassemble` 直接驗證 `36AA:0000` 起是有效、
看起來合理的 16-bit 程式碼，且 `36AA:0AC1` 附近確實是 EBOX 逐一走訪
「子物件」並呼叫底層繪圖函式的迴圈（呼叫 `11A4:xxxx` 這幾個
graphics segment 函式）——`11A4` 這個 graphics segment 編號，剛好與
`re_76`（Hires POC / route B 那邊的獨立觀察）記錄的
`graphics=11A4` 完全吻合，證實 route A／route B 這兩條獨立開發線，
在「原生、雙方都沒有各自修改過」的引擎函式上，執行期 segment
是一致、可重現的。

`36AA` **不是** `patch_dsun_scratch_cache.py` 裡 `EBOX_OVERLAY_BASE`
（檔案位移 `0x31390`）對應的那個 segment——直接讀取
`36AA:01CD`（`EBOX_STORE_LINE_HEIGHT` 的 overlay 內相對位移）跟已知
patch bytes（`41 41 6B C2 04 03 D8 26 89 4F 04`，已用
`ebox_store_line_height(2)` 算式驗證跟 patched EXE 檔案裡的實際
bytes 完全吻合）完全對不上。也就是說：`36AA` 這個活躍的 EBOX segment，
跟 `patch_dsun_scratch_cache.py` 這組 patch 鎖定的那個 overlay，是
**兩個不同的模組**——`36AA` 目前看到的是「EBOX 物件管理／繪製呼叫」
這一層，`EBOX_OVERLAY_BASE` 那組 patch 針對的可能是更底層、被
`36AA` 這層呼叫的另一個模組（尚未定位其執行期 segment）。

### 3.4 對話框外框 bounds table：`DS:[0xA2E8]`，只有一筆記錄

`36AA:0A6B` 起的迴圈，以 `SI` 為索引走訪一個陣列，每筆記錄 8 bytes
（`SI << 3`），位於 `DS:[0xA2E8 + SI*8]`（`DS` 在對話狀態下觀察到的
值是 `4B7A`），格式看起來是 `(x1, y1, x2, y2)` 四個 word。實機讀取
（v76、GPL-4@0x03BC 選單畫面顯示中）這張表的前 10 筆記錄，
**只有第一筆有非零值**：`(x1=0, y1=140, x2=318, y2=198)`——這正是
整個下半部對話框（320×200 座標系）的外框，其餘全是 0。

**這證明**：`SI` 迴圈走訪的是「這個 EBOX 有幾個子物件（目前只有 1
個，整個對話框本身）」，不是「這個對話框裡有幾行文字」。選項清單
每一行實際的 Y 座標，因此**不會**記錄在這張表裡，必須在更內層
（`36AA:0AF6` 呼叫的 `36AA:0BE0`，或者更早、呼叫 `GuiDrawEBox`
之前的地方）才會出現。

### 3.5 `36AA:0BE0` 這個函式：命中測試／裁剪，不是逐行輸出

反組譯 `36AA:0BE0` 起約 100 條指令，內容是一連串 min/max／矩形
交集運算（`cmp`／`jl`／`jg`／`jge` 交替，配合 `[A137]`／`[A139]`
這對座標和一個呼叫 `30F5:0DE0`——`30F5` 正是 `re_76` 記錄的
`cursor/GUI` segment），看起來是「游標／選取範圍與某個矩形的裁剪
判斷」，**不是**逐行印出文字內容的迴圈。真正決定每一行 Y 座標
的程式碼還沒找到。

### 3.6 execution trace 功能有效，但「guest 跑得比按鍵→暫停的網路延遲快很多」讓它抓不到重繪瞬間

`configure_execution_trace`（`before_instructions=4096`，
`max_trace_bytes` 開到 4194304）在 `pause_execution` 時能可靠拿到
剛好結束前的完整指令序列（含反組譯、CS/IP）——這是很好用的工具，
但兩次嘗試（`down`／`up` 鍵各一次，鍵按下後立即 `pause_execution`，
中間完全沒有主動 `sleep`）抓到的 4096 條指令，**全部**只是已知的
待機迴圈（`37E6`／`2D55`／`3419` 三個 segment 循環），完全沒有出現
新的、跟重繪相關的 segment。**推論**：畫面上翻頁效果的變化，
很可能不是「按鍵當下同步觸發」，而是配合遊戲固定的計時器／tick
週期才被主迴圈檢查並處理——這個週期對應的指令數遠遠超過
`max_trace_bytes`（4194304 bytes）能保留的量，導致「按鍵→重繪」
這段窗口早在我方發出 `pause_execution` 之前就已經被沖出 trace
緩衝區。要用 execution trace 精準捕捉這個時刻，必須先有一個已知的
程式碼位址可以直接設中斷點（見下一節建議）。

### 3.7 `36AA:07AB` 附近不是 `GuiEBoxSetText` 的函式入口

依 3.6 節建議反組譯 `36AA:07AB`（`re_76` 記錄的 route B `GuiEBoxSetText`
位址）附近，發現這裡落在一個函式**中段**（`0x0740` 起才是合理的函式
內容起點，`0x07AB` 本身是內層迴圈中段），內容是「以 `si`／`di` 兩層
迴圈走訪一個字元格網格（character cell grid），逐格跟 clip 範圍比較、
決定要不要跳過」——這看起來是**部分重繪／裁剪優化**邏輯（很可能是
「只重繪被捲動/更新影響到的格子」這類最佳化），一樣不是「逐行印出
文字內容、決定每行 Y 座標」的核心排版邏輯。這代表：`re_76`
記錄的「`GuiEBoxSetText` 在 `36AA:07AB`」這個位址，**在 route A 這個
build 上不能直接沿用**（可能兩邊的 patch 造成的程式碼位移不同，
即使 `36AA` 這個 segment 編號本身一致）；不能只套用 route B 的位址，
需要在 route A 自己重新確認函式邊界（例如先反組譯附近找到真正的
`push bp; mov bp,sp` 函式起點，而不是直接假設某個 route B 記錄的
offset 直接適用）。

## 4. 建議的下一步（2026-09-18 上半段訂定）

1. **不要再用 execution trace 盲猜時機**——這條路已經證明在目前的
   guest／bridge 速度差距下不可行，除非先有一個已知位址可以設
   `set_breakpoint`。
2. **往上追呼叫來源，而不是往下追 `GuiDrawEBox` 內部**。既然
   `GuiDrawEBox`（`36AA:0A6B` 起）只是「畫出已經算好的東西」，
   真正的 Y 座標計算應該在**呼叫它之前**。但 3.7 節已證明：**不能
   直接沿用 `re_76`（route B）記錄的 `GuiEBoxSetText` 位址
   `36AA:07AB`**——那是不同 build、程式碼位移不同，套過來落在一個
   無關的裁剪/命中測試函式中段。正確做法：
   - 先在 route A 這個 build 裡，從 `36AA:0A6B`（已確認是
     `GuiDrawEBox` 的一部分）往回找它自己的函式邊界（`push bp;
     mov bp,sp` 起點），再往回找呼叫 `GuiDrawEBox` 的地方，一路
     反查誰在呼叫它，而不是假設 route B 的絕對位址適用。
   - 找到真正的 `GuiEBoxSetText`（或等價的「設定/更新文字內容」
     入口）後，對它設中斷點，用 `up`／`down` 鍵（3.2 節的安全翻頁
     操作）觸發重繪，這次斷點是「已知位址」，不會被跑太快的問題
     卡住。
   - 從那裡往下用 `step_over`（不要 `step_into`，避免深入不相關的
     子函式）追蹤，找出「每一行文字」被寫入某個 table 或直接算出
     Y 座標的地方。
3. **另一條可能更直接的路**：找 GPL 直譯器處理 `0x48`
   （`gpl menu`）opcode 的原生 dispatch handler。如果選單的排版
   （不只是 Y 座標，可能連「一頁放幾行」的分頁判斷）根本是在 GPL
   直譯器層級決定、再把結果整批交給 EBOX 畫，那麼修法可能要動
   GPL 直譯器，而不是 `patch_dsun_scratch_cache.py` 那組 EBOX patch。
   目前完全沒有這個 dispatch table 的位址線索，需要從頭找。
4. **啟動方式**：這輪之後的任何動態除錯 session，記得用
   `Start-Process`（PowerShell）啟動 `dosbox-x.exe`，不要用會導管
   stdout 的方式（見 3.1 節），否則第一次 `pause_execution` 就會
   把整個行程弄掛。

**以上四點已在本文件第 6 節接續執行過一輪，但第 6 節的結論後來被
第 7 節推翻（抓錯了目標，追到的其實是圖示列 tooltip，不是對話
選單）——下一輪請直接讀第 7 節（尤其 7.3 節的具體建議做法），
不要重新從第 4 節這四點原點開始，也不要直接沿用第 6 節「已確認
對話情境」的結論。**

## 6. 2026-09-18（下半段）接續調查：找到疑似根因機制

延續第 4 節第 2 點的方向，本節記錄從 `GuiDrawEBox` 往上追呼叫鏈，
一路追到「畫一個字元」這個最底層函式，並在其中找到一個高度可疑的
Y 座標累加機制。DOSBox-X 除錯器沿用上一段 session 已啟動的連線
（`Start-Process` 方式啟動，未重開），CS/DS 等 segment 值與第 3 節
記錄的完全一致，證實同一個存檔／同一次遊戲執行期間 segment 配置
是穩定的。

### 6.1 `GuiDrawEBox` 真正的函式進入點：`36AA:0A2C`

用「掃描 `55 8B EC`（`push bp; mov bp,sp`）加上編譯器堆疊檢查慣用語
`39 26 9C 00 72 05 9A 0B 23 24 08`」的方法（比對位元組序列找函式
邊界，不依賴反組譯對齊），在 `36AA:0700` 附近的記憶體裡找出連續
5 個函式邊界（`0x07E0`、`0x082C`、`0x0844`、`0x0864`、`0x0A2C`）。
第 3.4／3.5 節記錄的 `0x0A6B` 迴圈，落在 `0x0A2C` 這個函式的**內部**
（`0x0A2C` 到下一個函式邊界之間），因此 `0x0A2C` 才是 `GuiDrawEBox`
自己的函式起點。其序言 `push bp; mov bp,sp; push si; push di;
mov di,[bp+06]` 中，第一個參數從 `[bp+06]` 讀取（略過 `[bp+02]`／
`[bp+04]` 兩個 word），證實這是一個**被 far call 呼叫**的函式（far
call 會把 CS 和 IP 都壓入堆疊，占用 `[bp+02]`／`[bp+04]`）。

**實機驗證**：在 `0x0A2C` 設中斷點，用第 3.2 節記錄的安全翻頁鍵
（`up`／`down`）連續觸發 3 次選單重繪，斷點**完全沒有命中**，即使
畫面確實有翻頁效果（右下角三角箭頭方向改變、選項文字內容換了一批）。
**結論：`GuiDrawEBox`（畫外框）只在選單第一次開啟時執行一次，翻頁
重繪走的是另一條「只更新文字內容」的路徑，不會重新呼叫
`GuiDrawEBox`。**

### 6.2 翻頁時真正會執行的函式：`36AA:06C0`

用同樣的位元組掃描法，在 `0x0700` 之前找到函式邊界 `36AA:06C0`
（同樣的序言＋堆疊檢查慣用語），其範圍涵蓋第 3.7 節記錄的
`0x0740`／`0x07AB`（原本誤判為「命中測試／裁剪」的字元格迴圈）。
在 `0x06C0` 設中斷點，`up`／`down` 觸發翻頁後**確實命中**，證實
`0x06C0` 就是翻頁重繪實際會執行的函式。

命中當下堆疊頂端（`SS:[SP]`）依序是 `0x09AA`（IP）、`0x36AA`
（下一個 word，語意上是「CS」，但其實是呼叫端手動 `push cs` 塞進去
的參數，不是 far call 自動壓入的返回位址——見 6.3 節）。

### 6.3 呼叫慣例的一個陷阱：同 segment 內用「`push cs`＋near call」
　假裝 far call

反組譯呼叫端 `36AA:09A7`（`E8 16 FD`）確認這其實是 **near call**
（相對位移編碼），前面緊接著 `push ax`（0x09A5）、`push cs`
（0x09A6）——也就是說，即使是同一個 segment 內的呼叫，這個 build
的編譯器仍然手動把 `CS` 當一般參數 push 進去，讓被呼叫端可以用
統一的「參數從 `[bp+06]` 起算」慣例讀取，不管呼叫端是真的 far call
還是「near call + 手動塞 CS」。**這是這個 build 的編譯器/呼叫慣例
特性，以後在這個 segment 裡看到「push ax; push cs; call
（近呼叫）」這個組合，不要誤判成 far call 或誤算堆疊版面。**

### 6.4 `0x06C0` 的真面目：畫「一個字元」的最底層點陣圖 blit 函式

完整反組譯 `0x06C0`（`36AA:06C0`～`36AA:07DF`）後確認：

1. 用 `[bp+06]`（呼叫端傳入的字元代碼）當索引，查一張位於
   `DS:[A378]`／`DS:[A37A]`（一個 far pointer 的 offset／segment
   兩個 word）指向的**字元中繼資料表**（每個字元 2 bytes 索引，
   表項 `+0x0108` 存的是「這個字元字形點陣圖」相對於同一個 base 的
   位移），算出這個字元字形點陣圖的 far pointer。
2. 字形點陣圖的**第一個 word 是高度**（存到區域變數 `[bp-16]`），
   寬度則另外呼叫 `0x53D6` 這個獨立函式取得（存到 `[bp-18]`）。
3. 用 `si`（0..寬度）／`di`（0..高度）雙層迴圈，對每個像素呼叫
   `11A4:2AF4`（`11A4` 正是 `re_76`／本文件 3.3 節都確認過的
   graphics segment）畫點，座標是
   `(X = si + DS:[A374], Y = di + DS:[A376])`——證實
   `DS:[A374]` 是目前游標 X，`DS:[A376]` 是目前游標 Y。
4. **關鍵**：雙層迴圈畫完「這一個字元」的所有像素之後（`0x07D1`～
   `0x07D7`），執行：
   ```asm
   mov ax,[A376]   ; AX = 目前游標 Y
   add ax,[bp-16]  ; AX += 這個字元自己字形的高度
   mov [A376],ax   ; 寫回游標 Y
   ```
   也就是說**游標 Y 是「每畫完一個字元就往下推進一次」，推進量是
   這個字元自己的字形高度，不是「畫完一整行才推進一次、用統一行高
   推進」**。全程沒有看到任何地方用「寬度」去推進 `[A374]`（游標
   X）——這點在 6.6 節列為尚未解開的疑點。

### 6.5 實機讀值驗證：中文字形確實比原始英文字形「更高」

用中斷點停在 `0x06C0` 入口時讀 `AX`，抓到目前正在畫的字元代碼
（連續命中觀察到會先跳過幾個 `0x20`＝半形空白，接著是 `0x7F`，
應為這套字形系統裡的一個中文字圖檔代碼）。手動依 6.4 節的定址公式
分別查了兩個字元的字形高度欄位：

| 字元代碼 | 字形高度（`[bp-16]`）|
|---|---|
| `0x7F`（畫面上正在繪製的中文字） | **10** |
| `0x41`（`'A'`，原始 ASCII） | **6** |

也就是說：**目前這套中文字形，每個字的高度值確實比原始英文字形
大**（10 對 6，差 4 px）。如果 6.4 節「游標 Y 逐字元累加字形高度」
這個機制真的是排版跑掉的元凶，中文字串會比對應長度的英文字串
產生**更嚴重**的 Y 座標飄移量——這跟「這個問題是翻譯內容補齊後
第一次真正點亮這個畫面才暴露出來」（第 1 節背景）的時間線完全吻合：
不是這次改動引入新 bug，而是原本用英文字形時飄移量太小、不明顯，
換成中文字形後飄移量放大到肉眼可見。

### 6.6 呼叫端 `36AA:0864`：內嵌一個 `%C/%P/%c/%s` 風格的
　printf 直譯器，逐行迴圈但起始座標不隨行數變化

繼續往上追 `0x06C0` 的呼叫端，落在另一個更大的函式 `36AA:0864`
（`push bp; mov bp,sp; sub sp,0x1E; push si; push di;
mov di,[bp+06]`）。反組譯後確認這是一個**格式化字串直譯器**：

- 逐字元掃描一個以 NUL 結尾的字串，非 `%` 字元直接呼叫 `0x06C0`
  輸出；遇到 `%` 則進入格式規格字元的比對（`CS:0x0A1C` 是一張
  4 項的跳轉表，比對字元剛好是 ASCII `'C'`(0x43)、`'P'`(0x50)、
  `'c'`(0x63)、`'s'`(0x73)，看起來是自訂的 `%C`／`%P`／`%c`／`%s`
  格式碼，對應的處理程式碼還沒有反組譯）。
- 外層還有一個以 `si` 為索引、上限是 `DS:[A2DE]` 的**行迴圈**，
  每一輪都會：
  1. 用 `si*8 + DS:[A2E8]` 取出**這一行專屬的邊界表項目**（就是
     第 3.4 節記錄過的那張 8-byte／筆 bounds table，這裡證實它
     同時也被**逐行重複使用**，不是只有 index 0 有意義——3.4 節
     觀察到「只有第一筆非零」是在 `GuiDrawEBox` 的呼叫情境下，跟
     這裡 `0x0864` 的呼叫情境時間點不同，兩者不衝突）。
  2. 呼叫 `33F5:0073`——反組譯確認這其實只是一個
     `memcpy(dest, src, 8)` 的包裝（呼叫 `0824:0452`），把這一行
     的邊界表項目**複製**到一塊固定緩衝區 `DS:[A368]`，供 `0x06C0`
     內部的裁剪運算使用（`0x06C0` 會呼叫 `3783:0133`／`3783:00B4`
     等函式，拿 `A368` 跟目前游標位置＋字形尺寸做交集裁剪）。
  3. **但緊接著設定「這一行的起始游標座標」時，用的是
     `mov ax,di; add ax,[A372]` 算 Y、`mov ax,[bp+08]; add ax,[A370]`
     算 X——這兩行完全沒有用到剛剛複製進 `A368` 的邊界表 y1／x1，
     `di`／`[bp+08]` 是 `0x0864` 這個函式自己的參數，在整個行迴圈
     裡從頭到尾都是常數，不會隨 `si`（行數）改變。**

   換句話說：**目前追到的程式碼路徑裡，每一行文字開始繪製時的
   起始 X／Y，是同一組固定值，不會因為這是選單的第幾行而不同**；
   每一行的邊界表項目只被拿去做「裁剪範圍」，沒有被拿去做
   「起始座標」。

### 6.7 尚未解開的疑點（下一輪從這裡接續）

1. **X 座標（`DS:[A374]`）在目前追到的所有函式裡都沒有被推進**。
   `0x06C0`（畫字元）本身只推進 Y，不推進 X；呼叫端在讀下一個字元
   時用的輔助函式 `0x53A6`（反組譯確認：會判斷是不是雙位元組字元
   前導位元組，是的話讓字串指標 `[bp-06]` 多跳 1 byte——這代表這套
   引擎原生就有 DBCS／雙位元組字元支援，值得記一筆，但不是這次
   要追的重點），也只推進**字串讀取指標**，不推進**畫面游標 X**。
   目前完全不知道 X 座標在哪裡被推進——**可能藏在 `%C`／`%P`／
   `%c`／`%s` 那四個格式規格字元各自的處理程式碼裡**（`CS:0x0A1C`
   跳轉表指向的位址，這輪還沒有反組譯過），下一輪應該優先反組譯
   這四個 handler，尤其是 `%P`（很可能是「設定位置」，如果選單的
   每一行文字其實是靠格式字串裡嵌入的 `%P<x>,<y>` 之類的顯式定位碼
   來換行／換位置，而不是靠 6.6 節那個「行迴圈」本身移動座標，那
   6.6 節看到的「起始座標不隨行數變化」就不是 bug，而是預期行為，
   真正的問題會在 `%P` handler 內部）。
2. **「Y 每字元累加字形高度」這件事本身，究竟是遊戲引擎原生設計
   （例如：本來就假設呼叫端會在每行開頭插入一個「重設 Y」的控制碼
   或格式碼，只是目前的翻譯內容/GPL 補丁沒有正確插入這個控制碼），
   還是純粹的既有引擎瑕疵（原始英文文字因為字形矮、單行字數少，
   飄移量小到不明顯，換成中文字形才被放大到肉眼可見）**——這兩種
   假設現階段都還站得住腳，需要先解開疑點 1（找到 `%P`／`%C` 等
   handler 的實際行為）才能判斷,並決定修法應該是「補上正確的控制碼
   ／格式碼」（GPL 補丁／字串內容層級的修正）還是「修引擎本身的
   Y 推進邏輯」（EBOX patch 層級的修正）。
3. **驗證方向建議**：在 `CS:0x0A1C` 這張跳轉表的 4 個目標位址各設
   一個中斷點，`up`／`down` 觸發翻頁重繪，觀察哪些 handler 真的被
   呼叫到、傳入什麼參數（尤其是懷疑最大的 `%P`），比對其對
   `DS:[A374]`／`DS:[A376]` 的實際影響。這是目前最短、最直接能
   收斂到根因的路徑。
4. **不要重複已經走過的死路**：`GuiDrawEBox`（`0x0A2C`）已確認翻頁
   時不會被呼叫，不用再往這個方向追；`0x53A6`／`0x33F5:0073` 已經
   反組譯確認是無關的輔助函式（字串指標推進、記憶體複製），不用
   重查。

## 7.（重大修正，2026-09-19）第 6 節「已確認對話情境」其實抓錯了
　目標——那是圖示列 tooltip，不是對話選單文字

**結論先講：第 6 節從 6.2 節開始，一路往上追到的整條呼叫鏈
（`36AA:06C0`→`36AA:0864`→`3241:0426`→`3241:08FB` 附近），
目前有很高機率其實是「狀態列圖示的 tooltip 文字」渲染路徑，
不是對話選單的選項文字。第 6 節記載的所有底層機制（字元 blit
函式、逐字元 Y 座標累加、`%C/%P/%c/%s` 格式碼、元件結構
`+0x60`／`+0x62` 欄位）作為「這個引擎共用文字渲染機制長什麼樣子」
的技術事實應該仍然成立（因為這些都是可重現的實機讀值），但**把
它們跟「對話選單行距重疊」這個症狀掛勾，目前站不住腳**，下一輪
需要重新驗證，不能直接沿用第 6 節的結論繼續往下修。

### 7.1 怎麼發現抓錯目標的

在 `36AA:06C0` 設中斷點、按 `up`／`down` 觸發重繪，命中時堆疊
深度（`EBP=0xFA72`）每次都一樯，一開始誤以為「同一個深度＝同一個
穩定的對話選單呼叫路徑」，因此直接採信。但這次重新核對呼叫慣例時
發現一個定址失誤：**在 `36AA:06C0` 的中斷點命中當下（指令還沒執行
`push bp`），`EBP` 暫存器本身就已經是呼叫端 `36AA:0864` 自己的
frame pointer，不需要（也不應該）再對 `[EBP+0]` 多解一次參照**。
先前（第 6.2／6.6 節）誤把 `[EBP+0]` 解出來的值當成「`0864` 自己的
BP」再往下多跳一層，實際上那一跳解出來的是 **`0864` 呼叫端
（`3241:0426`）自己的參數**，不是「`0864` 的呼叫端是誰」。

用修正後的正確算法（`[EBP+06]`／`[EBP+08]`／`[EBP+0A..0D]` 直接就是
`0864` 自己收到的參數，不必多跳）重新讀這次命中的格式字串指標，
結果是 `4B7A:3C5C`——就是第 6.6 節一開始意外撈到、後來被歸類為
「不相關雜訊」的那個 `%C%C%s\0BUTN %u\0...ICON %u\0...` 圖示範本
字串！也就是說，第 6.2 節開始那條「已確認是對話情境」的呼叫鏈，
從頭到尾抓到的都是**同一個圖示 tooltip 元件**（結構位於動態配置的
`90xx`／`91xx` 段，例如 `915B:0004`、`90F0:0004`），只是因為它剛好
在按下 `up`／`down` 後很快被重繪（推測 `up`／`down` 同時也會改變
圖示列的鍵盤焦點，觸發焦點圖示的 tooltip 重繪），才被誤判成
「按鍵→對話選單重繪」的因果關係。

### 7.2 這個修正對第 6 節其他內容的影響

- **6.1（`GuiDrawEBox` 真正進入點 `0x0A2C`，翻頁不會呼叫它）**：
  這個結論本身不依賴「6.2 之後抓到的是不是對話情境」，**應該還是
  成立的**，可以保留。
- **6.2～6.5（`0x06C0` 是畫一個字元的底層 blit 函式、逐字元把
  `DS:[A376]` 累加該字元字形高度、中文字形高度 10 對 ASCII 高度 6）**：
  這些都是對**這個共用底層函式本身**的反組譯事實，不因為呼叫端是
  圖示還是對話而改變——**函式本身的行為描述應該仍然正確**，只是
  「因此推論對話選單會有 Y 飄移」這個推論目前**沒有實機證據支持**，
  需要重新在真正的對話呼叫鏈上驗證一次。
- **6.6（`0x0864` 內部 si 迴圈、`memcpy` 到 `A368` 只做裁剪、起始
  座標不隨 si 變化）**：這段觀察是**對圖示 tooltip 這個呼叫實例**
  做的，不能直接套用到對話選單（對話選單如果走的是完全不同的呼叫
  路徑，`si` 的意義、`[A2E8]`／`[A2DE]` 這兩個全域表被誰、在什麼
  時機填值，都需要重新確認，不能假設跟圖示 tooltip 共用同一份
  資料）。
- **6.7 疑點 1（`%P` 是空操作、X 座標找不到推進點）**：這個發現
  仍然成立（`%P` 的反組譯事實不受呼叫端身份影響），但既然整條
  呼叫鏈的「使用情境」判斷錯了，**不能再假設這就是對話選單排版
  的核心邏輯**——`%P` 有可能對圖示 tooltip 這種簡單單行文字完全
  用不到，但對話選單（如果走不同的呼叫路徑）可能有自己另外一套
  排版方式。
- **`3241:0426` 這個「元件焦點顏色選擇＋呼叫 `0864`」的函式**：
  現在看起來很可能是「所有 GUI 文字元件（圖示 tooltip、按鈕、
  也可能包含對話選單選項）共用的中層繪製函式」，`si` 是元件
  類型選擇碼（目前只看過 `si=1,2,3`，`si=2` 對應圖示）。**如果
  對話選項也是走同一個函式、只是 `si` 是別的值**，那麼下一輪
  應該去找 `si` 是其他數值時的行為分支（`3241:0426` 函式一開始
  `cmp ax,0008`／後面多處 `cmp si,0002` 的分支，還有其餘 `si` 值
  對應的路徑目前完全沒有反組譯過）。

### 7.3 下一輪建議做法（不要重複這次繞遠路的方式）

1. **不要再用「按鍵後第一個命中 `0x06C0`／`0x0864` 的中斷點」這種
   方式去找對話選單的呼叫鏈**——這次證實狀態列圖示 tooltip 的重繪
   頻率／時機跟對話選單重繪很接近，光靠中斷點命中的時間點無法
   分辨兩者，且圖示 tooltip 的呼叫頻率遠高於對話選單，用中斷點
   盲抓幾乎每次都會先抓到圖示。
2. **改用內容過濾，不要用時機過濾**：命中中斷點後，先讀出
   `0864`（或其呼叫端）收到的格式字串／文字內容指標，實際
   dereference 出來看是不是真的是對話選單的中文選項文字（例如
   比對開頭幾個 byte 是不是等於目前螢幕上顯示的那幾個選項的已知
   內容），確認內容相符了才繼續往上追呼叫鏈，不要只憑「按鍵後
   碰巧撞到」就假設是對話情境。
3. **另一個更直接的辦法**：如果除錯器支援記憶體讀取／寫入
   中斷點（`set_real_memory_breakpoint`／`set_protected_memory_breakpoint`，
   這兩個工具這次都還沒用過），可以先找到目前螢幕上選項文字
   實際存放的記憶體位址（例如從已知的 GPL 字串 catalog 或
   `build_cjk_display_staging.py` 輸出物件反查），直接對那個位址
   設「讀取」中斷點，這樣不管是哪個函式去讀它，都會準確命中，
   不會像這次一樣被圖示 tooltip 洗版。
4. **重新核對 BP chain 定址時，先確認「中斷點命中當下 `EBP` 究竟
   是誰的 frame pointer」，不要想當然爾多跳一層**——判斷方法：
   如果斷點設在函式的**第一個 byte**（`push bp` 那條指令本身還沒
   執行），此時 `EBP` 還是**呼叫端**的 frame pointer，直接對
   `EBP` 加參數位移（`+06`／`+08`…）就能讀到「這個函式」收到的
   參數；只有當斷點設在 `push bp; mov bp,sp` **執行完之後**的位址，
   `EBP` 才會變成「這個函式自己」的 frame pointer。這次會抓錯，
   就是把兩種情況搞混，多繞了一層。

## 8. 2026-09-19 接續：兩種內容過濾方法都試了，暫時卡關

延續第 7.3 節的兩個建議做法，本節記錄實際嘗試結果——**兩條路都在
目前的工具限制下卡關**，記下失敗原因，避免下一輪重蹈覆轍。

### 8.1 嘗試一：程式碼中斷點＋逐次檢查格式字串指標（7.3 第 2 點）

在 `36AA:0864` 設中斷點，每次命中都直接讀 `[ESP+4]`（`di`）／
`[ESP+6]`（X）／`[ESP+8..+11]`（格式字串 far pointer，此時 `EBP`
尚未被這個函式自己覆寫，讀取方式見第 7 節訂正過的算法），連續
命中約 10 次，**格式字串指標全部都是 `4B7A:3C5C`**（同一個圖示
tooltip 範本），對應的元件結構 segment 依序是
`915B→90F0→908C→908C→9022→9022→8FC1→...`，明顯是狀態列圖示
逐一輪詢重繪（每個圖示似乎呼叫兩次，猜測是「量測寬度」＋
「實際繪製」各一次）。**這個圖示列輪詢重繪的隊列看起來相當長**
（至少 8 個以上不同 segment，且還在繼續），用「盲跳過每一次命中」
的方式要跑完整輪、才可能輪到對話選單，代價太高，這次沒有耐心跑完
就放棄了這個方法。

### 8.2 嘗試二：記憶體「值改變」中斷點（`set_real_memory_breakpoint`，
　7.3 第 3 點的變體）

改用 `DS:[A376]`（游標 Y 全域變數）設定「值改變即停」的記憶體
中斷點，構想是：圖示的 Y 固定是 `3`，對話框外框是 `y=140~198`，
只要看到寫入值落在對話框的範圍就能確定抓對目標。實測發現這個
方法**在目前的 bridge 實作下速度太慢，不可行**：每次
`continue_execution` 只能讓 `DS:[A376]` 的值往前推進**極小的
一步**（觀察到的序列是 `3 → 7 → 7 → 11 → 21 → 21 → ...`，且
命中位址常常是**相鄰的兩條指令**，例如連續兩次命中分別停在
`36AA:07DA` 和 `36AA:07DC`）——這代表 `set_real_memory_breakpoint`
底層很可能是用「整台 CPU 逐指令單步、每步都檢查目標 byte 有沒有
變化」實作的軟體監看點，不是真正的硬體資料中斷點。在這個 bridge
的每次呼叫都有網路來回延遲的前提下，這種「每次 `continue` 只前進
一條指令」的機制，實務上**完全跑不完**一整段字元繪製迴圈（一個
字元的 blit 就有上百條指令），更不用說跑到對話選單真正被觸發
的那一刻。**結論：`set_real_memory_breakpoint`／
`set_protected_memory_breakpoint` 這兩個監看點工具，在需要「跑過
大量程式碼、只在特定條件才停」的場景下不適用，只適合「已經停在
非常接近目標的位置、只差幾條指令」的場景。**

### 8.3 目前對「圖示列重繪」這個雜訊源的新理解

兩次嘗試都指向同一件事：**這個畫面存在一個非常頻繁、獨立於對話
選單之外的狀態列圖示重繪佇列**，佇列長度看起來不小（八個以上
不同的動態配置 segment，每個可能呼叫兩次 `0x0864`），而且似乎
一直在跑（可能是每個遊戲 tick 都重新檢查所有圖示的 tooltip／
focus 狀態）。這個雜訊源的存在，本身也是一個值得記錄的環境事實：
**之後任何想用「在共用繪圖函式上設中斷點、靠時機或幾次
`continue` 過濾」的策略，都要預期會先撞上這個圖示重繪佇列，
不是只有這次調查會遇到。**

### 8.4 下一輪建議：換一條完全不同、不受即時性影響的路

前兩節證明「在共用底層函式上攔截、事後過濾」這條路，不管是用
時機還是用內容過濾，都被這個圖示重繪雜訊拖垮。下一輪建議改走
**靜態、由上往下**的路線，不依賴「準確抓到某一個瞬間」：

1. **直接找 GPL 直譯器裡 `0x48`（`gpl menu`）opcode 的 dispatch
   handler**（第 4 節第 3 點最早提過的方向，這次因為第一條路看似
   有進展所以被擱置，現在應該優先權提高）。這個 handler 是
   **GPL 位元組碼層級**的進入點，只有在直譯器真的執行到一條
   `gpl menu` 指令時才會被呼叫，執行頻率遠低於共用的字元繪圖
   函式，不會被圖示重繪淹沒。目前完全沒有這個 handler 的位址
   線索，需要先找到 GPL 直譯器的主 dispatch 迴圈／opcode 跳轉表
   （可能要從已知會執行 GPL 指令的某個時間點，例如剛觸發對話的
   那一刻，用 `configure_execution_trace` 或分析呼叫堆疊往回找，
   而不是在字元繪圖層級瞎猜）。
2. **另一個可能更快的辦法：暫時關掉圖示重繪的雜訊源**，而不是
   繞過它。如果能在 `3241:0426`（第 6 節找到的、圖示與選單共用的
   中層繪製函式）的**入口處**用 patch 或條件式暫停的方式，讓
   `si`（元件類型碼，圖示目前看到的都是 `si=2`）等於 2 的呼叫
   直接跳過／回傳，圖示列雜訊應該會消失，這樣再對
   `36AA:0864`／`36AA:06C0` 設中斷點時，就只會撞到真正的對話
   選單呼叫（假設它們真的走同一條 `0426` 路徑、只是 `si` 不同）。
   這個做法需要先確認「暫時讓圖示不重繪」不會導致除錯器或遊戲
   本身出現非預期的副作用（目前完全沒驗證過，只是理論上可行）。
3. **不要再嘗試 `set_real_memory_breakpoint`／
   `set_protected_memory_breakpoint` 來跨越大段程式碼**——已經
   證實這兩個工具在這個 bridge 上的實作代價，只適合「已經非常
   接近目標」的場景，不適合當作大範圍過濾工具使用。
