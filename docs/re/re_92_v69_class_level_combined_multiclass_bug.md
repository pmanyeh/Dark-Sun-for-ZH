# v69：職業＋等級合併顯示——單職正常，多職有 bug 待查

日期：2026-09-17

延續 `re_91`。使用者要求把職業／等級改成「牧師(3) / 聖堂武士(2) /
吟遊詩人(2)」這種合併格式（等級內嵌括號，原本獨立顯示等級數字的那一
行隱藏）。實機測試：**單職正常，雙職／三職會顯示錯誤的職業名稱**（等
級數字本身沒錯）。這版**不要部署**，先記錄現象與已排除的可能性。

## 1. 結論

- GERAKIS（單職）：`角鬥士(3)` 正確，原本獨立的等級行也正確隱藏了。
- K'RATCHEK（三職）：`戰士(2)/德魯伊(3)/靈能師(8)`——**這次測試中顯示
  正確**。
- CERMAK（雙職）：`保育師(7)/角鬥士(4)`——本身看不出錯（但下面 CILLA
  的狀況讓人懷疑是否巧合正確）。
- CILLA（三職）：**三段全部顯示「保育師」**（她應該是
  Preserver/Druid/Thief＝保育師/德魯伊/盜賊），只有括號裡的等級數字
  三段不同（跟她 `record+0x24/0x25/0x26` 的原始資料 2/2/3 相符）。

用中斷點即時追蹤 CILLA 的欄位2（`class_slot2_label_entry`）證實：**組字
邏輯本身完全正確**——`es:[bx+0x22]` 讀到 `0x06`（Druid，跟直接讀記憶體
確認的原始資料一致）、`class_offsets` 查表查到的來源字串正確指向
「德魯伊」的 Base94 資料、逐位元組複製迴圈正確複製了「德」「魯」
「伊」三個字＋等級「2」＋括號，`class_combined_buffer` 在呼叫
`decode_start` 之前內容確實是正確的「德魯伊(2)\0」。**問題出在
`decode_start`／`339E:016D` 這段共用管線某處，把三個欄位的字（不是
等級數字）混在一起，畫面上三段都變成同一個（時序上最後解碼的欄位1）
的名字，但等級數字卻各自正確**——目前不確定確切機制，懷疑是共用的
CJK 字形暫存 slot（`glyph_loader`／`active_slot`／`transport_codes`
那套，最多 7 個全域槽位）在同一次繪製裡被三次獨立的 `decode_start`
呼叫互相覆蓋，但實際繪製（`call 339E:016D`）可能是延遲到三個字串都
準備好才一次讀取，導致文字部份（透過 slot 間接引用）讀到最後一次的
內容，而等級數字（直接內嵌的純 ASCII，不經過 slot）不受影響。這個
理論還沒有反過來驗證（例如為什麼同一套機制在 `re_91`／v68c 的「純
職業名稱、不含等級」版本上，K'RATCHEK 三職顯示是正確的）。

## 2. 已排除的原因

- **不是** `class_offsets`／`class_combined_buffer` 的資料或索引算錯
  ——即時中斷點逐指令追蹤，CILLA 欄位2 從讀記錄到寫入緩衝區每一步
  都正確。
- **不是**等級數字轉換算式的問題——各角色、各欄位的等級數字全部正確
  （包含個位數不補零的情況）。
- 已知會強制 `cs:[cached_id] = 0xFFFF` 讓每個欄位都不會因為三個欄位
  共用同一個 tag（`0xFF95`）而誤觸快取直接跳過解碼——這個保護措施
  本身有沒有生效還沒有逐指令確認到底。

## 3. 尚未完成／建議

- 這個 bug 只在**多職**（2 個以上欄位在同一次繪製裡都呼叫
  `decode_start`）才會出現，需要對 `339E:016D` 本身（或它呼叫的更
  底層繪字/字形載入函式）做更深入的即時追蹤，確認繪製是「每個字串
  解碼完立刻畫」還是「三個字串都解碼完才一次畫」，以及 `active_slot`
  等全域狀態有沒有在三次呼叫之間被正確重置或互相干擾。
- 在查清楚並修正之前，**不建議部署 v69**：雖然單職正常，但多職顯示
  錯誤的職業名稱是不能接受的迴歸；等級行隱藏的 patch
  （`5FB0:1A01` no-op）是全域生效的，若真的要先上單職的效果，必須
  連帶處理「多職角色暫時看不到任何等級資訊」的問題，目前沒有這樣
  部分部署。
- `tools/build_view_class_level_combined_candidate.py`（v69）先保留
  當作已知有 bug 的紀錄，不要在這個基礎上繼續疊加其他修改。
