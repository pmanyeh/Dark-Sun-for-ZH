# 對話選項四選一分頁「殘影」問題：逆向追蹤進度 checkpoint

> 日期：2026-09-20
> 狀態：**「鏡射複製」修法（第 25 節）已實機驗證能解決「換頁畫面
> 完全不更新／凍結」這個原始主症狀，且不會像整頁翻轉（第 23～24 節）
> 那樣導致當機或讓對話框消失**。做法：換頁迴圈結尾（原本呼叫
> `1DAB:2C8D` 的地方）改成先跑一次原本的按鈕重繪（畫進背後頁，不變），
> 再把 `[11A4:0006]`（背後頁指標）暫時設成等於 `[11A4:0004]`（目前
> 顯示頁），重新對 4 個按鈕各自呼叫一次 `3241:0426` 重繪（此時會畫進
> 目前顯示頁），畫完後把 `[0006]` 還原——全程不碰 `show_page`／CRTC，
> 純粹是「重繪兩次、切換目標頁」，風險遠低於整頁翻轉。
>
> **但實機測試發現殘留的問題只解決了一半（見第 26 節）**：換頁後
> 選項文字下方仍會出現一排虛線狀殘影，且**已確認跟清除矩形高度完全
> 無關**（把按鈕的清除高度從 10 改到 3、16、30 都測試過，畫面毫無
> 變化，這個假設可以正式排除）。已確認殘影只在按過 `Down` 換頁之後
> 才出現，第一頁（從未換頁）不會有殘影，代表這確實是換頁重繪路徑的
> 問題，不是對話框開啟當下就有的獨立瑕疵。根因目前**尚未定位**，第
> 26 節記錄了對 `36AA:052F`（清除矩形函式）呼叫參數的初步反組譯，
> 但參數版面跟舊版文件（第 2 節）的描述對不太起來，需要下一輪重新
> 從頭確認 `052F`/`11A4:76C2`/`11A4:771C` 的真正呼叫慣例，而不是
> 沿用舊文件的猜測。第 1～24 節記錄的排錯過程與教訓仍有參考價值，
> 保留不刪，但第 23～24 節的整頁翻轉修法已證實不可行，不要重複
> 嘗試。**任何進一步的 `write_memory`／插入程式碼實驗都要先明確
> 告知使用者風險**，且優先在不影響遊戲進度的時間點測試。

## 0. 背景

`re_96`／`re_97` 解決的是舊版 `GuiMenuLayout`（動態 MENU 控制項）的
行距重疊問題（`--menu-line-gap`）。但本輪要修的「殘影」問題，實際
發生在**後來另一條開發線**：`tools/patch_dialogue_menu_wind.py` +
`--dialogue-option-pitch`，把 WIND-3008 這個對話選項視窗的 5 個
固定 `BUTN`（按鈕）子物件，從原本 8px 間距的 5 選項版面，改成
11px 間距、只顯示 4 個按鈕＋分頁（「MORE」三角形指示器），第 5 個
按鈕被移到視窗外停放。這是**完全不同的一條程式路徑**（固定 WIND
按鈕 + 分頁邏輯，不是 `GuiMenuLayout` 動態排版），`re_96`／`re_97`
的結論在這裡不適用，必須重新反組譯。

**症狀**：實機截圖顯示，翻頁後新一頁的選項文字周圍／下方，殘留
前一頁文字筆劃的碎片（虛線狀雜訊），而且**每多翻一次頁，殘影會
越疊越多**（不是單純「上一頁沒清乾淨」的一次性殘留，而是累加式
的疊圖）——這個「累加」線索很重要，暗示問題比較像「有時候乾脆不
清除背景就直接疊字」，而不是「清除矩形算得太小」。

## 1. 本輪環境注意事項

- 本輪沿用使用者已經開著的 DOSBox-X-AI session（`Start-Process`
  啟動、原生 bridge 259876 埠），遊戲當時已經停在殘影畫面（"WHAT DO
  YOU SAY?" 選單），這是本輪能直接動態除錯的前提，不用重新啟動。
- **檔案位移 → 執行期 segment 的换算公式（僅本次 session 有效）**：
  用 `memory_search` 對照 `scratch_test/cjk_display_staging_v83_dialogue_four_paged/GAME/DARKSUN/DSUN.EXE`
  裡已知的位元組序列（例如 `patch_dialogue_menu_wind.py` 的
  `PAGE_SIZE_PATCHES` 附近，不含任何會被 loader 重定位的 far
  segment 立即值），在即時記憶體裡找到完全一致的比對結果：
  `file_offset 0x7DC55` ↔ 實機線性位址 `0x5FC15`（`5FC1:0005`）。
  **由此得到 bias = 執行期線性位址 − 檔案位移 = −0x1E040**，也就是
  `runtime_linear = file_offset − 0x1E040`。這個 bias **只在這次
  session、這次遊戲執行期間有效**——這個 overlay 模組每次載入的
  位址可能不同，下一輪要重新用同樣方法（挑一段不含可重定位 far
  segment 立即值的位元組序列去 `memory_search`）重新推算，不能直接
  套用 −0x1E040 這個數字。
- 有一個共用的 GUI 繪製函式段 `3241`（`0426`＝畫一行/一個控制項，
  `07FA`＝設定控制項文字並觸發重繪，`071A`＝設定 enable/disable
  狀態）**在這次執行中沒有被重定位**（far call 指令裡的 segment
  立即值 `3241` 直接命中，不需要 bias 校正）——這點目前只是實測
  觀察，還沒查清楚為什麼這個段不用重定位，留給下一輪好奇的話可以
  查，不影響本文件的可用性。
- **教訓（呼應 `re_96` 8.1 節)**：`3241:0426`／`3241:07FA` 這類共用
  繪製函式，同時也被「狀態列圖示 tooltip」之類的高頻背景重繪呼叫。
  在這個函式上單純設中斷點、按一次鍵就 `continue`，十之八九會先
  撞到圖示重繪（`si` 暫存器＝元件類型碼；圖示是 `si=1`，选项清单
  按鈕也用 `si=2`，兩者共用同一個函式，不能只靠中斷點命中與否來
  判斷抓到的是哪個元件，一定要進一步讀 `[bp+06]` 指向的控制項
  結構、比對 `"BUTN"+control_id` 是不是我們要的 `0x081C..0x081F`
  範圍）。本輪第一次設中斷點就親身踩到這個雷（見第 4 節）。

## 2. 已確認的呼叫鏈（四選項分頁的「填字」路徑）

```
(翻頁事件，觸發點尚未找到——見第 5 節)
  -> 檔案位移 0x7D860 起的迴圈函式（本次執行期 5F82:0000）
     si = 0..3 逐一处理 4 個按鈕槽：
       cmp dx,ax（dx=本頁實際選項數，ax=si）
       若 si < dx（此槽有真的選項文字）：
         call 222E:324B   -- 用 catalog record（51 bytes/筆，
                              base=DS:5537）格式化出顯示字串
         push controlID(=0x081C+si，movsx 成 dword)
         push windowHandle(DS:[4683:0000] 全域目前視窗指標)
         call 3241:07FA   -- SetButtonText（本次執行期 5F82:0047）
       若 si >= dx（此槽本頁沒有選項，要清空）：
         push DS:1F16（固定的空白樣板字串）
         push controlID / windowHandle（同上）
         call 3241:07FA   -- 本次執行期 5F82:006D
     inc si; cmp si,4; 迴圈到 4 為止
```

`3241:07FA`（SetButtonText）內部：

```
2D55:049E(windowHandle, "BUTN", controlID) -> 取得按鈕結構遠指標(dx:ax)
若找不到 -> 寫錯誤碼到 [9DDA]，呼叫 0824:2EC5（很可能是 fatal/log），return -1
若找到：
  0824:37E4(新字串遠指標, &local_buf[bp-5C]) -- 疑似做斷行／格式碼展開
  把 local_buf 逐位元組複製進按鈕結構 +0x6E（文字內容欄位），
    複製長度固定等於按鈕結構自己的 +0x6D 欄位值（不是新字串的實際
    長度！這點還沒確認會不會造成資料層級的問題，見第 6 節疑點 1）
  若按鈕的樣式旗標（+0x9E 的 bit3/bit4）任一為真：
    push 2, push 按鈕遠指標, call (near, 靠 push cs 偽裝成 far)
         3241:0426   -- 實際「清背景＋畫字」的共用繪製函式
    若回傳非 0 視為失敗，return -1
  return 0
```

`3241:0426`（共用繪製函式，`si`=呼叫端傳入的元件類型碼，
選項按鈕是 `si=2`）內部關鍵段（本次執行期同一個 `3241` 段）：

```
... (0x043D~0x0508：量測文字、決定前景色 di，這段對 si 敏感但
     跟殘影無關，略)
0x058C: cmp dword es:[bx+64],0000        ; bx = [bp+06] = 按鈕結構
        je 0x5E9                         ; 為 0 就整個跳過清背景！
        (非 0 才會走清背景路徑：)
0x05A4: eax = es:[bx+68]                 ; 取「清除矩形」遠指標
0x05B1: call 11A4:6706(rect_ptr)         ; 疑似 Lock/取得矩形資訊
0x05C6: push [bp-04]色, rect_ptr, 0,
        es:[bx+5E], es:[bx+5C]
        call 36AA:052F                   ; 真正的填色/清除呼叫
0x05EC: cmp byte es:[bx+6D],0            ; 若文字長度欄位=0 -> 不畫字
0x05F3~0632: 把按鈕結構 +0x6E 開始、長度=+0x6D 的內容複製到區域
        緩衝區 [bp-60]，結尾補 0
0x063F: push local_buf, di(前景色), [3C02](字型?), 0, "%C%C%s"樣板
        (DS:3C5C), es:[bx+62], es:[bx+60]
        call 36AA:0864                   ; 逐行印字（re_96 已大量
                                          ; 反組譯過的同一個函式）
```

`36AA:052F`（填色/清除矩形函式）內部先呼叫 `11A4:76C2`／
`11A4:771C`（疑似 rect 物件的 GetWidth/GetHeight 存取器）把
`(x,y)+rect_ptr` 換算成 `(x1,y1,x2,y2)`，再用 `3783:0079` 跟
`DS:[A2E8+si*8]`（`re_96` 3.4 節記錄過的同一張「子物件邊界表」！）
做交集裁剪，交集結果才是真正拿去畫的區域。

## 3. 目前最可疑的兩個假說

1. **`es:[bx+64]==0` 直接跳過清背景**：`0x058C` 這個判斷式意味著
   「只有某些按鈕才會清背景，其餘直接把新字疊印在舊字上」。如果
   這 4 個選項按鈕（`0x081C..0x081F`）在這條路徑上剛好是
   `+0x64==0`（例如因為 `patch_dialogue_menu_wind.py` 只改了
   `WIND-3008` 資源裡的 Y 座標欄位，沒有觸碰任何跟「是否需要不透明
   背景」相關的旗標／欄位，導致這批按鈕從資源解析出來時就沒有設定
   這個欄位），就會完美解釋「每次都直接疊字、越疊越多」這個實機
   觀察到的**累加式**殘影現象。
2. **`es:[bx+68]` 指向的矩形跟目前文字的實際換行高度對不上**：
   若背景確實有清除，但矩形是「按這顆按鈕的固定尺寸」而不是「這次
   要畫的文字實際換行後的尺寸」，換到較短的中文譯文時，矩形可能
   縮小到蓋不住前一次較長／較多行譯文殘留的範圍。這個假說能解釋
   「殘影」但比較難解釋「累加」，除非清除矩形本身也一直用同一個
   (經常偏小的) 固定值，每次都只清一小塊、永遠清不乾淨。

**兩者中，假說 1（背景清除被整個跳過）目前證據權重較高**，因為它
直接對應到實機觀察到的「累加」現象；但本輪未能在**選項按鈕本尊**
身上實際讀到 `+0x64`／`+0x68` 的數值來證實（見下一節）——之前讀到
的一組數值其實是誤觸了 MORE 三角形圖示按鈕（`BUTN 0x0830`），不是
選項文字按鈕。

## 4. 本輪的一個岔路：誤把「MORE 三角形圖示」當成選項按鈕

在 `3241:0426` 的 `0x058C` 設中斷點、按下 `down` 鍵後第一次命中，
讀出的按鈕結構（`9232:0004`）解出 `"BUTN" + id=0x0830`——查
`WIND-3008` 原始資源（`from Steam/games/Dark Sun-ENG/GAME/DARKSUN/RESOURCE.GFF`
的 `WIND` chunk 3008，未經任何 CJK patch）確認：

```
42 55 54 4E 30 08 00 00 31 01 12 00 ...   <- BUTN id=0x0830, X=0x0131(305), Y=0x0012(18)
```

`0x0830` 正是分頁邏輯裡用來畫「下一頁／上一頁」三角形指示器的
按鈕 ID（對照 `tools/patch_dialogue_menu_wind.py` 的
`REMOVED_CHOICE_ID = 0x0820` 與 `CHOICE_IDS = 0x081C..0x081F`，
`0x0830` 不在這個範圍內，是另一個獨立的圖示按鈕）。也就是說，
第一次的 `+0x64`／`+0x68` 讀值（`+0x64=0x00002F44` 非零、
`+0x68` 指向 `91D0:0004` 這組看起來合理的矩形資料）是**三角形
圖示按鈕**的資料，不能拿來代表選項文字按鈕 `0x081C..0x081F` 的
真實狀況——這是本輪最大的一次繞遠路，記錄下來避免下一輪重踩。

同一份 `WIND-3008` 原始資源裡，確認 5 個選項按鈕的原始（未 patch）
記錄格式一致，都是 `BUTN` + id(4 bytes) + X(2 bytes) + Y(2 bytes)
+ 18 bytes 的 0 填充（每筆記錄共 30 bytes），且**完全沒有額外的
寬度／高度欄位**：

```
BUTN 0x081C: X=3, Y=13   (= FIRST_CHOICE_Y)
BUTN 0x081D: X=3, Y=21   (= 13+8)
BUTN 0x081E: X=3, Y=29   (= 13+16)
BUTN 0x081F: X=3, Y=37   (= 13+24)
BUTN 0x0820: X=3, Y=45   (= 13+32，這顆已被 patch 停到 y=61)
```

資源裡沒有寬高欄位，呼應了第 3 節假說 2 的可能性沒被排除，但也
支持假說 1：既然資源本身沒有任何跟「背景清除矩形」直接對應的
欄位，那個矩形（`+0x68`）跟「要不要清除」的旗標（`+0x64`）很可能
是**執行期動態配置**、依控制項類型／樣式初始化出來的，而不是
靜態寫死在 `WIND-3008` 裡——這代表如果選項按鈕跟三角形圖示按鈕
在「建立時的樣式」上有差異（例如三角形圖示是標準的 opaque icon
按鈕，而選項按鈕是這次為了容納多行 CJK 文字而稍微客製過的類型），
兩者在 `+0x64` 有無被設值上完全可能不同。

## 5. 卡關點：找不到真正觸發「翻頁」的輸入方式

`re_96` 3.2 節記錄「方向鍵 up/down 可以安全翻舊版 MENU 控制項的
頁」，但這是舊版 `GuiMenuLayout` 動態選單的結論。**這次全新的
WIND/BUTN 四選一＋三角形分頁介面，本輪測試 `up`／`down`／`5`
鍵、以及對三角形圖示座標的滑鼠點擊，都沒有觀察到任何新的
`3241:0426` 命中，也沒有觀察到畫面內容變化**——很可能：

1. 這套新介面翻頁的按鍵／滑鼠操作跟舊版不同，本輪没猜對；或
2. 滑鼠點擊座標换算有誤——`get_mouse_capture` 回報
   `guest_width/height = 640x400`（宣稱是 320x200 native mode
   的「雙倍寬高」渲染結果），但本輪用 `move_mouse_absolute`
   校準測試（要求座標 `(320,200)`）後截圖比對，游標視覺上似乎
   落在遠小於 320 的 X 位置，換算關係跟工具文件描述的不一致，
   本輪未能在合理呼叫次數內校準出準確的公式，因此后续滑鼠點擊
   （包含瞄準三角形指示器的嘗試）座標很可能都不準。

**下一輪建議**：
- 優先直接問使用者「實機是用什麼操作翻到殘影那一頁的」（滑鼠點
  三角形？鍵盤哪個鍵？），比繼續盲猜省時間非常多。
- 如果要繼續走校準路線：改用 `capture_frame` 搭配已知會在固定
  螢幕座標畫出東西的操作（例如先點擊視窗中一個已知位置的按鈕，
  比對點擊前後該按鈕的「按下」視覺狀態變化落在截圖的哪個像素）
  來反推座標換算公式，會比單看游標箭頭本身的視覺位置準確，因為
  游標 sprite 在小截圖上用肉眼很難精準定位到個位數像素。
- 找到可靠的翻頁觸發方式後，直接重複第 4 節的方法：中斷點設在
  `3241:0426` 的 `0x058C`（用本輪算出的 bias 或當輪重新算過的
  bias 換算），命中後**務必先讀 `[bp+06]` 指向結構 `+0x04..+0x0B`
  確認 `"BUTN"+id` 落在 `0x081C..0x081F` 範圍**再繼續分析，避免
  重蹈第 4 節誤抓三角形圖示的覆轍。讀到選項按鈕真正的 `+0x64`／
  `+0x68` 數值後，就能直接判斷是「假說 1：整個跳過清除」還是
  「假說 2：矩形尺寸對不上」，兩者的修法完全不同（假說 1 可能要
  在 `WIND-3008` 或按鈕初始化路徑補上正確的樣式旗標；假說 2 則要
  修矩形尺寸的來源或改用 always-max-size 的清除矩形）。

## 7. 同一輪接續：確認使用者實際操作方式後的第二次嘗試

問過使用者後確認：畫面上的翻頁動作是**滑鼠點擊右下角的三角形
圖示**，不是鍵盤。這節記錄第二次嘗試的結果——**部分證實了第 3 節
假說 1（`+0x64==0` 導致整個跳過清背景），但還沒能 100% 確認是套用
在選項文字按鈕本尊上**，下一輪應該從這裡接續，不用重新推算 bias
（同一個遊戲執行期間，`5FC1:0005`／`5FC9:000C` 這組校準點依然
有效）。

### 7.1 三角形圖示的絕對螢幕座標推算

從目前存活的 `WIND-3008` 視窗實例（執行期指標 `923A:0004`，
`+0x00` 開頭的 `"WIND"` 標記／`0x01D7`／`0x0BC0` 都跟靜態資源檔
header 完全吻合，確認找對了視窗）讀出 `+0x10`／`+0x18` 兩組
重複的 `(140, 318, 198, 0)`，對應 `re_96` 3.4 節記錄過的同一個
外框 `(x1=0, y1=140, x2=318, y2=198)`（native 320x200 座標）。
三角形圖示按鈕（`BUTN 0x0830`）的 `+0x5C`／`+0x5E` 欄位讀到
`X=0x131=305`（已經是絕對座標，因為視窗 `x1=0`）、`Y=0x12=18`
（視窗**局部**座標，要加上視窗 `y1=140`），推算絕對 native 座標
約 `(305, 158)`。`get_mouse_capture` 回報 `guest_width/height=
640x400`（native 320x200 的兩倍），所以点击时把这组座標乘以 2，
使用 `click_at(610, 316, coordinate_space="guest_pixels")`。

**重要教訓**：`capture_frame` 回傳的截圖**不含滑鼠游標**
（`cursor_included: false`），這次一開始誤把畫面上某個遊戲本身
的靜態圖案（門口/人物陰影）當成游標在移動，花了不少來回才發現
截圖裡本來就看不到游標，不能用「肉眼比對游標在截圖裡的位置」來
校準滑鼠座標映射——下一輪如果還要校準，只能用「點擊前後某個已知
UI 元素的視覺狀態變化」這種間接方式，不要重蹈覆轍。

### 7.2 點擊 `(610, 316)` 命中的結果：疑似不是選項按鈕本尊

在 `3241:0426`（共用繪製函式入口）設中斷點、點擊上述座標後，
**真的命中了**，而且這次呼叫端是 `CS=30F5`（透過真正的 far call，
不是 `07FA` 那種「push cs 偽裝」的 near call）——代表這是一條
之前沒追過的、由滑鼠點擊事件直接觸發重繪的獨立路徑，可能正是
我們要找的「翻頁」呼叫鏈。

讀出的按鈕遠指標＝`8388:0004`，解出：
- `+0x04`：`"BUTN"` 標記，確認是一個按鈕物件。
- `+0x54`（父視窗指標）＝`981C:0004`——**跟目前全域「目前視窗」
  指標 `DS:[4683:0000]`＝`923A:0004`（也是三角形圖示的父視窗）
  不一致**，代表這顆按鈕很可能**不屬於**我們的對話選項視窗，而是
  螢幕上其他 UI（例如狀態列圖示）。
- `+0x5C`／`+0x5E`（位置）＝`(0, 0)`——不吻合任何一顆已知選項
  按鈕的座標（`X=3, Y=13/21/29/37`），也不吻合三角形圖示
  `(305,18)`。
- `+0x6D`（文字長度）＝`0`——目前沒有文字內容。
- **`+0x64`＝`0x00000000`，`+0x68`＝`0x00000000`，兩個都是真正的
  NULL**——這會讓 `0x058C` 的 `cmp dword es:[bx+64],0000; je skip`
  直接跳過整個清背景步驟！**這是本輪第一次在非假設情境下，實機
  讀到「背景清除被整個跳過」的真實案例**，直接支持第 3 節假說 1。

但因為位置／父視窗都對不上對話選項視窗，**這顆按鈕的身份還沒有
確認**——最可能的解釋是：`(610,316)` 這個換算座標其實沒有精準
命中三角形圖示本身，而是命中了畫面上其他目前閒置、尚未使用的
UI 元件（例如狀態列圖示格），只是**恰好**也是走同一條
`3241:0426` 共用繪製路徑、`+0x64`／`+0x68` 也剛好是 NULL。

### 7.3 下一輪具體建議

1. **不要再靠推算座標盲點**——上面的推算流程雖然邏輯合理，但
   兩次嘗試（先前的鍵盤/滑鼠混合校準、這次的精算座標）都沒能
   100% 確認命中對話選項視窗裡的元件。最可靠的辦法是請使用者在
   截圖上標出滑鼠點擊的**畫面像素位置**（或用某種螢幕錄影／滑鼠
   軌跡記錄工具），拿到精確數字後直接套用，不用再猜。
2. **命中 `3241:0426` 之後，先用 `+0x54`（父視窗指標）比對
   `DS:[4683:0000]` 目前的全域視窗指標，等於才繼續分析**——這是
   本節學到的、比單靠「位置座標是否眼熟」更可靠的過濾條件，因為
   位置欄位在不同執行時刻可能因為視窗捲動／重排而變動，但「這個
   物件屬不屬於目前使用者正在互動的那個視窗」不會變。
3. 如果之後真的命中了屬於 `923A:0004`（或當輪重新確認過的
   最新視窗指標）底下、`+0x5C`／`+0x5E` 落在 `X≈3` 附近（四顆選項
   按鈕的共同 X 值）的物件，那才是真正的選項文字按鈕，這時再讀
   `+0x64`／`+0x68` 才有決定性意義。
4. 如果多次驗證都確認**選項文字按鈕本身**的 `+0x64` 也是 `0`，
   第 3 節假說 1 就完全成立，修法方向會是：找出這批按鈕在
   `WIND-3008` 解析/建立時，`+0x64`／`+0x68` 應該被設成什麼值
   （可能要對照一顆「正常會清背景」的按鈕，例如原版遊戲裡其他
   畫面用到的標準按鈕，比對兩者在建立階段的差異），或者更省事的
   替代方案：在 `patch_dialogue_menu_wind.py` 產生 `WIND-3008` 之外
   ，額外在 `SetButtonText`（`3241:07FA`）呼叫前，用一支獨立的
   「強制清除這顆按鈕完整區域」的小函式呼叫墊在前面（類似手動補一
   個 `36AA:052F` 呼叫，rect 用按鈕的最大可能尺寸而不是依賴
   `+0x68` 的動態值）。

## 9. 根因確認（同一輪，問到使用者操作方式後的第三次嘗試）：清除
矩形的高度固定只有 10px（一行），不會隨換行行數變化

第 7 節點擊三角形抓錯目標之後，直接問了使用者，確認**上/下方向鍵
其實也能翻頁**（不是只有滑鼠點三角形），第一輪（第 4 節）用
`down` 鍵沒能命中 `5F82:0047`，這次重新嘗試就命中了——推測是
當時鍵盤事件送達時機或遊戲焦點的偶發問題，不是「這個按鍵沒作用」
（教訓：同一個操作**沒觸發中斷點，不代表這個操作本身無效**，
遇到這種情況應該多重試幾次，而不是過早改用滑鼠去猜座標，第 7 節
整節的滑鼠校準繞遠路本可以避免）。

用 `down` 鍵成功命中 `5F82:0047`（四選項迴圈裡「真的有文字」那個
分支），單步進入 `3241:07FA` → `3241:0426` → `36AA:052F`，這次讀到
的按鈕結構是 `91C5:0004`，直接確認：

- `+0x08`＝`0x0000081C`：**id 欄位其實在 struct+0x08，不是我先前
  誤判的 +0x04**（+0x04 是 marker 後緊接的另一個欄位，這次讀到
  是 `0x000000A3`，意義未知，不影響主線）。這一次才是真正修正過的
  完整 struct 偏移對照，取代第 4／7 節的錯誤假設。
- `+0x54`（父視窗）＝`923A:0004`，跟全域目前視窗指標
  `DS:[4683:0000]` 完全一致——**這次真的是對話視窗底下的子物件**。
- `+0x5C`／`+0x5E`＝`(3, 13)`——精準吻合 `BUTN 0x081C` 在
  `WIND-3008` 資源裡的原始座標（`X=3, Y=13`）。
- `+0x64`＝`0x00002F46`（非零）、`+0x68`＝遠指標 `9165:0004`
  （非零）——**背景清除路徑確實有被執行，不是像第 7 節那個無關
  控制項一樣被跳過**。第 3 節假說 1（整個跳過清除）在選項按鈕
  本尊身上被**推翻**。
- `+0x6D`＝`0x35`（53，文字內容長度）、`+0x6E` 起是實際譯文內容
  （含 `0x5E` 開頭的雙位元組序列，是這個專案自訂的 CJK 字符編碼，
  不是 ASCII）。

單步跟進 `36AA:052F`（真正的填色/清除函式）內部兩個關鍵存取器
呼叫，直接讀到清除矩形的最終計算結果：

```
x1 = [bp+06] = 3          (按鈕自己的 X)
y1 = [bp+08] = 13         (按鈕自己的 Y)
call 11A4:76C2(rect_ptr=9165:0004, x=0) -> AX = 0x012C = 300   ; 寬度
x2 = x1 + 300 = 303
call 11A4:771C(rect_ptr=9165:0004, x=0) -> AX = 0x000A = 10    ; 高度
y2 = y1 + 10 = 23
```

**清除矩形＝ `(3, 13) - (303, 23)`，高度固定只有 10 像素（剛好等於
單行 CJK 字高），完全不管這次要畫的文字實際換行後有幾行。**這就是
殘影的確定根因：只要譯文在 ~300px 寬的按鈕裡換行超過一行（中文
16x15 點陣字＋按鈕寬度換算，換兩三行是家常便飯），清除矩形只清得
到第一行的範圍，第二行以後的舊字永遠不會被清掉，而且**每次翻頁都
只清第一行**，所以殘影會隨著翻頁次數不斷疊加，跟使用者截圖裡觀察
到的現象完全吻合。

用 `disassemble` 追了一段 `11A4:771C`（回傳「10」的那個存取器）：
它不是單純讀 `rect_ptr` 某個固定欄位，而是 `lds si,[bp+06]`
取得 `rect_ptr`，再用另一個參數（本次呼叫是 `0`）當索引，跟
`[si+04]`（本次讀到＝`1`，即「這個 rect 物件只有 1 筆索引」）比較
範圍，通過後再做兩次 `shl bx,1`（`*4`）去查表——**這是一個通用、
可能被整個引擎大量其他 UI 元件共用的「區域/矩形類別」存取器，不是
`WIND-3008` 專屬的東西**，貿然直接改這個函式或它索引到的共用資料
風險很高（可能牽動遊戲裡所有用到同一個元件類別的畫面）。

## 10. 建議的修法方向（因為根因已確認，可以評估修法了）

清除矩形的「高度」是從按鈕的**類別/共用描述物件**（`9165:0004`
這個 rect_ptr）算出來的固定單行高度，不是每次依照「這次文字換行
後實際佔幾行」動態計算——這代表要修，思路上有三種，風險由低到高：

1. **內容層修正（風險最低，建議優先）**：既然引擎假設「選項按鈕
   文字固定一行」，最安全的做法是讓譯文配合這個假設——在
   localization pipeline／GPL 譯文審稿階段，針對 `WIND-3008`
   這四個選項按鈕使用到的譯文，**限制每則譯文在目前按鈕寬度
   （換算約 300px／field 寬度）下不能換行超過一行**（例如透過
   `tools/` 底下量測目前中文字型＋按鈕寬度後的「每行最大字數」，
   對過長譯文要求精簡或改寫，而不是逐字直譯）。這不用碰任何
   binary patch，風險最低，但要配合翻譯／審稿流程一起做，不是
   單純改程式能解決。
2. **加大按鈕本身的可用寬度（中風險）**：`patch_dialogue_menu_wind.py`
   目前只動了 Y 座標（`FIRST_CHOICE_Y + index*PITCH`），沒有動過
   X 座標／寬度。如果 WIND-3008 資源或按鈕類別裡能找到「按鈕寬度」
   欄位並適度加寬（配合視窗本身寬度上限 318px），能讓更多譯文在
   加寬後仍然維持單行，減少觸發這個 bug 的機率，但無法**保證**
   徹底解決（比較長的譯文還是可能換行）。
3. **直接修清除矩形的高度來源（風險最高，不建議在還沒完全弄懂
   `11A4:76C2`／`771C` 這組共用存取器＋它背後的資料表結構之前
   貿然嘗試）**：因為第 9 節已經確認這是一個「通用區域類別」的
   存取器，可能被此對話框以外的其他 UI 大量共用，直接改
   `9165:0004` 這個 rect 物件的內容，或是修改 `11A4:771C` 這個
   函式本身，都有可能影響到看似無關的其他畫面（例如其他視窗的
   按鈕、選單……），下一輪如果要走這條路，**必須先查清楚
   `9165:0004` 這個特定 rect_ptr 是不是`WIND-3008`專屬配置
   （例如檢查它的記憶體段是否隨著每次開關對話框而重新配置／
   釋放，還是整個遊戲執行期間共用同一份），確認影響範圍後才能
   評估動手的風險。

**個人建議：先走方案 1（內容層限制譯文長度）**，這是這次逆向
唯一確認「風險可控、不用碰任何組合語言」的修法，且完全符合這個
專案本來就有的「翻譯要配合原版排版限制」慣例（例如 VIEW CHARACTER
欄位、EBOX 對話行寬都有類似的長度/换行限制）。方案 2／3 可以留給
真的需要保留較長譯文措辭時再評估。

## 12. 使用者修正與現場實驗：把清除高度從 10 直接改成 12

使用者看過第 9／10 節後指出兩點修正：

1. 中文字高其實是 **11px**，不是 10px——清除矩形只清 10px，剛好
   少 1px，這才是殘影的直接成因（不是「完全沒清除」，是「差一點點
   沒清乾淨」）。
2. 翻頁時**每一行都有各自清除**（不是只清第一行），只是**越下面
   的行，殘留看起來越多**——這點目前還沒有找到獨立成因，暫時先
   接受「差 1~2px，多次翻頁疊加後視覺上更明顯」這個最簡單的解釋，
   還沒有排除「由上而下逐漸放大的系統性座標誤差」這個更複雜的
   可能性（見下方「尚待確認」）。

並直接建議修法：**既然清除高度固定是 10，直接改大（例如 12）
即可**。

### 12.1 現場資料結構驗證：確認每顆按鈕的清除矩形是「各自獨立的
複本」，不是共用同一份全域物件

用 `up`／`down` 鍵重新觸發翻頁（**這次確認鍵盤翻頁本身沒問題，
先前第 4 節「鍵盤沒反應」是巧合性的一次沒觸發，不是方法錯誤**），
在 `3241:0426` 設中斷點，依序讀到：

- `BUTN 0x081C` 的矩形物件在 `9165:0004`：`01 00 0A 00 00 00 2C 01 0A 00 01 00`
- `BUTN 0x081D` 的矩形物件在 `9101:0004`：`01 00 0A 00 00 00 2C 01 0A 00 02 00`

兩者內容幾乎一致（`+4`＝寬度表筆數1、`+6`＝高度10、`+0xA`＝寬度
300、`+0xC`＝高度10，只有最後一個 word 不同，猜測是實例序號），
證實**每顆按鈕都有自己獨立配置的一份小型「量測結果」物件**，不是
共用單一全域物件——這代表要調整高度，理論上可以只調整這幾顆
按鈕自己的複本，不會波及畫面上其他無關的 UI（風險比修改共用存取
函式 `11A4:76C2`／`771C` 本身低很多）。

進一步用 `memory_search` 在整台機器記憶體找同樣的樣板位元組序列
（`01 00 0A 00 00 00 2C 01 0A 00`），一共找到 5 份現存的複本
（`8FD5`／`9036`／`9097`／`9101`／`9165`，各自 `:0008` 起）——
對照到靜態 `DSUN.EXE` 檔案裡完全搜不到這段位元組，**證實這不是
從執行檔內建的靜態樣板直接複製出來的，而是在按鈕／圖示被建立時
即時運算寫入的**（很可能是呼叫某個「量字型高度」的函式，回傳值
剛好是 10，來源還沒追到——見下方「尚待確認」第 2 點）。

### 12.2 現場修改測試：把 5 份複本的兩個高度欄位（`+6`／`+0xC`）
都從 `0x0A` 改成 `0x0C`

用 `write_memory` 直接把上述 5 個位址的兩個高度欄位都改成
`0x0C`（12）。**這只是這次 DOSBox-X 執行期間的即時記憶體修改，
關掉/重開遊戲就會消失，不是永久修好——真正要收進建置流程，還需要
先找到「寫入 10 這個值」的來源程式碼（見下方「尚待確認」）。**

改完後嘗試用 `up`／`down` 鍵重新觸發翻頁想直接用截圖驗證效果，
但**這次連續多次按鍵都沒有觸發任何畫面變化，也沒有再命中任何
中斷點**——不確定是不是先前测試滑鼠點擊（第 7 節）不小心把畫面
焦點切到了選項清單以外的地方，導致方向鍵目前對這個清單不起作用。
`key_down`／`key_up`／`key_tap` 這幾個工具的說明明確寫著是透過

### 12.3 尚待確認的兩點

1. **「改成 12 是否真的解決殘影」還沒有實機畫面證據**，只確認了

   檢視 `cjk_draw_height` 這個貫穿全專案的字高設定本身**（但這個
   值同時也支撐著 VIEW CHARACTER、背包等已經驗收過的畫面，貿然
   調高可能牽動其他已完成的畫面，需要先查清楚這些畫面各自是不是
   也依賴同一個 `cjk_draw_height` 讀值，還是各自有獨立設定）。
   下一輪建議：重新開一次這個對話框（觸發 `WIND-3008` 建立/
   `BUTN` 子物件初始化的那一刻），在「量字型高度」相關的函式
   （`FontGetHeight`，`re_97` 記�AmSg過檔案偏移 `0x2C61F` 呼叫

3. **「越下面的行殘留越多」這個現象，本輪沒有另外找到獨立成因**

## 13. 重大教訓：直接把高度欄位從 10 改成 12，實機導致 DOSBox-X
直接閃退

第 12 節的即時記憶體修改，在原本那次 session 因為 debugger 主控台
被關掉、整個行程死掉而沒能驗證效果。**重開一次 DOSBox-X、重新
走到同一個對話選單，用完全相同的手法（`memory_search` 找到 5 份
複本、把 `+6`／`+0xC` 兩個欄位從 `0x0A` 改成 `0x0C`）再測一次，
這次確實套用成功、也正常 `continue_execution` 恢復執行，但**
**使用者一按翻頁鍵，DOSBox-X 整個閃退關閉**（`get_debug_status`
之後回報 `DOSBOX_NOT_CONNECTED`，訊息是本機軟體主動中止連線，
即行程本身當掉／結束，不是 bridge 連線問題）。

**結論：`+6`／`+0xC` 這兩個欄位不能天真地直接改大**。可能的原因
（本輪都還沒驗證，留給下一輪判斷）：

1. 這個物件可能不是單純的「(寬度,高度)」二元組，`+0xC` 這個
   word 可能同時被其他邏輯當成別的用途解讀（例如索引、位移量、
   或跟 `+0xE` 那個「實例序號」共同組成一個更大的值），改了數值
   但沒有同步改動與它相關聯的其他欄位，導致某處算出不合理的
   位址或迴圈次數而崩潰。
2. 第 12.1 節只驗證了 `36AA:052F`（清除/填色）這一條路徑會讀
   `+0xC`，但**沒有查過這個物件是否還被其他函式（例如命中測試／
   排版計算）用不同方式解讀**——如果有另一個地方把這個物件当成
   「寬 300、高 10」的碰撞矩形去做除法或索引運算，突然變成
   「高 12」可能剛好撞到一個沒被保護好的邊界情況。
3. 也可能單純是「跨兩個 word 欄位（`+6` 與 `+0xC`）值不一致」
   本身就違反了某個「這兩個值必須相等」的隱性假設（因為原始值
   剛好兩處都是 10）——這次測試兩處都同步改成 12，所以這個假設
   本身不太可能是問題，但仍列出來供下一輪排除。

**下一輪如果還要嘗試調整這個高度，強烈建議：**
- **不要再對正在互動、有真實遊戲進度的 session 直接做即時記憶體
  覆寫測試**——連續兩次的即時除錯操作已經造成一次「關掉 Debug
  主控台導致全滅」、一次「改高度導致閃退」，對使用者的遊戲體驗
  干擾很大，之後這類實驗應該只在**不在乎進度、隨時可以重開**的
  情境下做（例如新開一輪對話、或存檔後再測），並且**每次動手前
  要跟使用者明確說「這次操作有當機風險」**。
- 在真的要調整之前，先完整反組譯 `11A4:76C2`／`11A4:771C` 這兩個
  存取器函式的**全部**分支（本輪只追了「成功」路徑，`jc`／
  `jnc`／`0x776A` 那個失敗/例外分支完全沒看過），以及搜尋整個
  `DSUN.EXE`（或用 `xref`／呼叫關係）確認還有哪些函式會讀取這個
  物件的 `+0xC`／`+0xE` 欄位，先弄清楚全貌再動手，不要只驗證了
  「填色矩形這一條路徑看起來合理」就直接動記憶體。
- 因為兩次即時修改都沒能提供「改完之後殘影是否真的消失」的正面
  證據（一次死在驗證前、一次直接讓遊戲崩潰），**目前唯一有把握、
  風險可控的修法仍然是第 10 節方案 1（限制譯文單行長度，完全不
  碰任何 binary/記憶體）**，下一輪或現階段應該優先往這個方向走。

實際文字長度縮放」這個新的可疑點

使用者實際操作到殘影重現的那個瞬間，**這次改用純讀取方式**（不再
寫入任何記憶體），在那個當下直接讀取 4 顆選項按鈕（`91C5`／
`915A`／`90F6`／`908C`，對應 `0x081C`~`0x081F`）目前的完整狀態：

  **第 9 節「erase／draw 位置可能有落差」這個懷疑方向，到此可以
  排除**：不管是乾淨翻頁還是正在殘影的當下，四列的位置數值都是

- **但四顆按鈕的 `+0x6D`（文字長度欄位）在這個當下全部都讀到同一個

  為例，往下掃描 `+0x6E` 開始的文字內容，在第 41 個位元組就出現

  內容長了 12 個位元組**；這多出來的尾端位元組（`00 76 00 9A 00
  00 00 3E 01 73 00 9A 00 0B`）看起來不像正常文字編碼，比較像是
  某種數值／指標殘留。

**這代表 `+0x6D` 很可能不是「這次字串的實際長度」，而是這個欄位
所在物件的「固定容量上限」，每次 `SetButtonText` 都固定複製／
固定印出這個容量長度，不會依照這次真正要顯示的文字長短去縮放**
——這跟第 11 節「次要疑點 1」當時的懷疑方向一致，但這次是在**真正
殘影重現的當下**量到的數據，比之前條件更直接。

**目前還沒解開的關鍵問題**：這些超出真正字串結尾的尾端位元組，
會不會真的被畫面印出來？如果 `36AA:0864`（實際印字函式）內部是
正常的「掃到 `\0` 就停止」邏輯，這些尾端位元組理論上不該被畫出來
（只是留在記憶體裡的無害殘留）；但如果它是依照 `+0x6D` 這個固定
長度去逐字元印、不理會中途的 `\0`，那尾端這些殘留位元組就會被
當成「字元代碼」誤印出來，产生看起來完全不像正常中文字的雜訊
筆劃——這就會是視覺上「殘影／雜訊」的真正成因，而且完全不需要
牽涉「10px vs 11px」這個高度落差。

**下一輪最該優先做的事**：反組譯／單步跟進 `36AA:0864` 內部真正
逐字元輸出的迴圈，確認它是「遇 `\0` 停止」還是「印滿固定長度」。
如果是後者，修法方向會完全不同於第 9／10 節設想的「加大清除
高度」——而是要修 `3241:07FA` 複製文字進 `+0x6E` 時的邏輯，讓它
只複製到真正字串的 `\0` 為止（並把 `+0x6D` 同步寫成真正長度，
或至少確保尾端沒被印出的殘留位元組不會被當成字元編碼），這是
單純的「複製長度算錯」bug，理論上修正風險比動態調整某個共用存取
函式的回傳值低很多（但第 13 節的教訓仍然適用：**任何要動手寫入
之前，都要先跟使用者說清楚有當機風險，且最好挑一個不在乎進度
的時間點測試**）。

## 17. 靜態＋唯讀動態複驗字元 blit 迴圈：確認畫字函式本身沒有
off-by-one，但找到「陰影」是下一個最可疑的方向

使用者堅持這是優先問題後，做了一次完全零風險（純反組譯＋唯讀
斷點，沒有任何 `write_memory`）的深入複查，鎖定畫「單一字元」的
最底層函式 `36AA:06C0`（`re_96` 6.4 節已定位過的同一個函式）：

### 17.1 確認畫字迴圈本身沒有 off-by-one

完整反組譯 `36AA:06C0`~`07DF` 後確認：外層迴圈（X 軸，`si`）以
`cmp si,[bp-18]; jnc→跳出`（即標準 `si < width`）為界；內層迴圈
（Y 軸，`di`）以 `cmp di,[bp-16]; jnc→跳出`（即標準 `di < height`）
為界，兩者都是正常的「小於」判斷，**不是**「小於等於」的 off-by-
one。裁剪判斷（`[bp-12]/[bp-0E]`、`[bp-14]/[bp-10]`）雖然用了
`jbe`／`ja`（含邊界），但那是裁剪範圍的正常定義方式，不是 bug。
**結論：這個函式每次確實精準只畫「這個字元自己 `[bp-16]` 這個高度
值」那麼多行，畫完後把全域游標 Y（`DS:[A376]`）往下推進同樣的
高度值——函式本身找不到任何越界瑕疵。**

### 17.2 追蹤 `cjk_height_helper`（`patch_dsun_scratch_cache.py`）
實際掛勾位置，釐清它真正影響的是哪個變數

反組譯 `patch_dsun_scratch_cache.py` 裡的 `cjk_height_helper`／
`GLYPH_HEIGHT_LOAD`（file offset `0x0704`，即 `36AA:0704`）確認：
這個 helper 掛勾在**寬度變數 `[bp-18]`** 的來源（不是高度變數
`[bp-16]`！`[bp-16]` 直接從字形點陣圖自己的第一個 word 讀取，
完全不受這個 helper 影響）。helper 邏輯是：

```asm
mov ax, 9        ; 預設 9（原版 ASCII 高度）
cmp byte [bp+06], 0x7F   ; 這次要畫的字元代碼是不是 0x7F（CJK 標記）？
jne +1
inc ax           ; 是的話 AX 變成 10
ret
```

用唯讀中斷點在 `36AA:0704`（call 這個 helper 之前）連續攔了好幾次
翻頁重繪的實際字元，直接讀到：

- 字元代碼 `0x20`（空白）：原始點陣圖高度 `[bp-16]` 讀到 `4`。
- 字元代碼 `0x7F`（CJK 標記）：原始點陣圖高度 `[bp-16]` 讀到
  `10`，跟 `cjk_draw_height=10` 的設定完全吻合，**沒有發現任何
  單一字元的原始高度超過 10**。

也就是說：**目前抓到的實際字元，畫字迴圈本身的高度上限（`[bp-16]`）
從沒超過 10**，這跟「清除矩形固定 10px 不夠」這個假設出現矛盾
——如果畫的時候本來就只畫 10 行，10px 的清除矩形理論上應該夠用。

### 17.3 最新、尚未證實的假說：陰影可能是獨立疊加、不計入
`height` 欄位的第二次繪製

`re_39` 提過這批中文字形採「10×10 record：前 9 列主字形＋第 10 列
右下陰影」的設計。如果陰影不是單純「字形點陣圖本身最後一列」，
而是**額外用同一顆字再畫一次、往右下偏移 1px 的第二次繪製**（常見
的陰影做法），那麼：

- 主體本身：完整落在 `[bp-16]`＝10 行以內，跟我們量到的數據一致。
- 陰影副本：偏移後最底部那一行畫在「主體最後一行再往下 1px」的
  位置，**這一行不在 `[bp-16]` 算出的任何一次迴圈邊界內，也不會
  被同一次呼叫的清除矩形算進去**——如果清除矩形是依照「單一顆字
  的 `height`」計算，而陰影用的是「畫兩次、疊一個位移」而不是
  「同一顆字裡多一行」，兩者的高度需求就會恰好差 1px，跟使用者
  觀察到的「一般中文字殘影、比較矮的字（本身高度遠低於 10，加 1px
  偏移也還在範圍內）不殘影」完全吻合。

**這個假說本輪沒有時間完全證實**（需要再追 `36AA:0864` 或其呼叫
鏈，確認陰影究竟是不是「多一次偏移繪製」，還是真的內建在同一份
點陣圖的第 10 列裡）。如果證實陰影是獨立的第二次偏移繪製，修法
方向會是：**清除矩形的高度計算，要把陰影的偏移量也算進去（例如
`height + shadow_offset`，而不是只用 `height`）**，而不是像先前
嘗試的「直接把某個共用存取函式的回傳值改大」那麼粗暴、風險又
不明的做法——這樣修改的範圍明確（只影響「清除矩形高度計算」這
一步），理論上不會像第 13 節那樣動到其他函式共用的資料而導致
閃退，但仍然需要先完整確認陰影的繪製方式，才能安全動手。

**下一輪具體行動項**：
1. 反組譯／追蹤 `36AA:0864` 或其上層呼叫，確認一顆 CJK 字是「一次
   `36AA:06C0` 呼叫」還是「兩次（主體＋偏移陰影）呼叫」。
2. 如果是兩次呼叫，找出清除矩形的高度／寬度是在哪個函式、哪個
   時間點計算出來的（本輪已知的 `9165:0004` 這類 rect_ptr 物件，
   透過 `11A4:76C2`／`771C` 存取——但這兩個存取器本輪只追了「正常」
   分支，還沒查過如果傳入「兩次繪製」的完整範圍會不會不同）。
3. 只有在完全確認「陰影需要多少額外像素」之後，才評估要不要／
   怎麼修正清除矩形的計算，並且比照第 13 節的教訓，動手前一定要
   先告知使用者風險、且不要選在使用者在乎進度的時間點測試。

## 18. 本輪收尾：追「陰影是否為第二次偏移繪製」時再次撞見共用
函式雜訊，尚未證實

延續第 17 節，在 `36AA:06C0`（畫一個字元）設中斷點，連續攔兩次
命中，記錄字元代碼與全域游標 `DS:[A374]/[A376]`：

- 第一次：字元代碼 `0x7F`，游標 `(X=153, Y=3)`。
- 第二次：字元代碼同樣 `0x7F`，游標 `(X=153, Y=13)`——**X 沒變、
  Y 剛好推進了 10（跟量到的字高一致）**。

X 完全沒有推進、Y 卻連續推進，代表這兩次命中**不是同一行文字裡
相鄰的兩個字元**（同一行應該是 X 推進），比較像是「同一個 X 位置、
逐行往下」的另一種畫面（例如某個直排列表），而選項按鈕的 X 應該
是 `3`，這裡卻是 `153`——**這兩次命中很可能又是撞到 `re_96` 8.1
節記錄過的共用函式雜訊（圖示列或其他無關 UI 輪詢重繪），不是我們
要追的選項按鈕文字**。第 17.3 節「陰影是否為第二次偏移繪製」這個
假說，本輪沒有時間在正確目標上驗證。

**本輪到此為止**，不是問題已解決，是這一類「在共用底層函式上盲設
中斷點」的做法，難以在合理次數內穩定命中「選項按鈕文字」而不被
其他 UI 雜訊洗版，繼續盲試的邊際效益已經很低。第 17 節的「陰影
偏移」假說仍是目前最有希望的方向，**下一輪建議直接鎖定第 7.3 節
／第 16 節已經建立的過濾條件**（命中後先讀 `+0x54` 父視窗指標，
比對是否等於目前對話視窗 `DS:[4683:0000]`，且 X 座標落在選項按鈕
的 `3` 附近）再繼續往下追，會比重新盲設中斷點有效率很多。

## 19. 修正過的呼叫鏈驗證：確認參數正確，但字元繪製的 X/Y 步進
模式違反直覺，本輪未能完全解開

第 18 節懷疑的「命中共用函式雜訊」，這次用更嚴謹的方式排除：

1. 發現 bias 算錯（前幾節推算的 `-0x1E040`／`-0x19710` 都有誤，
   正確值這次重新用 `memory_search` 校準得到 `-0x1A710`；這個
   overlay 每次 DOSBox-X 重開都可能落在不同位址，**每一輪都要
   重新校準，不能沿用任何前一輪算出的具體數字**）。
2. 用修正後的 bias 找到四選項迴圈函式，中斷點設在其中「真的有
   文字」那個分支的 `call 3241:07FA`，命中後**直接讀取
   `3241:07FA` 呼叫 `36AA:0864` 時的完整參數**（不是只看 `ES`
   暫存器這種間接證據），確認：
   - `x=3, y=13`（`BUTN 0x081C` 自己的位置）；
   - 文字樣板指標＝`DS:3C5C`（跟已知的 `"%C%C%s"` 樣板位址一致）；
   - 文字內容指標指向的本地緩衝區，內容是 9 組 `5E xx yy` 字元，
     跟這顆按鈕當下應該顯示的譯文吻合。
   
   這次**確定**是真正選項按鈕的呼叫，不是誤觸圖示或其他 UI。

3. 從這個已確認的呼叫點往下追 `36AA:06C0`（畫一個字元），卻觀察
   到違反直覺的模式：**連續四次命中，字元代碼全部是 `0x7F`，
   全域游標 X（`DS:[A374]`）完全不變（`153`），Y
   （`DS:[A376]`）卻精準地每次 `+10`（`3→13→23→33`）**。這跟
   「同一行文字裡，相鄰字元應該橫向推進 X」的預期完全相反，反而
   像是 `re_96` 6.4 節記錄過的「垂直清單」模式。但畫面上這行文字
   實際顯示出來明明是正常的**橫向**一行中文，兩者矛盾。

**本輪對這個矛盾沒有解開**，列出兩個可能方向留給下一輪：

- 可能 `0x7F` 在這個位置**不是**代表「畫一個 CJK 字元」，而是
  某種「換行／版面控制碼」，真正的字元圖案是透過另一個尚未定位
  的機制畫出來的（呼應 `re_96` 6.7 節「X 座標推進點至今未知」
  這個懸案，代表這個謎團可能從 `re_96` 到現在都沒解開，不是本輪
  独有）。
- 可能这几次命中根本不是同一顆字元一次次呼叫，而是同一個
  `36AA:0864` 呼叫內部，對**多個不同的格式規格（`%C`／`%P` 等）**
  各自呼叫一次 `0x06C0` 作為「flush/佔位」用途，真正的可見字元
  繪製發生在其他還沒攔到的地方。

**如果真正的字元繪製機制、或負責換行/版面配置的邏輯本身就跟目前
假設的不一樣，那麼第 9/13/17 節鎖定的「清除矩形高度」可能根本
不是問題的正確切入點**——這是本輪最誠實的結論：花了大量來回，
仍未能 100% 定位到「殘影像素究竟是哪一行程式碼多畫出來、或該清
沒清」這個最終答案。

這個 bug 涉及的渲染管線層數很多（WIND/BUTN 物件、共用的
`3241:0426` 繪製函式、`36AA:0864` 格式字串直譯器、`36AA:06C0`
底層字元 blit、還有一個目前意義未明的「垂直步進」現象），本輪
已經：

- 確認了選項按鈕的位置、清除範圍在資料層級是自洽的（第 9、19 節）；
- 排除了好幾個一開始看似合理的假說（換行溢出、erase／draw 座標
  不一致、固定 53 長度覆蓋）；
- 證實直接調整清除高度數值會導致 DOSBox-X 閃退（第 13 節），這

- 找到這個專案自己在 2026-08 也遇過同一類「局部清除跟不上實際

低風險替代方案**（本輪沒有時間實作或驗證，記錄下來供評估）：

- 比照 `re_76` 記錄的 EBOX 關閉機制（「清除不是靠 formatter 傳空
  字串，而是 EBOX destruction 加背景重建」），**在每次翻頁時，
  對整個 WIND-3008 選項清單區域強制做一次完整的背景重繪**（例如
  重新呼叫視窗建立時期用過的「畫整個視窗背景」那個函式一次），
  而不是依賴目前這套逐按鈕局部清除的機制。這樣即使不知道清除
  矩形／字元繪製確切少了幾個像素，只要「整個區域先清乾淨再畫」，
  殘影就不會有機會出現。**缺點**：需要先找到「畫整個視窗背景」

  音效），這本身也是一項新的逆向工程任務，一樣要先在使用者不
  在乎進度的時間點測試。

考慮到這個 bug 牽涉的渲染機制複雜度，已經超出單一 session 能夠
完全解開並安全修復的合理範圍。建議把這份文件（尤其第 19、20 節）
作為下一輪的起點，優先嘗試「整個視窗強制重繪」這條路，而不是
繼續在字元級別的組合語言細節裡打轉。

## 11. 次要疑點（不影響下一輪主線，但值得記一筆）

1. `3241:07FA` 複製文字到按鈕結構 `+0x6E` 時，複製長度用的是
   **目的地按鈕結構自己的 `+0x6D` 欄位值**，不是來源字串的實際
   長度——如果 `+0x6D` 是「這顆按鈕的固定容量上限」，那麼每次
   `SetButtonText` 都會複製滿版容量長度的位元組（不管新字串多短），
   多出來的尾端位元組會是 `0824:37E4` 那個斷行函式的區域堆疊緩衝區
   殘留值。這**理論上**可能讓 `+0x6E` 文字緩衝區尾端夾雜前一次呼叫
   遺留的堆疊雜訊，但因為 `3241:0426` 畫字時是用同一個 `+0x6D`
   欄位當作「要印幾個字」的長度依據（見第 2 節 `0x05EC` 附近），
   如果這個欄位本身沒有跟著新字串長度同步更新，就會固定印出「滿
   容量」長度的文字（包含尾端雜訊字元）——這如果成立，會是另一種
   殘影成因（印出雜訊字元，而不是背景沒清乾淨），下一輪如果假說 1
   跟假說 2 都被排除，可以往這個方向查。本輪沒有時間確認 `+0x6D`
   的值究竟是「固定容量」還是「當次字串長度」（如果是後者，這整段
   疑慮就不成立）。


## 21. 2026-09-20：參照 Hires Text 的繪圖與清除機制

這次不再假設「清除矩形高度不夠」就是根因。`D:\git\dsun-hires-text-poc\v9`
保留了同一款遊戲在 Mode-X 雙頁面下的實測資料；它提供了這個問題正確的
頁面生命週期模型。

### 21.1 Hires Text 已確認的頁面模型

- 完整頁面使用 surface 0／1，分別對應當時的 `A000`／`A400` backing page；
  `show_page(FFFF)` 會切換這兩頁的顯示角色和 resident descriptor。
- 對話選項是 surface 3 的局部視窗。surface 3 連到 backing surface 1，且有自己的
  clip rectangle；它不是獨立的完整畫面。
- Hires Text 的 RAM mirror 實作保留了 `ram_buffer_owned_rect_copy`：先解析來源與
  目的 backing surface，再只複製指定矩形。這是「兩張頁面都要取得同一段背景」的
  既有實作模型。

上述資訊來自 `delegation/result-010.md`、`result-012.md` 與
`src/ram_buffer_gateway.asm`。該 assembly 是 Hires Text 的 EMS mirror，不能直接
貼進目前的 CJK staging build；但它已證明頁面同步要以 backing surface 為單位，而非
僅改按鈕的資料矩形。

### 21.2 不能直接借用的全頁 copy

`delegation/result-068-page-copy-owned-v72.md` 定位到一個完整畫面 copy：

```text
5F05:2FED  ->  1CC2:00B0
source surface 5  ->  destination surface 1
```

它用於離開回覆頁時，把預先保存的完整世界背景復原。MORE 翻選項頁時並不走這條路。
若在 MORE 時強制呼叫它，會把剛建立的 `WIND-3008` 對話面板一起蓋掉，因此不可作為
本問題的修補。

### 21.3 本專案的直接實測

目前 build 的真正局部清除鏈已確認為：

```text
BUTN redraw
  3241:05D7  ->  36AA:052F
  36AA:0662  ->  222E:3180
  222E:31C2  ->  11A4:672A
```

在選項翻頁時，以原始 VGA plane snapshot 比較 `36AA:052F` 前後，選項所在的下方區域
確實被改寫；再比較同一次 `show_page(FFFF)` 前後，變化落在另一個 physical backing
page。這解釋了兩項現象：

1. 把 choice rect 的 `+0x0C` 高度從 10 暫改成 12、13 甚至 30，最終可見畫面都沒有
   改善；清除寫到的並不是最後顯示舊字殘影的那一頁。
2. 越靠下的選項殘影越多，因為每個 slot 都在錯頁留下了上一頁的圖樣，而新頁只更新
   了其餘位置。

此外，空白 slot 的長度 byte 已暫改為零測試，使它們完全略過文字 renderer；殘影仍在。
因此固定 53-byte 選項文字 buffer 也不是這個問題的原因。

### 21.4 修補方向與下一個驗證點

修補必須同步的是 `WIND-3008` 選項區的**背景像素**，不是調整 glyph 或 `BUTN` 的
文字資料。可行方向有二：

1. 在 MORE 的 page transaction 中，將 `36AA:052F` 已清除的 choice rectangle 同步到
   下一個要顯示的 backing page，再讓原本的 slot redraw 繼續執行。
2. 在 page flip 後，以既有的視窗背景組合路徑重新畫完整個 `WIND-3008` 選項區，再畫
   新頁的選項。

下一步先在 `222E:3180 -> 11A4:672A` 的實際呼叫中記錄「局部清除所解析出的 surface
與 physical segment」，並與 `11A4:5814` 的下一顯示頁比對。這可讓修補針對正確的
來源與目的頁面，不會誤用關閉對話才需要的完整 surface-5 copy。

## 22. 獨立複驗：用 `vga_snapshot` 直接比對像素，確證第 21 節的
雙緩衝理論

第 21 節的結論這次用**另一套完全獨立的方法**複驗過，結果一致：不看
暫存器／指標，直接用 `vga_snapshot` 在 `36AA:052F`（清除/填色呼叫）
執行前後，各抓一次兩個 backing page 對應的原始 VGA 記憶體（plane
0／1，位移 `0x2FD0`／`0x6FD0`，剛好對應選項按鈕所在列、相差
`0x4000` 的兩個 page）。同時讀出 CRTC 暫存器：
`start_address_high=0x40, start_address_low=0x00`，即目前顯示頁的
起始位移是 `0x4000`——代表**位移 `0x6FD0` 那一頁才是目前螢幕上看得
到的頁面，`0x2FD0` 是目前看不到的背後頁**。

比對結果：

- 執行 `36AA:052F` 前，`0x2FD0`／`0x6FD0` 兩頁在這個區域內容幾乎
  相同（都還殘留著字元圖案的高熵位元組）。
- 執行後，**`0x2FD0`（背後頁）的內容變成了明顯規律、低變化的
  背景色 pattern，證實清除確實有效**；**`0x6FD0`（目前顯示頁）
  逐位元組比對完全沒有變化，一個位元組都沒動。**

**這證實了第 21 節的結論：清除呼叫本身正確無誤，但寫的是目前
「沒有顯示」的那個 backing page，畫面上實際顯示的那一頁完全沒被
碰過。** 這解釋了為什麼調整清除高度（10→12→22→30…）、調整文字
長度／內容，全部都測不出效果——因為這些嘗試全部發生在「有沒有
清乾淨」這個正確的環節，但清乾淨的是錯誤的頁面，跟畫面上看到的
殘影完全無關。

**根因至此已有兩種獨立方法交叉驗證，可信度高，可以視為確認。**

### 22.1 建議的修法方向（尚未實作）

既然清除本身沒問題，只是寫錯頁，修法不需要動清除高度／矩形計算，
而是要讓同一次重繪也同步寫到「目前顯示中」的那一頁。可行做法：

1. 在 `36AA:052F`（或其呼叫端 `3241:0426`）完成一次局部清除＋畫字
   後，**多做一次同樣的寫入，目標位移加上／減去 `0x4000`**（依照
   當下 CRTC `start_address` 判斷目前顯示頁是哪一個，寫到「目前
   顯示頁」對應的位移）。這是最小、最直接的修補，只多寫一次同樣
   內容到另一個位移，不改變任何清除範圍或文字邏輯。
2. 或者，比照第 21.4 節建議，在 page transaction／MORE 換頁的
   當下，找到「該次重繪之後，究竟有沒有接著呼叫 `show_page`」，
   如果 MORE 換頁根本不會觸發 `show_page`（不像正常畫面更新那樣
   兩頁交替），那麼從一開始就不該寫到「背後頁」，應該直接判斷
   CRTC 目前顯示頁、寫到正確的那一頁，不需要「額外多寫一次」。

**下一步驗證重點**：確認 MORE 換頁事件本身，前後有沒有呼叫
`show_page`（頁面翻轉）。如果**沒有**，代表這整個重繪原本就設計
成「畫在下一個要顯示的頁」，但 MORE 換頁這個特殊情境從來不會真的
觸發後續的翻頁動作，導致寫入的內容永遠不會被顯示出來——這樣的話，
方案 2（直接判斷並寫到目前顯示頁）會比方案 1（額外多寫一次）更
根本、更省事。這是下一輪應該優先確認的問題。

## 23. 完全定案：不是繪圖邏輯的錯，是 MORE 換頁完全沒有呼叫
`show_page`

延續第 22 節的驗證重點，直接找到並反組譯了 `11A4:5814`——這正是
`show_page` 函式本身：

```
[11A4:118E]      全域「目前顯示頁」旗標（0 或 1，兩者對應 A000／A400）
show_page(page)：
  若 page == 目前 [118E] -> 什麼都不做，直接返回
  否則（含 page==0xFFFF 強制翻轉）：
    [118E] ^= 1                              ; 翻轉旗標
    (ax, bx) = ([118E]==0) ? (A000,A400) : (A400,A000)
    [11A4:0004] = ax   ; 「目前顯示中」的實體 segment
    [11A4:0006] = bx   ; 「目前背後」的實體 segment
    算出對應的 CRTC start address，寫入 port 0x3D4/0x3D5 完成真正翻頁
```

實機讀到：`[118E]=1`，`[11A4:0004]=0xA400`（目前顯示頁）、
`[11A4:0006]=0xA000`（目前背後頁）。而第 22 節驗證過選項按鈕的
重繪固定寫到「A000 對應的那個 offset」——**這剛好正是 `[0006]`
「背後頁」欄位所指的那個頁！**

**這代表選項按鈕的繪圖／清除邏輯完全正確、完全正常**：它就是按照
標準雙緩衝設計「永遠畫在背後頁」，沒有任何 bug。**真正、唯一的
問題是：`MORE` 換頁這個互動，從頭到尾都沒有呼叫 `show_page` 去把
剛剛畫好的背後頁翻上來顯示**——這也直接解釋了第 22 節量到的
「翻頁前後 CRTC start address 完全沒變」這個現象（因為根本沒執行
翻頁）。

### 23.1 修法方向（已收斂，風險大幅降低）

因為問題不在畫面內容或清除範圍，只在「畫完之後忘記翻頁」，修法
變得非常單純：**在 `MORE`／換頁的處理流程最後，補上一次
`call 11A4:5814`，參數傳 `0xFFFF`（強制翻轉，等同於原本 `show_page`
支援的「不管目前是哪頁，一定翻」語意）**。

這個修法風險比之前任何一次嘗試都低，因為：
- 完全不用碰清除矩形、字型高度、文字內容或長度——這些全部已經
  證實是正常運作的。
- `show_page` 本身是遊戲原生、到處都在用的機制（不是我們自己兜出來
  的邏輯），呼叫它不會有「不知道會不會波及其他畫面」的疑慮。
- 若翻頁後畫面上其餘內容（NPC 對話框、人物立繪等）本來就已經跟
  背後頁同步（因為對話框開啟後除了選項文字，其餘內容並未再變動），
  翻頁應該只會讓「剛更新好的選項文字」正確顯示出來，不會連帶
  把其他東西弄亂。

**唯一還沒驗證的風險**：如果背後頁在這個當下，除了選項文字之外，
還有其他「尚未同步」的舊內容（例如上一次翻頁前的殘影，這正是我們
正在修的問題——換句話說，背後頁目前可能同時混著「這次更新好的選項
文字」和「更早之前殘留、從未真正翻頁顯示過的舊選項文字殘影」），
直接翻頁可能會讓這些**尚未被看過的舊殘影一次性全部曝光**，反而
讓使用者第一次看到更多雜訊，而不是更少——但只要之後每次換頁都
正確呼叫 `show_page`，從下一次翻頁開始應該就會回歸正常（因為每次
翻頁後角色互換，下次重繪會畫在「新的背後頁」，而新的背後頁在
上一輪已經是「使用者剛看過的正確畫面」）。

下一步：找到 `MORE` 換頁事件處理完 4 個按鈕重繪之後、回到主迴圈
之前的確切位置（呼應第 2 節已知的四選項迴圈函式結尾），評估在
該處插入 `call 11A4:5814` 的可行性與所需的程式碼空間（code cave）。

## 24. 實機測試第 23.1 節修法：定位到真正的換頁函式、發現旗標
被無關程式碼污染、最終證實「整頁翻轉」會導致當機

延續第 23.1 節「下一步」，本節在**全新重開的 DOSBox-X session**（見
第 24.0 節環境說明）用直接讀堆疊的方式，精確定位到第 2 節文件化的
「四選項迴圈函式」在這次執行期的真正位址，並實際測試了 `show_page`
修法——結果**證實此修法不可行，且已造成 DOSBox-X 當機**。

### 24.0 本輪環境重開紀錄

  bridge 出現「回應 id 持續錯位」（`DOSBOX_PROTOCOL_ERROR`），重試
  無法恢復，且當時螢幕已進入不明狀態。使用者主動關閉 DOSBox-X，
  由本輪重新用 `Start-Process` 啟動 `scratch_test/
  cjk_display_staging_v83_dialogue_four_paged/launch-dosbox-x.cmd`
  （與第 1 節记录的同一個 build），重開後 bridge 恢復正常。
- **重要更正**：畫面右半邊那片「雜訊」在**全新重開、尚未做任何
  操作**時就已經存在，證實跟第 21～23 節做的任何實驗都無關，是這個
  build（或 `capture_frame` 截圖工具讀取超出遊戲實際可視寬度的
  VRAM）本身既有的現象，不是我們造成的損壞。第 22 節提到的「翻頁後

  嚴重的真正問題）。

### 24.1 用「直接讀取堆疊」取代 `get_call_stack` 工具找出真正呼叫鏈

這次改用更可靠的方法定位「MORE 換頁後、四個按鈕重繪」的迴圈函式：

1. 在 `3241:0426`（共用重繪函式）下中斷點，用 `key_tap` 送
   `down` 觸發換頁（**使用者提醒：滑鼠移進遊戲視窗本身就會觸發
   這個中斷點，改用方向鍵送出按鍵更乾淨**）。
2. 中斷點命中後，**不要相信 `get_call_stack` 工具回傳的多層
   `return_address`**——實測發現這個工具回傳的每一層 `return_address`
   都硬套用當下的 `cs`（例如全部標成 `3241:xxxx`），但呼叫鏈中其實
   混雜了真正的 far call（例如從可重定位的 overlay 呼叫固定的
   `3241` 段），這種情況下堆疊上存的返回位址其實是 4 bytes
   （IP+CS），`get_call_stack` 似乎只按 2 bytes（純 near return）
   去解讀整條鏈，導致越往上层的 frame 資料越不可信、甚至互相矛盾。
   **可靠的做法是在中斷點命中的當下（子函式的 prologue 都還沒執行
   前），直接用 `read_memory` 讀 `SS:SP` 這 4 個 bytes，自己解讀
   前 2 bytes 是返回 IP、後 2 bytes 是返回 CS**——這樣才在
   `3241:0426` 的呼叫鏈上，精確追出：`3241:0426`
   ← `3241:07FA`（`SetButtonText`，確認過就是第 2 節文件化的函式）
   ← **`5FD1:0CA2`**（真正的四選項迴圈函式，這次執行期的 far call
   返回位址，`CS=5FD1` 是實際執行用的 segment，不是憑 bias 換算出的
   任何「等效」segment 別名）。
3. **教訓**：對動態重定位的 overlay 下中斷點時，即使用 bias
   算出某個 `linear address` 完全正確，也**不能隨便挑一個 alias
   segment（例如用 `memory_search` 比對命中時回傳的 canonical
   `SEG:OFF`）去設中斷點**——這個除錯器的中斷點比對似乎是精確比對
   `CS:IP` 這個 pair，而不是先解析成 linear address 再比對，
   如果 CPU 實際執行時用的 CS 剛好是「同一個 linear address 的
   另一個等效 segment 值」，中斷點會完全不觸發、沒有任何錯誤訊息。
   後來改用「先抓到一個從這個函式呼叫出去的已知呼叫、讀它壓在堆疊
   上的真正 CS」這個方法，才拿到 CPU 實際使用的 `5FD1` 這個值。

用這個方法換算：檔案位移 `0x7D860`（第 2 節「四選項迴圈函式」的
起點）↔ 這次執行期的 `5FD1:0C30`（`bias = -0x1FB50`，僅本次
session 有效，換算方式見第 1 節）。反組譯確認函式結構跟第 2 節
文件化的 pseudocode完全吻合（`cmp dx,ax` 判斷本頁是否有效選項、
`call 222E:324B` 格式化字串、`call 3241:07FA` 設定按鈕文字）。

### 24.2 找到迴圈結尾的 `call 1DAB:2C8D`，但它其實是無關的計時器函式

反組譯到迴圈結尾（`5FD1:0CC5` `inc si` → `cmp si,4` → 未滿 4 就
`jmp` 回迴圈頂端；滿 4 之後）：

```
5FD1:0CCE: push 0000
5FD1:0CD0: call 1DAB:2C8D    ; 就是第 23 節誤認的「tooltip 相關呼叫」
5FD1:0CD5: pop cx
5FD1:0CD6: pop si
5FD1:0CD7: leave
5FD1:0CD8: retf              ; 函式在這裡結束，完全沒有呼叫 show_page
```

反組譯 `1DAB:2C8D` 本體才發現：**這根本不是「翻頁收尾」用的函式，
是一個跟游標閃爍／按鍵重複速率相關的計時器倒數函式**：

```
1DAB:2C8D(reset_flag):
  若 reset_flag != 0 -> [0BB8] = 0     ; 重設計時器
  若 [0BB8] > 0 -> [0BB8]--             ; 倒數
  若 [0BB8] == 0：                       ; 倒數到 0 才觸發一次
    call (內部函式：設 [38D2]=1, [3CD4]=1)
    call 36AA:0B57                      ; 呼叫另一個未知函式
  return
```

`[11A4:118E]`（`show_page` 用來判斷目前顯示頁的旗標）**會被
`36AA:0B57`（或其呼叫鏈更深處）間接改動**，但這個改動**是計時器
觸發式的（`[0BB8]` 倒數到 0 才會發生一次），跟這次換頁事件完全
無關，純屬「剛好共用同一個全域變數」的巧合／副作用**。實測驗證：
用 `write_memory` 把 `call 1DAB:2C8D` 重導向到一個包裝函式（保留
原呼叫 + 額外呼叫 `show_page(0xFFFF)` 強制翻頁）後，單步觀察發現：

- 呼叫前 `[118E]=1`。
- 光是原本的 `call 1DAB:2C8D` 執行完，`[118E]` 就已經自己變成
  `0`（計時器這次剛好倒數到 0，觸發了副作用）。
- 接著我們自己加的 `show_page(0xFFFF)` 又把 `[118E]` 從 `0` 強制
  翻回 `1`——**兩次翻轉互相抵銷，`[118E]` 最終跟呼叫前一模一樣**。
- 用 `vga_snapshot` 讀 CRTC `start_address_high`，呼叫前後**完全
  沒變（都是 `0x40`）**，證實畫面真的沒有任何翻頁效果，跟视觉觀察
  （連續按多次 Down/Up，畫面像素完全沒變化）吻合。

**這解釋了`[118E]` 這個軟體旗標不能直接信任**：它會被這個無關的
計時器機制隨機污染，導致它記錄的「目前顯示頁」跟硬體 CRTC 的真實
狀態可能不同步。

### 24.3 修正後再測一次：直接讀硬體 CRTC 判斷目前頁，結果導致當機

把包裝函式改成：先呼叫原本的 `1DAB:2C8D`，然後**直接用 `IN`
指令讀 CRTC port `0x3D4`/`0x3D5` 的 `start_address_high` 暫存器**
（不信任 `[118E]`），把讀到的硬體真實值換算回 `[118E]` 該有的值、
強制寫回 `[11A4:118E]`，最後才呼叫 `show_page(0xFFFF)`——理論上
這樣就不會被計時器的副作用污染，一定能翻到正確的另一頁。

**實機測試結果**：呼叫後畫面上**整個對話框 UI（人物立繪、對話框
邊框、選項文字框）全部消失，直接看到底層的遊戲世界畫面**（就像
對話框從沒開過一樣），而且**緊接著 DOSBox-X 整個行程當掉、bridge
連線中斷、`Get-Process` 確認行程已經不存在**。

**原因分析**：這代表對話框的「固定畫面」（人物立繪、邊框等）**只
在對話框開啟的當下畫了一次，畫在當時剛好正在顯示的那一頁，從未
被複製或重繪到另一頁**。選項按鈕重繪雖然遵守標準雙緩衝（永遠畫在
背後頁），但整個對話框的其餘部分完全不是這樣設計的——它們假設
「這個畫面永遠不會被翻頁」，所以只存在於單一一頁。我們的
`show_page` 呼叫打破了這個假設，翻到了「從未畫過對話框」的那一頁，
後續遊戲邏輯大概是在存取某個因此變成無效/未初始化狀態的資料結構時
才真的當機。

### 24.4 結論：放棄整頁翻轉，改用「矩形鏡射複製」方向

**`show_page` 整頁翻轉修法到此證實完全不可行**，不只是風險高，
這次測試已經實際造成當機。不應該再嘗試呼叫 `show_page` 或任何會
改變 CRTC `start_address` 的操作來修這個殘影問題。

新方向：既然問題只出在「選項文字重繪永遠畫在背後頁，前景頁看不到」
，而對話框其餘部分完全不能承受翻頁，那麼**修法應該完全避開翻頁／
CRTC 這一層**，改成：

1. 選項文字重繪（`36AA:052F` 清除 + `36AA:0864`/`36AA:06C0` 畫字）
   照原本邏輯畫進背後頁之後，**額外把這個矩形的內容用 VGA latch
   技巧（`Write Mode 1`：讀一個位址的資料到 latch，寫另一個位址時
   CPU 資料被忽略、直接寫回 latch 內容，可以一次做完 4 個 color
   plane 的複製）鏡射複製到目前顯示中的那一頁**（位移相差固定的
   `0x4000`，方向依 `[0004]`／實測的硬體 CRTC 值決定，但**只做
   VRAM-to-VRAM 複製，完全不去動 `[118E]`／CRTC/`show_page`**）。
2. 這個做法的風險大幅低於整頁翻轉：因為畫面上「目前顯示中」的那
   一頁永遠不變，我們只是額外把新文字的像素多寫一份到它身上，不會
   曝露任何從未畫過的區域，也不會影響對話框其他固定內容。
3. 下一步：确认選項按鈕矩形的實際螢幕座標（寬度已知為
   `300`，高度目前是 `10`；X/Y 起點需要從 `patch_dialogue_menu_wind.py`
   的 Y 座標公式或即時讀取 rect_ptr 物件取得)，寫一個小的 VRAM
   latch 複製迴圈（每個 plane 逐 byte 複製 `height` 列 ×
   `width/4`-ish bytes，實際 byte 數需要依 VGA 記憶體排列公式
   確認），插入點改成緊接在 `36AA:052F`／文字繪製完成之後（而不是
   迴圈結尾的 `1DAB:2C8D` 呼叫點，因為現在要「每個按鈕各自複製自己
   的矩形」，不是「整頁翻一次」）。

## 25. 實作「鏡射複製」修法：重繪兩次＋暫時切換背後頁指標

第 24.4 節提出的方向後來簡化成更容易實作、風險更低的版本：**不用
自己寫 VGA latch 複製迴圈，而是直接重新呼叫遊戲自己的重繪函式
`3241:0426` 一次，把目標頁偽裝成目前顯示頁**。

### 25.0 本輪環境重開紀錄

上一輪（第 24 節）測試造成 DOSBox-X 當機，使用者關閉行程，本輪重新
用 `Start-Process` 啟動同一個 build 重開。用第 24.1 節的方法（直接
讀堆疊，不信任 `get_call_stack`）重新定位這次執行期的四選項迴圈
函式：檔案位移 `0x7D860` 這次對應到 `5F82:0000`（`bias=` 依當次
`memory_search` 命中結果換算），迴圈結尾的
`call 1DAB:2C8D`（原本第 23～24 節誤認的「翻頁收尾」，其實是無關
的游標閃爍計時器，見第 24.2 節）這次落在 `5F82:00A0`。**教訓**：
既然 `write_memory`／`read_memory` 是照 `linear = seg*16+off` 定址，
不像中斷點需要精確比對 CPU 實際使用的 CS，所以只要重新
`memory_search` 同一段 anchor bytes，直接在命中的 canonical
alias 位移上 `+0xA0`（第 24.1 節量出的固定偏移量）就能拿到這次
session 的呼叫點位址，不需要再額外用讀堆疊的方式去反推「真正 CS」
——那個步驟只有設**中斷點**時才需要。

### 25.1 呼叫慣例確認：`3241:07FA`（`SetButtonText`）內部呼叫
`2D55:049E` 的真正參數編碼

反組譯 `3241:07FA` 本體（固定、非重定位段，位址每次 session 都一樣）
找到內部呼叫 `2D55:049E` 的確切程式碼：

```
3241:084B: push word [bp+0A]      ; controlID（word，movsx 過的 dword 只取低 word）
3241:084E: push dword 4E545542    ; "BUTN"——這是直接把 4 個 ASCII bytes
                                   ; 當成一個 32-bit immediate 值 push 進去，
                                   ; 呼叫端完全不需要「BUTN」字串的記憶體位址！
3241:0854: push dword [bp-04]     ; windowHandle（dword，SetButtonText 一進來
                                   ; 就從 [bp+06] 快取到這個 local）
3241:0858: call 2D55:049E         ; 回傳 dx:ax = 按鈕結構遠指標
3241:085D: add sp,000A
```

這個發現讓「鏡射複製」修法不需要自己找/嵌入任何字串常數，直接把
`66 68 42 55 54 4E`（push dword 0x4E545542）原樣抄過去即可。

呼叫 `3241:0426`（共用清除＋畫字函式）的慣例（從一個姊妹函式
「設定 enable/disable」內部的呼叫點反組譯確認）：

```
push 0002                 ; si＝元件類型碼，選項按鈕固定是 2
push dword 按鈕遠指標       ; (offset 在前/低位, segment 在後/高位)
push cs                    ; 呼叫端跟 0426 同一個 3241 段，用 push cs
call near 0426             ;   + 近呼叫偽裝成遠呼叫，讓 0426 的 retf 正常運作
add sp,0006
```

**我們自己的包裝函式因為執行在 `4B7A`（跟 `3241` 不同段），不能用
`push cs;近呼叫` 這招**——改用一個貨真價實的遠呼叫
（`9A <offset> <segment>`）取代，效果完全等價：CPU 執行遠呼叫時一樣
會把（IP, CS）依相同順序、相同格式壓進堆疊，`0426` 內部的 `retf`
分不出差異，這樣改完全安全，不需要在乎呼叫端跟被呼叫端是不是同一段。

### 25.2 包裝函式最終設計（96 bytes，寫在 `4B7A:8000` 這塊已驗證
安全的空白暫存記憶體）

```
call 1DAB:2C8D                     ; 保留原本的游標閃爍計時器呼叫，不變

; 把「背後頁」暫時偽裝成「目前顯示頁」
push es
mov ax,11A4 / mov es,ax
mov ax,es:[0004]        ; ax = 目前顯示頁
mov bx,es:[0006]        ; bx = 真正的背後頁（存起來，最後要還原）
mov es:[0006],ax        ; [0006] := 目前顯示頁（欺騙後面的重繪函式）
pop es
push bx                  ; OLDBACK 存在自己的堆疊上

; 對 4 個按鈕（controlID = 0x081C..0x081F）各自：
;   1. 呼叫 2D55:049E(windowHandle, "BUTN", controlID) 取得按鈕遠指標
;   2. 呼叫 3241:0426(si=2, 按鈕遠指標) 重繪——這次會畫進「偽裝過的
;      背後頁」，也就是真正在螢幕上顯示的那一頁
for controlID in 0x081C..0x081F:
    dx:ax = call 2D55:049E(...)
    call far 3241:0426(0002, dx:ax)

; 還原真正的背後頁指標，後續正常的雙緩衝重繪才不會被我們污染
pop bx
[11A4:0006] := bx
retf
```

完整位元組編碼與逐行反組譯驗證見對話記錄；重點是**完全沒有出現
`show_page`／CRTC／`[118E]` 這些第 23～24 節證實危險的東西**，只是
「重繪兩次、繪圖目標頁面暫時互換」。

用 `set_breakpoint` + `step_over` 完整單步過一次包裝函式全程
（含 4 次 `2D55:049E`／`3241:0426` 呼叫），確認：

## 27. 2026-09-20：靜態複核與下一次唯讀驗證

本節不改動遊戲檔，也不啟動 DOSBox；目的是收斂第 26 節仍有歧義的
兩個前提。

### 27.1 `36AA:052F` 的實際呼叫參數

重新從 `3241:05C3` 到 `05D7` 的 push 順序和一次已捕獲的真實 choice
slot stack 反推，呼叫的參數順序如下：

```text
3241:05C3  push [bp-04]             ; frame / fill index
3241:05C6  push dword [bp-08]       ; rect/frame table far pointer
3241:05CA  push 0000
3241:05CC  les bx,[bp+06]           ; BUTN
3241:05CF  push es:[bx+5E]          ; y
3241:05D3  push es:[bx+5C]          ; x
3241:05D7  call 36AA:052F
```

例如 slot `081C` 在 call 前的實際 stack 依序是 `x=3`、`y=13`、`0`、
`9165:0004`、`0`。所以進入 `052F` 後，`[bp+06]` 是 x、`[bp+08]` 是 y、
`[bp+0C..0F]` 是遠指標、`[bp+10]` 是 frame index；第 26.3 節把
`[bp+08]` 看成 ES 的那次讀值，是取 stack frame 邊界時多偏移了一層。

`11A4:76C2`／`771C` 會以 frame index 解開該遠指標所指向的表項，再取得
實際背景圖框資料。這表示 `BUTN` 可見的外部 rect 欄位雖然可讀為
300×10，仍不足以單獨說明「最終背景圖框和裁剪後實際寫到哪些掃描列」。
第 26.1 的高度實驗仍是很有價值的排除結果，只能排除那個欄位本身是直接
控制可見殘影的開關。

### 27.2 字庫陰影不會寫到第 11 列

目前 CJK bank 的 record 為 `width + width*height`，而 CJK draw-height helper
對 marker `0x7F` 回傳 10。字庫產生器放置陰影時使用 `(x+1, y+1)`，但有
`sy < height` 的限制；超出最後一列的陰影直接不寫入。底層 glyph blit 的
Y 迴圈也以 `di < height` 為終止條件。

因此，橘色虛線不能由「單一 CJK glyph 在 10-pixel record 外多畫一列」造成。
它仍可能是兩次重繪採用不同背景來源、裁剪範圍或目標 page 時，舊像素沒有被
第二次更新覆蓋。

### 27.3 下次 DOSBox 可用時的唯一下一步：逐階段 VRAM 差異

只在使用者自行開啟 DOSBox、且已停在可重複對話的測試點時進行；不選答案、
不載入存檔、不寫記憶體。對一次 `Down` 交易分別保存四個 plane、兩張 backing
page 的選項區掃描列：

1. 原始四個 slot 正常重繪前；
2. 原始四個 slot 完成後；
3. 鏡像 wrapper 的四個 slot 完成後。

比較每個 slot 的文字頂端前後各兩列，尤其是 `y+10` 到 `y+13`。若那些列在
步驟 2 已被清掉、步驟 3 又出現，根因在鏡像呼叫的畫字或裁剪上下文；若兩步
都未改寫，根因在背景 frame／clip 的實際高度。這項量測能決定後續該修 wrapper
的呼叫上下文，或改成同步實際 frame 的範圍，不再重複盲調 height。

### 27.4 首次快照嘗試：新 DOSBox session 沒有鏡像 wrapper

使用者自行開啟的新 DOSBox-X session 已成功連上 native bridge，並停在第一頁
選項。送出一次 `Down` 後，於原始 `3241:05D7 -> 36AA:052F` 呼叫之前保存了
第一份四 plane、兩張 page 的 VRAM snapshot：
`scratch_test/re98_stage1_before_original.json`。

原本預期在原始四格重繪後進入的暫存 wrapper 位址 `4B7A:8000`，此 session
讀回連續 32 bytes 都是 `FF`，且對該位址設中斷點不會命中。這證實第 25 節的
wrapper 是上一個 DOSBox process 的 runtime-only 注入，重開後不會保留；本次
無法取得第 3 階段快照。所有中斷點已移除、遊戲已恢復執行，沒有寫入遊戲檔。

下次量測前，必須先重新注入已驗證的 wrapper，或將它製作成可重複載入的測試
補丁；兩者都屬於 write-memory／程式碼注入，執行前要明確告知使用者風險。

### 27.5 三階段 VRAM 實測完成：wrapper 不是虛線來源

重新注入第 25 節的 runtime-only wrapper（`4B7A:8000`，88 bytes）並把目前
overlay 的原始 timer far call `6000:09E0` 改指向它後，依第 27.3 節取得：

- `re98_stage1_before_original_wrapper.json`：原始 `3241:05D7` 前；
- `re98_stage2_before_mirror.json`：原始四格完成、wrapper 入口；
- `re98_stage3_after_mirror.json`：wrapper 所有四格完成、`retf` 前。

比對方式是將原始 pass 寫入的 page-1 region（`6C00`）與 mirror pass 寫入的
page-0 region（`2C00`）以相同的 page-local offset 比較。四個 VGA plane 都得到：

```text
plane 0: write set 721 bytes，post-write bytes 全相同
plane 1: write set 743 bytes，post-write bytes 全相同
plane 2: write set 773 bytes，post-write bytes 全相同
plane 3: write set 722 bytes，post-write bytes 全相同
```

每一個改寫位址和每一個改寫後的 byte 都一致。包含點狀殘留所在的掃描列，原始
pass 已經產生，mirror pass 只把同一份結果忠實重現到另一張 page。因此第 25 節
wrapper、目標 page 暫時切換、以及 far-call ABI 都不是殘影根因。

下一個切入點應是 `36AA:052F` 解析出的 background frame／clip：原生 pass 本身
沒有將那些舊像素改成正確背景。後續不再調 wrapper；應在 `76C2`／`771C` 解出
frame table entry 後，讀取真正被 `222E:3180` 使用的影像與裁剪資料，找出點狀列
為何仍屬於原生輸出。

### 27.6 根因定位：choice 背景 entry 已被舊 CJK 字形污染

第 27.5 節後改以 `3241:07FA` 的 control-ID 參數過濾，確認真正 choice
`081C` 的 BUTN 是 `91C5:0004`，其 `+68` frame table 是 `9165:0004`。對
frame index 0 套用 `11A4:76C2` 的實際位址計算後，背景 entry 位於
`9165:000E`：

```text
width  = 300
height = 10
type   = 1
pixels = 接續的 3000 bytes
```

讀取這 3000 個背景 pixel 後，發現其中已有 **94 個 `FE`** 與 **5 個 `14`**。
本專案的 CJK glyph renderer 分別使用 `FE` 作前景、`14` 作陰影；乾淨的對話面板
背景不應含這兩個字形色。這表示 `36AA:052F` 所謂的「清背景」不是從乾淨背景
重建，而是重新 blit 一份已被舊選項文字污染的 300×10 快取，因此精確重現了舊字
的點狀殘留。

這同時解釋：

- 為何原始 pass 與 mirror pass 都產生相同虛線；
- 為何調高 rect height 無效：來源 image 本身就是髒的；
- 為何第一頁剛開啟正常、翻頁後才出現：初次建立後快取被選項字形污染。

下一個修補方向是：在對話首次建立且背景仍乾淨時，保存四個 choice background
entry 的 3000-byte pixels；每次 MORE 換頁、每個 choice 重繪之前先恢復對應的
乾淨 entry，再走原生 `052F` 和文字繪製。這樣可保留原有面板紋理，無需猜測或
填色背景。此修補需新的 runtime buffer 與程式碼注入，先以乾淨 entry snapshot
驗證後再製作可重複的 staging patch。

## 28. 正式解法：背後頁只補每個選項最上 2 列

2026-09-23 的實機測試。只改當時那次 DOSBox 行程的記憶體，`DSUN.EXE` 沒有寫入。

### 28.1 做法

`3241:07FA` 負責把文字寫進選項 `081C`–`081F`。在它重畫每一格之前，先把該格
最上若干列換成沒有文字的面板像素，兩個顯示頁都貼（位址差 `0x4000`）。貼完後
還原暫存器，照原本的方式建立堆疊，再跳回 `3241:0801`，由遊戲自己畫新字。

畫面列是 `153 + (編號 - 081C) × 11`。面板取自選項之間的空白列。先貼 2 列時，
空槽最上兩列的舊字會消失；第二頁「你」比「站」更靠左，左緣約 5 個像素原先沒
被蓋到，把範圍延伸到文字左緣後，那一小點也消失。使用者確認殘留已清掉。

之後改成整槽 11 列（一列乾淨面板直向重複 11 次）。11 列正好是一個選項槽，
不會碰到下一格。

### 28.2 使用者確認的效果與代價

11 列版本確實能清掉殘留。代價有兩項：

- 背景閃爍比較明顯。新字畫上之前會先整列刷過一次面板。
- 背景不連續。那 11 列是同一條掃描列重複貼上，不是原本逐列變化的面板紋理。

因此列為候選，不採用為正式修法。若日後要保留這個方向，面板必須是開窗當下、
尚未畫字時存下的完整 11 列原圖，不能用同一列重複。

### 28.3 背後頁只補最上 2 列：正式解法

同一行程再改一次，仍不寫入 `DSUN.EXE`。差異是：

- 只寫目前沒有顯示的那一頁。CRTC 起始位址與 `0x4000` 互斥的那一頁才貼。
- 每個選項只貼最上 2 列，用兩條不同的空白面板，左緣包含「你」比「站」更靠左的那幾個像素。
- 下面的列仍由原本的背景圖處理，貼完才畫新字，再由遊戲自己切頁。

使用者確認這個版本殘留清掉，而且沒有 11 列版本的閃爍與背景不連續。這是正式解法。

固化在 `patch_dialogue_choice_paging`：`3241:07FA` 的 7-byte 開頭改成遠呼叫程式段 `0x2E86:D730`。程式、面板像素與 12 個字型 bank 檔名都放在 `0xD720` 這段啟動後仍保持為 0 的程式空白。資料段尾端會被啟動程式清成 0；`0x9716` 是資料表尾端；`0xFD80` 則是執行期清單，Load 會覆寫跳過去的位址而閃退。

可測試的組合包是 `scratch_test/cjk_display_staging_v85_choice_top_rows`。它包含目前的法術譯文，以及編譯器能安全寫入的對話。選單形狀不合或會移動 `GPL-3` 固定進入點的腳本整段略過，那些段落維持 v84 已翻譯的內容或原文。

### 27.7 Hires Text 參考與正確保存時機

Hires Text 的 `ram_buffer_owned_rect_copy_try` 採用的模型正可參考：先保存已驗證
為乾淨的矩形，之後只逐列複製該矩形回目的 surface；不翻轉 CRTC，也不以全頁
copy 覆蓋對話框。這與本問題所需的「每個 choice 各保留 300×10 pixels」一致。

本次使用者重新讀檔並開啟對話後，已先保存四個 entry 的資料到
`scratch_test/re98_clean_choice_backgrounds.json`。但這個時間點仍在**初次文字畫完
之後**：`081C` entry 的 `FE` 分布跨 `x=1..295`、`y=5..7`，並非單一 UI marker；
其餘 choice 則使用不同選取/前景狀態。故這份檔案可作結構與位址證據，不能當作
最終的乾淨背景來源。

正確擷取點是下一次重新讀檔並進入對話時，在第一個 choice 的
`3241:05D7 -> 36AA:052F` 已完成背景 blit、但 `3241:0426` 尚未進入
`36AA:0864` 輸出第一個字形的短暫區間。此時保存四個 entry 才能讓後續 MORE
重繪前逐一復原真正無字形的背景。
