# DGROUP 尾端候選暫存格：動態監看證實為使用中，靜態零掃描結論作廢

> 日期：2026-08-17
> 前置文件：`re_55_fbov_overlay_relocation_and_ds_relative_redirect_design.md`（尤其第 5～7 節）

## 1. 背景與目的

`re_55` §7 用純離線的檔案零 byte 掃描，在 DGROUP（連結期 `0x4356`，`maxoff=0xA4BC`）
找到最大一段全零候選區間 `DS:0x427A`，長度 25154 bytes，作為「4-byte 暫存格」的候選
存放位置，但文件本身已註明「純靜態零區間掃描無法分辨『真正沒人用的間隙』與『執行期
才初始化的 BSS 變數』」，並排定下一輪要連上 DOSBox-X-AI 用 memory watchpoint 做整場
遊戲執行期的動態驗證，確認候選區真的從未被寫入後才能定案。

本文件記錄這一輪動態驗證的完整過程與結果：**候選區間的假設被推翻**。

## 2. 環境確認

- DOSBox-X-AI MCP server：新對話重新抓取 deferred tools 後可用（`ping`／
  `get_project_status` 正常，`phase: P7E`）。
- 但 MCP server 本身在線不代表 DOSBox-X 有在跑：一開始 `get_debug_status` 回傳
  `DOSBOX_NOT_CONNECTED`（连不到 `127.0.0.1:9876`），因為根本沒有 DOSBox-X 進程存在。
- 用 `scratch_test/cjk_display_staging_v26_gpli_event_relocation_gap2/launch-dosbox-x.cmd`
  啟動（正式可玩 checkpoint v26，build 身分見 `HANDOFF_NEXT_SESSION_2026-08-16.md` §1）。
- **踩坑**：用 Bash 工具跑 `cmd /c launch-dosbox-x.cmd` 失敗——MSYS/git-bash 會把
  `/c` 這種單字母參數誤判成路徑轉換（變成類似 `C:\` 的東西），導致 `cmd.exe` 變成
  開一個空白互動視窗、印完版權訊息就因為 stdin 是 EOF 而立刻結束，`launch-dosbox-x.cmd`
  根本沒被執行到。改用 PowerShell 的 `Start-Process -FilePath launch-dosbox-x.cmd
  -WorkingDirectory <staging 目錄>` 才成功啟動且不阻塞。
- 由使用者手動操作滑鼠把遊戲帶到「讀取存檔 → 進入遊戲 → 開啟物品欄」的狀態（agent
  只用 `capture_frame` 觀察畫面、口頭描述按鈕位置，未自主操作滑鼠，符合既有規則）。

## 3. 交叉驗證：DS/SS 與已知常數一致

暫停後讀到的暫存器：

```text
CS=2D55 EIP=0533   DS=4B7A  SS=4B7A  ES=8566
EAX=4E5402EE EBX=4B7A03F7 ECX=00060000 EDX=00008566
ESI=00002BCA EDI=00000019 EBP=0000FE14 ESP=0000FDFC
```

`DS=4B7A` 與 `re_08`／`re_54` 記錄的同一 build 觀測值完全吻合，且套用 `re_55` §5 的
公式 `CODE_BASE_runtime = DS − 0x14D0 = 0x4B7A − 0x14D0 = 0x36AA`，與 `re_54` 記錄的
`36AA` 一致——這輪連線確實是同一顆已知 build，不是意外跑到別的版本。

另外確認 **`SS=DS=4B7A`**，即堆疊與 DGROUP 共用同一個 segment。多次暫停觀察到的
`SP` 值（`0xFDFC`、`0xFD40`、`0xFEA6`、`0xF81E`、`0xF6DE`）全部落在 `0xF000~0xFFFF`
一帶，遠高於候選區間上限 `0xA4BC`。這代表**堆疊使用的是這個 64KB segment 裡
link-time DGROUP（`maxoff=0xA4BC`）以外的上層空間**，候選區間本身不會跟堆疊直接
重疊——這點交叉驗證通過，但不代表候選區安全（見下節）。

## 4. 動態監看方法與結果

用 `set_real_memory_breakpoint("4B7A:XXXX")`（單 byte「值改變即停」監看點，DOSBox-X
原生 `BPPM` 機制）在候選區間灑了 20 個取樣點，間距約 2KB：

```text
0x427A 0x427D 0x437A 0x4A7A 0x527A 0x5A7A 0x627A 0x6A7A 0x727A 0x7A7A
0x827A 0x8A7A 0x927A 0x9A7A 0xA07A 0xA27A 0xA37A 0xA400 0xA4B8 0xA4BB
```

恢復執行、請使用者照常遊玩（切換物品欄／裝備欄／場景等），**兩個取樣點在合理時間內
就被觸發**，且都能用反組譯直接確認寫入端：

### 4.1 命中一：`DS:0x427A` —— 遠指標組裝函式的固定暫存格

```text
0BC1:04A7   mov  ax,[bp+0A]
0BC1:04AA   mov  [427A],ax        ; 無 segment override，預設 DS=4B7A → 命中
0BC1:04AD   mov  ax,3F9F          ; （監看點在「值改變後」停在這裡，即下一條指令）
```

往前往後展開同一函式（`0BC1:0490~04E8`），可看到它反覆做「從堆疊參數取一個
segment 或 offset → 寫進某個固定位置」的樣式（另外也有 `es:[0003]`／`es:[0001]`／
`es:[0367]`／`es:[0365]`／`es:[0363]` 等寫入，但那些用 `es:` 且 `es` 先被設成
`0x3F9F`／`0x3FA5`，寫的是**別的 segment**，只有 `[427A]` 這行落在 `DS=DGROUP`）。
整體樣式強烈像是「把多個遠指標參數組裝好，供後續呼叫使用」的通用 thunk/marshaling
邏輯——跟 `re_55` §6 原本想借用同一個位置存放的用途性質相同，代表 `0x427A`
本來就是遊戲自己在用的暫存格，而不是空地。

**復現性**：刪除這兩個相關監看點前，同一 `CS:IP`（`0BC1:04AD`）在下一次
`continue_execution()` 後又立刻命中一次（暫存器 `EAX`／`ECX`／`EDX`／`EDI` 均比上次
略增，證明是真的再執行了一輪，不是殘留的舊停止狀態）。代表這個函式呼叫頻率很高
（推測每次跨 overlay 呼叫或每次畫面派發都會執行一次），完全不能拿來借位。

### 4.2 命中二：`DS:0x8A7A` —— 場景轉換批次填充 0xFFFF

使用者手動觸發場景轉換的當下，監看點命中：

```text
0824:3711   repe stosw          ; ES=DS=4B7A, AX=0xFFFF
```

命中時 `EDI=0x8A7C`、`ESI=0x8A74`、`ECX` 低 16 位餘 `0x000C`（12 個 word 未填完），
代表這是一個以 `0xFFFF` 為填值、正在批次覆寫一段連續記憶體的迴圈，範圍涵蓋
`0x8A7A`。從填值挑 `0xFFFF` 這個典型「slot 無資料」哨兵值來看，很像是切換場景時
重置某個狀態陣列（例如物件/事件 slot 表），屬於場景轉換必經路徑，同樣不能借位。

### 4.3 命中當下的其餘取樣點讀值（命中一與命中二之間的快照）

| offset | 值 | offset | 值 |
|---|---|---|---|
| `0x427A` | `0x0E`（剛被寫） | `0x8A7A` | `0x02`（命中二之前的快照，之後被 `0xFFFF` 填充覆寫） |
| `0x427D` | `0x00` | `0x927A` | `0x00` |
| `0x437A` | `0x28` | `0x9A7A` | `0x00` |
| `0x4A7A` | `0x00` | `0xA07A` | `0x4B` |
| `0x527A` | `0x00` | `0xA27A` | `0x9F` |
| `0x5A7A` | `0x00` | `0xA37A` | `0xE3` |
| `0x627A` | `0x00` | `0xA400` | `0x00` |
| `0x6A7A` | `0xFF` | `0xA4B8` | `0x45` |

**關鍵：一半以上的取樣點在遊戲才剛開場沒多久（僅逛過讀檔畫面＋物品欄＋一次場景切換）
就已經是非零值**（`0x437A`、`0x6A7A`、`0x727A`、`0x7A7A`、`0x827A`、`0x8A7A`、
`0xA07A`、`0xA27A`、`0xA37A`、`0xA4B8`）。監看點記錄的是「設定當下的基準值」，
不是磁碟上的 0，所以這不直接等於「這些位置也一定會被動態寫入」，但已經證明
**整段候選區間在遊戲開機初始化階段就被大量塞入真實資料**，跟 `re_55` 假設的
「這是磁碟零掃描找到的空區、可能沒人用」完全相反。

## 5. 結論

1. **`DS:0x427A` 與 `DS:0x8A7A` 已用實機證據確認為使用中**，不可作為暫存格候選。
2. **整個 25154-byte 候選區間的「磁碟零掃描」假設已作廢**：它只反映連結時的初始值，
   不反映執行期真實使用狀況；候選區裡目前已知至少一半取樣點在遊戲早期就非零。
3. **堆疊（`SS=DS=4B7A`）確認不與候選區重疊**（`SP` 恆在 `0xF000` 以上），這點可以
   保留給下一輪，但不足以單獨支撐任何候選位置的安全性。
4. **DS 與 CODE_BASE 差值公式（`CODE_BASE_runtime = DS − 0x14D0`）依然有效且再次
   交叉驗證通過**，不受本輪結論影響，可直接沿用。

## 6. 下一步建議（尚未執行，留給下一輪）

- 不要再用「靜態零掃描找最大候選區」這個方法。改用**執行期記憶體快照比對**：在
  遊戲跑到穩定狀態後，對整個 DGROUP（或至少候選區間）做一次完整 dump（`read_memory`
  可一次讀多個 bytes，不必逐 byte），間隔一段涵蓋多個子系統操作（戰鬥／法術／
  存讀檔／地圖／對話）的遊玩時間後再 dump 一次，逐 byte 比對兩次快照，只有**兩次
  快照都是 0x00**的位置才進入候選名單，比目前的稀疏取樣點監看更全面。
- 值得追查 `0BC1:0490~04E8` 這個遠指標組裝函式的完整呼叫者與用途——如果它本來就是
  Borland overlay 呼叫機制自己的通用 marshaling helper，也許有平行的、尚有餘裕的
  欄位可以合法借用，而不必再找全新的空地。
- 若快照比對法也找不到夠大的穩定候選，可能要回頭考慮 `re_55` §4 提到的另一條路
  （在 4 個 consumer 各自 overlay 單元的私有 fixup table 插入新項目），儘管風險較高。

## 7. 快照比對法找到的新候選：`DS:0x6100`（同一輪已確認，尚未寫入 build）

依第 6 節建議，改用完整記憶體快照比對法，取代原本的稀疏取樣監看點：

1. **基準快照**：遊戲在讀檔進入物品欄、觸發過一次場景轉換後（即第 4 節兩個熱點被
   排除的那個時間點），對候選區間 `DS:0x427A~0xA4BC`（25154 bytes，與 `re_55` §7
   記錄的長度一致）做一次完整 `read_memory` dump，存檔於本機（用
   `D:\git\DOSBox-X-AI\ai\dosbox_client.py` 直接連線讀取＋比對，繞過把 25000+
   bytes 塞進對話上下文的限制）。
2. **第二次快照**：使用者接續大範圍遊玩（含一次存檔——中途觸發了已知的
   `vendor/opends/docs/known-bugs.md` §2.4「Saves but exits」閃退，確認跟本次
   監看無關，存檔本身有成功寫入、重讀 `SAVE08.SAV` 接續）後再 dump 一次。
3. **逐 byte 比對**：25154 bytes 裡有 3638 bytes（約 14.5%）在這段期間內有變動，
   證實候選區間確實高度活躍；但仍找到多段「兩次快照都還是 `0x00`」的連續區間，
   其中最大一段是 **`DS:0x5AB4`，長度 3036 bytes**，其餘較大的有 `0x8E9C`
   （1432 bytes）、`0x9848`（782 bytes）、`0x9EB7`（428 bytes）、`0x5223`
   （341 bytes）、`0x9B99`（323 bytes）。

### 7.1 最終候選確認：`DS:0x6100`

在 `0x5AB4` 這段 3036-byte 全零區間的正中央挑了 `DS:0x6100`（離兩端各留
1500+ bytes 安全邊界），對這 4 個 byte（`0x6100~0x6103`，等同最終暫存格的真實
大小）設精準監看點，請使用者接續遊玩並**明確涵蓋戰鬥、施法、地圖切換、多選項
對話**（先前兩輪快照已涵蓋物品欄、場景轉換、存讀檔）。結果：

- 監看點全程未觸發，`get_debug_status()` 一路維持 `running=true`；
- 遊玩結束後讀值仍為 `00 00 00 00`。

至此 `DS:0x6100` 已經過**三輪獨立證據**交叉確認（兩次全區快照比對 + 一次針對性
主動監看），且遊玩範圍已覆蓋物品欄、裝備欄、場景轉換、存讀檔、戰鬥、法術、
地圖、多選項對話——已知的主要子系統均已測過，暫時沒有再發現任何寫入。

### 7.2 結論與後續

`DS:0x6100`（連結期偏移，換算執行期位址依 `re_55` §5 公式即
`DS_runtime:0x6100`）可作為 `re_55` §6 設計的間接呼叫暫存格候選位置，供下一輪
實作 v37 patch 時使用。**注意**：這仍是動態抽樣驗證，不是數學上的證明——後續
建版測試時仍應保守處理（例如先以只讀觀察 patch 驗證，不直接大改 4 個 consumer）。
本輪全程未寫入 guest RAM，未修改任何 build。
