# v62 材質標籤：懸停名稱已修好，說明卡路徑待確認

日期：2026-09-16

## 目前狀態

v62 候選版（`scratch_test/cjk_display_staging_v62_material_labels`）已建置、
離線驗證（155/155 測試，含新增的 `MaterialLabelsMachineTests` Unicorn 模擬）
全數通過，但**實機驗證未通過**：VIEW CHARACTER 裝備欄右鍵開啟的說明卡，材質
字仍顯示英文（"Wooden"），底部懸停名稱則本來就不含材質字（不受影響）。

本文件記錄本次即時偵錯找到的根本原因，暫時擱置材質翻譯工作，待之後回頭處理。
**以下所有結論皆為本次 session 的即時觀察，尚未做第二次獨立覆核，標記為待確認。**

## 已確認的架構事實

1. v62 修改的呼叫點（`MATERIAL_SITE = 0x6E241`）只影響**底部懸停名稱**的組字
   路徑；VIEW CHARACTER 說明卡走的是完全不同的呼叫點，v62 對它沒有作用。
   這與 `re_54` 原本認定「懸停標籤與說明卡共用同一個 stack buffer」的假設
   不一致——這次的即時追蹤顯示至少在 VIEW CHARACTER 裝備欄情境下，兩者是分開的。

2. VIEW CHARACTER 說明卡的材質組字程式碼**不存在於任何磁碟檔案**（對
   `DSUN.EXE`、`GPLDATA.GFF`、`DARKRUN.GFF`、`RESOURCE.GFF` 逐一位元組搜尋，
   均搜不到即時記憶體中觀察到的呼叫端 byte 序列）。實機追蹤到的呼叫端組
   （即時位址如 `5B7C:0EFF` 一類，每次重進畫面位址都不同）符合遊戲 GPL
   腳本引擎在執行期動態編譯（JIT）成原生 8086 碼的特徵，而非傳統
   FBOV overlay 靜態內容。這代表**呼叫端本身沒有可修補的靜態位元組**。

3. 不論是舊的靜態說明卡呼叫點（`re_54` 記載、位於檔案位移約 `0x0728F5`，
   走 `lcall 0xa8,2`）、還是這次新追到的 VIEW CHARACTER 動態編譯呼叫點，
   兩者最終都會呼叫**同一個常駐、靜態的共用組字串函式**：
   - 檔案位移 `0x22932`（於本次即時追蹤中，其執行期位址為 `2577:0002`，
     在整個測試過程中維持不變，與呼叫端位址會變動不同）；
   - 進入時的引數包含一個遠指標（指向要複製的文字）、一個格式常數、以及
     目的地緩衝區的 `ss:bp` 相對位址；
   - 兩條呼叫路徑都先把材質索引（一個 0-15 的小整數，來源欄位在不同呼叫端
     位移不同：舊路徑是 `es:[bx+0x14]`，VIEW CHARACTER 路徑是 `es:[bx+8]`，
     兩者都先 `and ax,0xf` 遮罩取低 4 位）透過一張**常駐、靜態**的
     4-byte-stride 遠指標表（檔案位移 `0x40A80` 起，每筆
     `{offset_lo,offset_hi,0x56,0x43}`，段固定為 DGROUP 的
     pre-relocation segment `0x4356`）換成指向英文材質字串表
     （檔案位移 `0x4A102`，NUL 分隔："Wooden\0Bone\0Stone\0Obsidian\0
     Metal\0Leather\0..."）的遠指標，再交給 `0x22932` 做逐 byte 複製。

## 為什麼不能直接套用既有做法

- 材質英文表本身雖是常駐、靜態、容易安全修改的資料，但 `0x22932` 對它做的
  是**逐 byte literal 複製**，不會像既有的 NAME 解碼重導向那樣先解析
  Base94 triple；直接把材質表換成 Base94 或 transport byte 不會被正確解碼。
- `0x22932` 是被大量其他 `%s` 呼叫共用的組字函式；`re_54` 已記載
  v34/v35 曾嘗試廣泛修改共用 `%s` byte loop，結果造成空白畫面、閃退或
  main-loop hang，因此**不能整個改寫或廣泛攔截這個函式**。

## 可能的修復方向（尚未實作、尚未驗證）

在 `0x22932` 入口處插入一個**窄範圍條件判斷**：只在遠指標的 segment 等於
DGROUP pre-relocation segment（`0x4356`／執行期 `0x4B7A`）且 offset 落在
材質字串表已知的六個位置（`0x17A2`–約 `0x17CA`）之內時，才把該指標替換成
指向本 session 既有中文解碼器（`cjk_name_slot_cache.asm`）產生的緩衝區，其餘
呼叫完全不受影響。此設計因為條件判斷範圍極窄（只命中材質表六個固定字串），
理論上可避免 v34/v35 那種廣泛修改造成的風險，但：

- 尚未確認 `0x22932` 入口附近是否有足夠、不受 overlay relocation 影響的
  安全插入空間；
- 尚未確認插入條件判斷後是否會影響该函式原有的暫存暫存器／堆疊使用；
- 尚未離線驗證（Unicorn）、尚未建置、尚未實機測試。

下次回頭處理材質翻譯時，應從這個方向繼續，而不是回頭修 `MATERIAL_SITE`
（該點已確認只影響懸停名稱，是既已成立的正確修法，繼續保留）。

## v62 現況建議

v62 目前的 `MATERIAL_SITE` 修改（底部懸停名稱）本身沒有問題，可以視為
獨立、正確的小改動保留；但因為使用者實機驗證時同時看的是說明卡（未受影響），
本次未取得「懸停名稱本身確實顯示中文」的畫面證據，**嚴格說 v62 尚未完成
實機驗證**，狀態應標記為待確認，不可視為已驗收。
