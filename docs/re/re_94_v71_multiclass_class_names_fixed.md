# v71：多職業職業名稱修復完成——雙職/三職角色都能正確顯示中文

日期：2026-09-18

延續 `re_93`。上一輪深入處理多職業職業名稱 bug 後，因為在有限時間內連續
引入新的未知問題（一度比原本更嚴重的亂碼），最終決定保守撤回、退回英文
顯示。本文件記錄這次重新以更系統化方式（先用即時反組譯確認
`339E:016D` 的真正呼叫方式，再動手修，而不是邊猜邊試）處理後，**多職業
職業名稱已完整修復並實機驗證通過**：GERAKIS（單職）、CERMAK（雙職）、
K'RATCHEK（三職）、CILLA（三職）全部正確顯示中文，沒有殘留任何亂碼。

## 1. 先確認根因，再動手——即時反組譯 `5B7C:2DC1`

在 `re_93` 的基礎上，這次先用中斷點＋反組譯把 `5B7C:2DC1`（VIEW
CHARACTER 的多職業組字函式，overlay 25）的完整邏輯釘死，而不是繼續憑
`re_93` 遺留的假設去猜：

- **三職路徑**（`5B7C:2E56`-`2EBE`）：依序讀出 `record+0x23`（職業3）、
  `record+0x22`（職業2）、`record+0x21`（職業1）三個欄位各自的「量寬→
  查表→push 遠指標」，三個遠指標全部 push 完後，**只呼叫一次**
  `call 339E:016D`（模板 `0x1D62`，3 選字串串接版）。
- **雙職路徑**（`5B7C:2EC9`-`2F15`）：結構相同，只是欄位換成
  `record+0x22`／`record+0x21`，**同樣只呼叫一次** `339E:016D`（模板
  `0x1D79`）。
- **單職路徑**（`5B7C:2F1F`-`2F55`）：`v68b` 已經 patch 過的既有邏輯，
  單一 `339E:016D` 呼叫（模板 `0x1CEA`）。

兩個路徑的解碼順序**永遠是「後面的欄位先解碼、slot1 永遠最後解碼」**
（三職：職業3→職業2→職業1；雙職：職業2→職業1），這點在雙職／三職
兩條路徑裡都用即時單步驗證過，不是只看反組譯猜的。

這確認了 `re_93` 的假設：問題出在「先分別解碼、收集全部遠指標，最後才
一次呼叫共用的繪圖函式」這個結構，撞上兩個共用、有限的資源：

1. `name_buffer`：25-byte 共用暫存區，後解碼的欄位會蓋掉先解碼、還沒被
   讀取的字串內容。
2. 7 個實體字形插槽：`decode_start` 原本每次呼叫都重置插槽計數，後解碼
   的欄位會把先解碼欄位的字形點陣資料換掉。

## 2. 修法：兩個獨立、互不依賴的改動

### 2.1 每個非最後欄位改用私有緩衝區

`class_slot2_label_entry`／`class_slot3_label_entry` 原本跟
`class_slot1_label_entry` 共用同一個 `class_decoded`（直接回傳
`name_buffer` 指標）。現在改成各自的 `class_slot2_decoded`／
`class_slot3_decoded`，解碼完立刻把 `name_buffer` 的內容複製到專屬的
`class_slot2_buffer`／`class_slot3_buffer`（各 25 bytes），回傳私有
緩衝區的指標。`class_slot1_label_entry` 永遠最後解碼、之後不會再有
別的欄位覆寫 `name_buffer`，所以維持原樣不需要私有緩衝區。

### 2.2 一次性 `class_skip_reset` 旗標，讓插槽池跨欄位累加

新增 `cs:[class_skip_reset]` byte，`decode_start` 在真正重置
`slot_count` 之前先檢查它：非 0 就跳過重置（讓這次解碼繼續往前一個
欄位已經用掉的插槽上累加），並把旗標立刻歸零（一次性、用完即清，不會
殘留影響下一次呼叫）。

誰來設定這個旗標、設成什麼值，**完全從角色紀錄本身現場判斷，不依賴任何
呼叫歷史**：

- `class_slot3_label_entry`：職業3 在雙職／三職路徑裡永遠是最先解碼的
  欄位（只要它有觸發），所以永遠強制 `class_skip_reset=0`（正常重置）。
- `class_slot2_label_entry`：檢查 `record+0x23`（職業3欄位）是否非
  0——非 0 代表職業3剛剛已經先跑過，這次要接著累加
  （`class_skip_reset=1`）；是 0 代表自己是雙職角色的第一個欄位，要
  正常重置。
- `class_slot1_label_entry`：檢查 `record+0x22` 或 `record+0x23`
  是否有任一個非 0——只要有，代表自己是「群組裡最後一個」，要接著
  累加；兩個都是 0 就是純單職角色，行為跟修復前完全一樣（正常重置，
  不受任何影響）。

這個設計刻意避免用「旗標歷史」判斷（`re_93` 第二輪嘗試疑似用的是
「所有職業 tag 一律跳過重置，只在 slot1 解碼完才清零」這種寫法，對
「這次沒有更早的兄弟欄位」的情況——例如單純雙職的職業2、或任何在
同一畫面裡先解碼過的無關欄位——完全沒有防呆，插槽池會被無關欄位的
殘留內容污染）。改成每次都從角色紀錄本身重新判斷「我是不是這組的
第一個」，不管呼叫順序或畫面上還解碼過什麼別的東西，結果都一定正確。

## 3. 修復過程中額外挖到的既有 bug：`malformed_triple` 只跳 1 byte

第一輪實機測試 K'RATCHEK 時，`class_slot1_buffer`（Fighter，理論上只有
「戰士」2 個字）意外多出兩個不該有的位元組（`2B`、`61`），不是原本
預期的「2 個字形碼 + 結尾 0」。往回追查發現 `decode_start` 的
`malformed_triple`（處理「插槽池已滿、這個 triple 放不下」跟「Base94
資料損毀」兩種情況共用的錯誤處理路徑）只用 `inc si` 跳過 1 個 byte
（0x5E 的 tag byte 本身），沒有跳過緊接著的 2 個資料 byte——這兩個
本來該被跳過的資料 byte，會被下一輪 `decode_next` 當成「不是 0x5E
開頭，所以是字面字元」直接複製進緩衝區，變成看起來像亂碼的多餘字元。

這是**修復前就存在的既有 bug**，只是修復前從來沒有任何欄位會在自己
單獨解碼時就把 7 個插槽塞滿（大部分欄位頂多 2-4 個相異字形），所以這條
路徑幾乎沒被踩到過；這次的「跨欄位累加插槽」設計第一次讓單一角色的職業
名稱有機會在還沒解碼完自己的字串前就把整個插槽池用完，因而首次觸發。
比對同一個函式裡 `emit_slot`（正常配置成功時）跟 `glyph_error`（字形檔
讀取失敗時）都正確用 `add si, 3` 跳過整個 triple，可以確認
`malformed_triple` 原本的 `inc si` 就是寫錯，不是刻意設計。改成
`add si, 3` 後，插槽池滿了的欄位會正確顯示「有效字形 + 一個 `?`」，
不會再夾帶垃圾字元。

## 5. 使用者要求繼續：把插槽池從 7 個擴充到 10 個，消掉最後的 `?`

看過上面「核心 bug 已修好、只剩 1 個字優雅降級成 `?`」的結果後，使用者
選擇同一會期內繼續，把插槽池也擴充掉，徹底消除 `?`。

### 5.1 先推導清楚定址換算，不重蹈 `re_93` 的錯誤

`re_93` 第二輪嘗試擴充插槽池時，新插槽的點陣資料位置算錯了（用
`OFFSET label + FONT_CORE_PAYLOAD_OFFSET(0x239B)`），結果寫到不相干的
FONT 記憶體，撞出比修復前更嚴重的亂碼。這次先用即時除錯把 `[font_pointer]`
相對定址空間跟 `OFFSET label`（CS 相對）定址空間的真正換算關係**用實際
暫存器數值核對出來**，不是重新用理論推導猜：

在斷點停在我們自己的 payload 內部（`class_slot2_label_entry` 等）時讀
`CS` 暫存器，發現 **`CS` 這次會期實測就是 `[font_pointer]` 的 segment
本身**（兩者都是 `0x80E3`），`DS:[0xA378]` 讀出的 `[font_pointer]`
offset 部分則是 `0x0004`——這個 `0x0004` 剛好等於
`plan_name_slot_consumers.py` 裡原本就存在、但先前沒人拿來這樣用的
`FONT_RUNTIME_BASE_OFFSET` 常數。用一個實際位址核對：
`class_slot2_buffer` 的 `OFFSET`（組譯器算出來）是 `0x2C1B`，實測它在
記憶體裡的絕對位置換算回 `[font_pointer]` 相對值是 `0x2C17`，剛好等於
`0x2C1B - 0x0004`。也就是說換算公式是：

```text
[font_pointer] 相對位移 = OFFSET label - FONT_RUNTIME_BASE_OFFSET(0x0004)
```

跟 `re_93` 用的「加上 `0x239B`」方向、數值都不一樣——`0x239B`
（`FONT_CORE_PAYLOAD_OFFSET`）換算的是完全不同的另一件事（trampoline
用它把 `[font_pointer]` 相對轉成 CS 相對，是給「跳進我們自己程式碼」用
的，不是給「定址我們自己的資料」用的），這正是 `re_93` 當初搞混方向
才撞出亂碼的原因。

### 5.2 實作：`glyph_slot_count` 常數化、`class_extra_slots`、
`copy_staging_to_slot` 分岔

- `transport_codes`／`slot_ids` 從 7 個擴充到 10 個。新增的 3 個
  transport code 字元選了反引號（`` ` ``）、底線（`_`）、直線（`|`）
  ——沿用 `re_93` 已經驗證過的方法論（用
  `localization/catalog/dialogue_units.json` 13295 筆對話文本逐一搜尋
  確認完全沒出現過），但**刻意不選 `/`**：VIEW CHARACTER 自己的多職業
  範本本來就會在職業名稱之間畫一個字面上的 `/` 分隔符，如果拿 `/` 當
  transport code，之後任何角色的職業名稱一旦用到它，會把畫面上「本來
  該顯示 `/` 分隔符」的那個字形插槽點陣資料換成某個中文字，導致分隔符
  忽而是 `/` 忽而是亂碼字——這是這次才想到、`re_93` 沒有評估過的風險。
- `allocate_slot` 的插槽數上限從寫死的 `7` 改成 `.equ glyph_slot_count,
  10`。
- 新增 `class_extra_slots: .space 306, 0`（10-7=3 個插槽 × 102 bytes）
  ，是我們自己 payload 裡新增的儲存空間，不是遊戲原本配置好的 7-插槽
  暫存區。
- `copy_staging_to_slot` 依 `active_slot` 是否 `> 7` 分岔：`<=7` 走
  原本的 `first_slot_offset` 算法不變；`>7` 改成
  `OFFSET class_extra_slots - FONT_RUNTIME_BASE_OFFSET`
  加上 `(active_slot-8) * cjk_record_bytes`，換算成跟內建插槽同一套
  `[font_pointer]` 相對位移空間後才繼續走原本共用的複製／指標表寫入
  邏輯（這兩步都不需要因為新舊插槽而分岔，因為它們吃的是「已經換算好
  的統一位移」，不管來源是內建插槽還是擴充插槽）。

### 5.3 實機驗證：K'RATCHEK／CILLA 的 `?` 完全消失

重新建置後，用同一套「斷點在 `call 339E:016D` 前讀三個緩衝區」的方法
交叉核對：K'RATCHEK 的 `name_buffer`（Fighter／戰士）從修復前的
`7E 3F 00`（戰+溢位問號）變成 `7E 60 00`（戰+士，`士` 這次真的分配到
新的第 8 個插槽，transport code 是新選的反引號 `` ` ``=`0x60`）。畫面
截圖確認：

- **K'RATCHEK**：`戰士/德魯師/靈能師`——8 個字全部正確，`?` 完全消失。
- **CILLA**：`保育師/德魯伊/盜賊`——同樣 8 個字全部正確，`?` 完全消失。
- **CERMAK**（雙職，6 字，原本就不需要超過 7 插槽）／**GERAKIS**
  （單職）：重新驗證，畫面跟擴充插槽池之前完全一樣，沒有回歸問題。

目前的職業名稱表（8 種基礎職業，`class_cleric`～`class_thief`）沒有任何
單一角色的三職組合會用到超過 10 個相異字形（K'RATCHEK／CILLA 的 8 個

`malformed_triple` 的正確版本還是會接手，不會亂碼），留作保險。

建置腳本仍是 `tools/build_view_class_multi_candidate.py`；FONT 端的
插槽池擴充邏輯已經合併進同一份 `cjk_name_slot_cache.asm`，沒有另外開
新版本號。Checkpoint 內容已更新為含插槽池擴充的最終版本。

## 6. 使用者回報「職業顏色跟以前不一樣」——查證後確認是遊戲原生行為，不是 bug

擴充插槽池、驗證 K'RATCHEK／CILLA 不再顯示 `?` 之後，使用者用畫面截圖回報
「顯示角色職業時，字體顏色與原本不同」：中文版 K'RATCHEK 的「戰士」是
白色（正常），但「德魯伊」變成紅色、「靈能師」變成洋紅色，跟參考用的
英文版「Fighter/Druid/Psionic」全部統一白色不一樣，看起來像是這次改動
引入的迴歸。

### 6.1 先排除「跟字形內容或插槽有關」

即時斷點在 `call 339E:016D` 之前，逐一核對三個緩衝區指標跟解碼內容，
確認：

- K'RATCHEK 的 `德魯伊`（class_slot2_buffer，transport code `3C 3E 5C`
  ＝實體插槽 4/5/6）跟 CERMAK 的 `保育師`（同樣是 class1/name_buffer，
  但因為 CERMAK 是雙職、`保育師`在解碼順序上排第二、一樣接在
  `class_skip_reset` 累加邏輯後拿到同樣的插槽4/5/6）**用的是完全相同
  的 transport code、完全相同的實體插槽**——但 CERMAK 的 `保育師`
  顯示白色（正常），K'RATCHEK 的 `德魯伊` 卻顯示紅色。
- 同一個字形 ID（`232`／師）同時出現在 CERMAK 的「保育師」（白色、
  正常）跟 K'RATCHEK 的「靈能師」（洋紅色）裡，證明顏色差異**不是
  字形點陣資料本身帶有色彩資訊**，也不是插槽編號決定的。

這排除了「跟這次插槽池修復的核心邏輯有關」的可能性——`class_skip_reset`
只管理實體字形插槽的重置/累加，完全不碰任何色彩參數。

### 6.2 追進 `339E:016D` 呼叫 `11A4:5956` 的顏色/畫筆管理機制

進一步追蹤發現 `339E:016D` 其實是一個 sprintf 風格的格式字串解譯器
（`%C`＝設定顏色、`%s`＝字串、`%d`／`%u`／`%c`／... 共 10 種格式碼，
在 `339E:0396` 有一份 10 項跳轉表）。職業名稱用的模板本身就是
`%C%C%C%s%C/%C%s%C/%C%s`（雙職模板 `0x1D79` 開頭一樣是
`%C%C%C%s`），每個 `%C` 呼叫 `11A4:5956`——這個函式的行為看起來像是
一個有限容量、參照計數式的「畫筆/顏色資源池」（`cmp ax,bx` 比對、
以 `[bx+si+8]` 記錄目前佔用者、`[si+6]` 維護計數），不是單純寫死的
「设定顏色＝某個常數」。

live 追蹤同一組 `%C` 參數（例如 `(0,0xFF)`）在 K'RATCHEK 的職業1（正常
顯示白色）跟職業2（顯示紅色）兩處**參數完全相同**，代表顏色差異不是
來自我們傳入的參數值，而是這個畫筆資源池本身的**累積狀態**——這是
遊戲引擎自己一個沒有文件記錄、狀態相依的機制，追蹤到這裡已經確認
「不是我們的程式碼造成的」，但還沒完全搞懂它精確的觸發條件。
