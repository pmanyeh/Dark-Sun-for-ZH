# 對話選項選單行高與行距機制：逆向分析與修復策略

> 日期：2026-09-19  
> 狀態：已定位根因並實作 `--menu-line-gap`；v77 已建置，遊戲內排版驗收待完成。

---

## 1. 概述與核心發現

在 `re_96` 中，v76 staging build（GPL 弧形對話選項中文化初版）在實機執行 GPL-4@0x03BC 六選一選單（"WHAT DO YOU SAY?"）時，發現選項清單多行文字在垂直方向上緊貼、彼此重疊。當時嘗試透過 `--ebox-line-gap` 及 EBOX line table 調整行距，但完全無效。

本輪逆向工程徹底釐清了原因，並鎖定了關鍵機制：

1. **選項清單根本不是 EBOX 控制項**：
   Dark Sun 引擎的對話視窗是一個**複合介面**。上半部（NPC 對話文字）是 `EBOX` 控制項；下半部（選項清單）則是專屬的 **`MENU` 控制項**（位於二進位段 `0x2C450`）。這正是為何任何針對 EBOX 的補丁對選項選單完全不起作用。
2. **鎖定選項行高計算的核心函式與組合語言指令**：
   - **函式**：`GuiMenuLayout`（檔案偏移 `0x2C51C`，段 `0x2C450` 偏移 `0x00CC`）。
   - **二進位檔案偏移（File Offset）**：`0x2C713` ~ `0x2C719`。
   - **關鍵指令**：
     ```asm
     0x2C713: 8B 46 FA        mov ax, word ptr [bp - 6]   ; 取出 GUI 字型高度 (FONT-100 高度為 9)
     0x2C716: 05 02 00        add ax, 2                   ; ★★★ 核心常數：硬編碼的 +2 行距 ★★★
     0x2C719: 01 46 F4        add word ptr [bp - 0x0c], ax; current_Y += (font_height + 2)
     ```
   垂直選單中，每個選項的 Y 軸推進量固定為：**`font_height + 2`**（英文預設為 $9 + 2 = 11$ 像素）。

## 2. 破解 `re_96` 的盲點與死胡同分析

在 `re_96` 的除錯歷程中，調查方向曾數度走偏，主要導因於以下三個混淆點：

### 2.1 混淆了代碼段（36AA vs 341D）
- `re_96` 將動態追蹤時的 `36AA` 段誤判為 EBOX。
- 經靜態映射確認：
  - `341D`（檔案基底 `0x31390`）：才是真正的 **EBOX** 模組（`EBOX_STORE_LINE_HEIGHT` 位於 `0x3155D`，排版渲染函式 `GuiDrawEBox` 位於 `0x31E51` 即 `341D:0AC1`）。
  - `36AA`（檔案基底 `0x33C60`）：是底層的 **FONT 字型渲染器**（`font_render_char`）。
- 因誤將 36AA 當成 EBOX，導致在尋找 Y 座標更新時找錯了模組。

### 2.2 誤將「字寬推進（X 軸）」當成「Y 軸飄移」
- `re_96` 觀察到 `36AA:06C0` 處修改了全域變數 `[0xa376]`，懷疑每印一個字元 Y 座標都在移動。
- 事實上：`[0xa376]` 是當前文字渲染游標的 **X 座標（水平位置）**。當一個字元渲染完成後，游標 X 推進該字元的寬度（英文 6px、中文 10px）。字型繪製單一字元時**絕對不會**動到 Y 基準線。

### 2.3 誤判 `"%C%C%s"` 是無關雜訊
- `re_96` 在 `36AA:0864` 看到格式化字串 `"%C%C%s"`，誤以為是某些 tooltip 或按鈕的無關程式碼。
- 事實上：這是整個 GUI 系統的頂層格式化文字繪製函式 `GgPrintString`。`MENU` 控制項在繪製各選項文字時（`GuiDrawMenuItem`），正是呼叫這個函式並傳入 `"%C%C%s"`。

## 3. 對話視窗的架構真相：EBOX 與 MENU 的雙控制項

在 Dark Sun 引擎架構中，對話視窗是由多個 GUI 子控制項組合而成：

```
+-------------------------------------------------------------+
| 对话窗口 (Composite Dialog Window)                          |
|                                                             |
| [上半部：NPC 对话文本]                                      |
| -> 控制项类型: EBOX                                         |
| -> 实现模块: Overlay 0x31390 (运行段 341D)                  |
| -> 排版逻辑: GuiDrawEBox (341D:0AC1)                        |
| -> 行高控制: EBOX_STORE_LINE_HEIGHT (0x3155D)               |
| -> 对应补丁: --ebox-line-gap (已实作且有效)                 |
|                                                             |
+-------------------------------------------------------------+
| [下半部："WHAT DO YOU SAY?" 对话选项清单]                   |
| -> 控制项类型: MENU                                         |
| -> 实现模块: Segment 0x2C450                                |
| -> 排版逻辑: GuiMenuLayout (文件偏移 0x2C51C)               |
| -> 行高控制: GuiMenuLayout + 0x01FA (文件偏移 0x2C716)      |
| -> 对应补丁: --menu-line-gap (已實作)                         |
|                                                             |
+-------------------------------------------------------------+
```

因為兩者屬於完全不同的控制項系統，所以先前對 EBOX 所做的任何改動，自然完全不會影響到下半部的選項選單。

## 4. 控制選項行高的詳細逆向分析

### 4.1 排版計算：`GuiMenuLayout`（檔案偏移 `0x2C51C`）

當對話選項產生時，引擎呼叫 `GuiMenuLayout` 計算選單外框與每一個選項項目的幾何位置：

1. **查詢字型高度**（檔案偏移 `0x2C61F`）：
   ```asm
   0x2C61F: 9A 47 28 00 00  lcall 0x2847, 3    ; FontGetHeight([0xa06d])
   0x2C624: 89 46 FA        mov [bp - 6], ax   ; 區域變數 [bp - 6] = font_height
   ```
   對話選單使用的是標準 GUI 字型 `FONT-100`，其高度為 **`9`** 像素。

2. **計算各選項的碰撞偵測外框（Bounding Box）**（檔案偏移 `0x2C6FE`）：
   ```asm
   0x2C6FE: 8B 46 F4        mov ax, [bp - 0x0c] ; AX = current_Y
   0x2C701: 03 46 FA        add ax, [bp - 6]    ; AX += font_height (9)
   0x2C704: 26 89 47 08     mov es:[bx + 8], ax ; item->y2 = current_Y + 9
   ```
   每個選項的點擊判定高度為 `font_height`。

3. **計算下一行的 Y 軸座標（關鍵行距累加）**（檔案偏移 `0x2C708` ~ `0x2C719`）：
   ```asm
   0x2C708: 26 F6 47 1C 02  test byte ptr es:[bx + 0x1c], 2 ; 檢查是否為垂直排列選單
   0x2C70D: 74 0F           je 0x2c71e
   0x2C713: 8B 46 FA        mov ax, [bp - 6]                ; AX = font_height (9)
   0x2C716: 05 02 00        add ax, 2                       ; ★★★ 加 2 像素行距 ★★★
   0x2C719: 01 46 F4        add [bp - 0x0c], ax             ; current_Y += (font_height + 2)
   ```

### 4.2 選項文字繪製：`GuiDrawMenuItem`（檔案偏移 `0x2CA12`）

繪製選項文字時，引擎從項目結構體讀取 `item->y`（`es:[bx + 4]`），並加上 2 像素偏移作為文字頂部起始點（`0x2CBF9: add dx, 2`），再傳入 `GgPrintString` 輸出文字。

## 5. 中文選項重疊／擠壓的數學根因

- **英文原版**：
  - 字型高度 = 9 像素。
  - 大寫英文字母實體高度通常只有 6 ~ 7 像素。
  - 每行間隔 = $9 + 2 = 11$ 像素。
  - 扣除字體後，上下行之間有 **4 ~ 5 像素的留白**，排版清晰美觀。
- **中文繁體版**：
  - 16x15 點陣字型中，中文字本體高度為 **10 像素**。
  - 若加上 1 像素陰影或 DBCS 特殊編排，實體高度達 **11 ~ 12 像素**。
  - 引擎依舊使用硬編碼的 $9 + 2 = 11$ 像素作為行距。
  - **$11 - 11 = 0$ 像素**！上下行漢字筆劃完全貼合，陰影部分直接覆蓋到下一行文字頂部，造成嚴重的「視覺重疊與擠壓」。

## 6. 修復建議與 Patch 方案

### 方案 A：直接修改選單行距累加常數（推薦，最小修改）

直接修改 `DSUN.EXE` 中 `GuiMenuLayout` 的行距常數：

- **目標檔案偏移（File Offset）**：`0x2C716`
- **原始機器碼**：`05 02 00` (`add ax, 2` $\rightarrow$ 步進量 11 px)
- **修改候選值**：
  - **`05 04 00`** (`add ax, 4` $\rightarrow$ 步進量 $9 + 4 = 13$ px，上下行留白 2~3 px)
  - **`05 05 00`** (`add ax, 5` $\rightarrow$ 步進量 $9 + 5 = 14$ px，上下行留白 3~4 px，最接近原版英文呼吸感)

### 方案 B：連動考慮項目碰撞判定區（Bounding Box）

若只修改行間距（`0x2C716`），選項文字彼此分開，但各選項的滑鼠熱區高度仍為 9 px（`0x2C701: add ax, [bp - 6]`）。這在鍵盤數字鍵操作（1~6）下 100% 正常，若希望滑鼠點擊判定區也同步放大，可考慮將 `0x2C701` 的 `add ax, [bp - 6]` 亦做適度調整。但在實務上，選項間距分開通常已經足以提供良好的滑鼠操作體驗。

### 方案 C：注意選單整體外框高度限制

在 `GuiMenuLayout` 的末尾（約 `0x2C748` 附近），選單會計算整體高度並儲存於選單結構體中。若每行增加 2~3 像素，一個 6 項選單總高度會增加 12~18 像素。需在實機驗證時確認 6 個選項的對話框是否會被螢幕下緣裁切。

## 7. 下一個 Session 執行清單 (Handoff Action Items)

在開啟新的對話 Session 後，可依循下列步驟直接執行：

1. **環境準備**：
   - 使用現有的 `scratch_test/cjk_display_staging_v76_arc_menu_options` 作為 base。
2. **實施 Patch**：
   - 以 Python 腳本或二進位編輯工具修改 `DSUN.EXE` 檔案偏移 `0x2C716`：
     - 將 `05 02 00` 修改為 `05 04 00`（13px）或 `05 05 00`（14px）。
3. **實機驗證（DOSBox-X）**：
   - 啟動遊戲並與開場 NPC 對話，觸發 GPL-4@0x03BC 六選一選單（"WHAT DO YOU SAY?"）。
   - 檢驗重點：
     1. 中文選項文字是否垂直分開、重疊現象是否完全消失。
     2. 按鍵盤數字鍵 1~6 測試是否能正常選擇對應項目。
     3. 滑鼠懸停（hover）與點擊選取是否正常。
     4. 最底部的第 6 個選項是否完整顯示在外框內、有無超出對話框邊界。
4. **工具化與固化**：
   - 將此補丁整合進 `tools/patch_dsun_scratch_cache.py` 或建置管線中（例如新增 `--menu-line-gap` 參數）。
   - 建立新 checkpoint（例如 `v77`）。
